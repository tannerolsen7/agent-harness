# Ambition Re-mine — Agentic Platform Engineering (Saul Fernandez / Stripe Minions)

## What this source is (plain English, 2-3 sentences)

A DEV Community article that argues agent configuration is a discipline — "Agentic Platform Engineering" — whose core principle is "treat agent intelligence as infrastructure, not improvisation." It fuses two things: a *reported* summary of Stripe's "Minions" (1,300+ unattended-agent PRs/week, built on devboxes + selective CI + a 500-tool internal MCP "Toolshed" + hard retry caps) and a *proposed* personal three-repo layout (`agent-library` brain / `agent-setup` bridge / `resource-catalog` map) wired together with symlinks. The persuasive force comes from Stripe's industrial numbers; the prescription is the solo-dev file-organization scheme.

## The full-ambition moves this source teaches

The conservative synthesis (pass3) was *unusually good* on this source — it already named five real gaps and resisted the page's generous self-grading. But it filtered those gaps through "is this safety or just token/clarity," ranked the three-repo split as "lower-leverage than it looks," and treated the autonomy-relevant ideas (retry caps, devbox isolation, the Toolshed) as either narrow tweaks or "implementation spike, not now." Under the new charter — autonomy is first-class, the scale is parallel fleets across 5+ repos — several of those dispositions are conservative bias. Here are the distinct world-class moves.

### Move: Hard iteration cap with a defined REJECT / human-handoff state on EVERY agentic loop

- **Plain-English what & why:** Stripe lets CI auto-fix a failing agent PR a maximum of **2 times**, then routes it back to a human — because LLM retries show diminishing returns: the failure mode is not "agent quits too early," it's "agent burns budget converging on nothing." Pass2 §E correctly elevated this from a one-bullet CI detail to a *control-theory* principle: every self-correcting loop in a harness (review auto-fix, `/debug`, `/refactor`, `/cr` re-runs, the `/loop` primitive) needs a hard ceiling and a named state it lands in when the ceiling is hit. Without it, an unattended agent loop can spin indefinitely, spend real money, and degrade the diff while *looking* like it's working.
- **The mechanism:** Add a max-iteration constant to every loop primitive and a first-class `REJECT` / `NEEDS-HUMAN` terminal state. Concretely: `/cr`'s Opus auto-fix gets `MAX_AUTOFIX_ROUNDS` (then it writes a `NEEDS-HUMAN` block instead of looping); `/debug` and `/refactor` get the same; the cloud `/schedule` and `/loop` runs get a budget-and-iteration cap that, on exhaustion, opens a Slack/Linear handoff rather than silently retrying. The handoff state must be *defined* (what artifact it leaves, where the human is paged), not just "stop."
- **Citation:** Confirmed absence — `[ground-truth §3c]`: disk `/cr` is "9 parallel passes (1–9) + Pass 11 `@reviewer` … **No REJECT tier, no UNATTENDED branching.**" There is no iteration ceiling and no handoff tier anywhere in the pass structure.
- **Conservative disposition:** Pass3 already named this its **"single most valuable, model-independent contribution"** and "Highest-value gap" — but then, in pass3 §d ("warrant fresh research?"), it gated even *encoding the number* behind "one short verification pass on current evidence for retry-value decay on Opus-class models … the only place re-research beats synthesis." So the idea was elevated in principle but its *implementation* was deferred-pending-research, and the broader generalization (cap *every* loop, not just CI) was left implicit.
- **RE-JUDGMENT under the new charter:** **ELEVATE — in-scope-now, and bigger than pass3 scoped it.** Pass3 was right to rank it #1 and wrong to gate it behind a research pass. The *principle* (hard cap + defined handoff) is model-independent and needs no further research to adopt — only the *specific number* is model-dependent, and you do not need to know the optimal number to build the mechanism; ship a sane default (2–3) as a tunable constant. Under autonomy-is-first-class this is not a CI nicety, it is the **safety backstop that makes unattended loops survivable**: a bug→PR agent or a cloud-scheduled self-improving loop *without* an iteration cap is the exact "burns budget converging on nothing" failure at fleet scale, multiplied across 5+ repos running concurrently. This should be a cross-cutting harness primitive (a shared `bounded-loop` contract every loop skill inherits), not a per-skill afterthought. Bigger by roughly: one local CI tweak → a harness-wide loop-governance contract that is a precondition for every autonomy feature.

### Move: A disposable, credential-isolated execution environment (the devbox) as the substrate autonomy runs on

- **Plain-English what & why:** Minions works because agents run in **devboxes** — cloud machines pre-loaded with the whole codebase and tools, spun up in ~10 seconds from a pre-warmed pool, running in a **QA environment isolated from production data by default**. Pass2 §D is blunt that this — not the markdown layout — is "the actual product": the agents "just plugged in" to years of platform investment. An unattended agent needs a place to run that it cannot use to damage production, and that can be thrown away and re-created. Worktrees give you *credential* isolation (the Tier-0 firewall keeps prod keys out) but they share the same machine, filesystem, and network — so a runaway agent still has the host.
- **The mechanism:** Build a disposable-environment tier behind the existing worktree/firewall. The resolved facts hand us the substrate: cloud `/schedule` already "clones the repo, runs committed skills, calls connectors" on Anthropic infra with a restricted network by default — that *is* a devbox-equivalent for scheduled autonomy. The build is: (1) make `/schedule` + cloud runs the default execution surface for any unattended/bug→PR work; (2) add an egress firewall for the local-worktree case so a local agent's network is restricted the way a devbox's is; (3) document the pre-warmed-clone pattern so spin-up is fast. This is the body the brain plugs into.
- **Citation:** Confirmed absence — `[ground-truth §3e, §3f, §5]`: no sandbox/devbox/disposable-compute component exists on disk. We have `worktree-create.sh` + the Tier-0 prod-key firewall (`gen-local-env.sh`, `test-local.sh`) `[ground-truth §3e, §6]`, which is credential isolation but not environment isolation.
- **Conservative disposition:** Pass3 §b.5 named it a "confirmed absence" but **narrowed it to "no disposable compute environment, which remains a confirmed absence"** and in §d explicitly demoted it: *"If/when we decide to build disposable-environment isolation, that is an implementation spike, not research"* — i.e., parked as a someday-spike. The old charter's "wrong threat model at solo scale" reasoning (the §F sandbox-stack rejection) sits underneath this demotion.
- **RE-JUDGMENT under the new charter:** **ELEVATE — autonomy changes the threat model the old rejection assumed.** The conservative read assumed a human is at the keyboard, so "same machine, same filesystem" is fine because a person catches a runaway. The moment a bug→PR agent or a cloud-scheduled loop runs *with no human present*, the absence of an environment boundary is the difference between "an agent made a bad commit in a throwaway clone" and "an agent ran an unbounded command on my host." The resolved fact that cloud `/schedule` already provides a restricted-network, repo-cloned, Anthropic-infra sandbox **moots the old durability objection entirely** and means most of this is *adoption, not construction*: make scheduled/cloud the default for unattended work, then add the local egress firewall to close the last gap. This is no longer a someday-spike; it is the execution substrate the whole autonomy charter stands on.

### Move: A machine-readable capability manifest / registry (`library.yaml`) as the harness's single source of truth

- **Plain-English what & why:** Fernandez's `library.yaml` is a central manifest declaring **every** layer, skill, rule, and prompt — what it is, where it lives, where it deploys — and `setup.sh` reads it to install the harness. The non-obvious value isn't installation; it's that a manifest **mechanically catches drift** between what the harness claims to have and what it actually has. Our harness has exactly the drift a manifest prevents: skills exist on disk that no canon page mentions, skills are documented that are empty stubs, a retired skill is still referenced.
- **The mechanism:** A `library.yaml` (or `skills-index.yaml`) at the harness root listing every skill/agent/hook/rule with its path, status (active/stub/retired), owner, and deploy target. A CI check fails the build if a file exists without a manifest entry or an entry points at nothing. This becomes the install descriptor for the plugin+marketplace distribution and the thing `/init` reads to lay down per-repo files. It is the registry the "single source of truth = GitHub" workstream needs.
- **Citation:** Confirmed absence — `[ground-truth §3b, §6]`: skills are inventoried only in prose (canon ~46 vs disk 26, reconciled by hand) with active drift — `/dev` and `/explain` exist on disk but in **no** canon page `[§6]`; `dep-update` documented but an empty stub `[§6]`; `/cr-feature` retired in canon yet still referenced. `skills-lock.json` is a **confirmed phantom** (referenced, never built) `[§6]` — so this is genuinely unbuilt.
- **Conservative disposition:** Pass3 §b.3 named it a "real absence" and correctly noted a manifest "would mechanically catch exactly this drift" and that the lock file is a phantom — **fully accepted as a gap.** It was not dismissed; it just wasn't elevated to a keystone.
- **RE-JUDGMENT under the new charter:** **ELEVATE — from "a real gap" to "load-bearing for distribution."** Under the old single-repo charter a manifest was hygiene. Under "GitHub becomes the single source of truth" + "distribution = plugin + marketplace + thin `/init` template," the manifest is the *spine* of the distribution mechanism: a plugin can't carry permissions and a marketplace needs a declarative descriptor of what it ships, and `/init` needs a list of what to lay down per repo. Across 5+ repos, hand-reconciling 26-vs-46 skills is not a one-time cleanup, it is recurring per-repo rot. So this isn't just "build the lock file" — it's "build the manifest that the plugin, the marketplace, the `/init` template, and the drift-CI all read." That is a first-class keystone, not a hygiene item.

### Move: Cumulative directory-scoped context loading (Layers) — load only what the current directory needs

- **Plain-English what & why:** Layers are markdown that becomes `AGENTS.md` for a specific directory and load **cumulatively** parent→child (global identity → repo git conventions → work safety posture → terraform workflow), so in `work/terraform/` the agent loads exactly 6 global + 1 domain + 1 directory skill — terraform rules never load in a React file. Pass2 §B sharpens this: the transferable insight is **scoping**, not the three-repo split (the two are orthogonal; you can scope inside one repo). The failure it prevents is a flat root `CLAUDE.md` that loads everything everywhere, wasting context and burying the rules that matter for *this* file under rules that don't.
- **The mechanism:** Per-directory `AGENTS.md`/`CONTEXT.md` files that the harness loads cumulatively by path, plus file-pattern rule scoping (a Supabase rule only when touching `src/data/` or migrations; a Tailwind rule only in components). Achievable in-repo today without any repo split.
- **Citation:** Confirmed absence — `[ground-truth §3a]`: our context docs are single root-level docs with no per-directory layer mechanism; "curated context / scoping" is not among declared hooks or mechanisms `[absent from §3e, §5]`.
- **Conservative disposition:** Pass3 §b.1 named it a real gap but flagged it *"token/clarity, not safety"* and noted it is **"partly already pre-authorized to shrink"** because "phrase-keyed skill descriptions → trigger should be the situation" is a Model-Capacity-Audit *replace* item `[ground-truth §9]`. So: real, but rated low-stakes and partially in tension with the "remove scaffold for a stronger model" doctrine.
- **RE-JUDGMENT under the new charter:** **UPHELD-CUT (as the article frames it) — but recover the narrow, correct version.** This is the one place to resist reflexive elevation. Pass2 §G is right that the article is written entirely in the "more curated markdown = more capable agent" frame, and the Model Capacity Audit `[§9]` explicitly *replaces* phrase-keyed / structural-scaffold mechanisms because Opus 4.8 needs **less** layering, not better-organized layering. The failure mode an over-built layer system *causes*: a tree of per-directory markdown that a capable model would have inferred from the code anyway becomes maintenance debt and a per-repo install burden — the exact "scaffold the model has outgrown" the golden rule (`[§9]`: "if you can't name a failure mode the constraint prevents, it's overhead") tells us to cut. **Keep the genuinely load-bearing slice:** file-pattern *rule* scoping for things a model can't infer (which RLS pattern applies, which credential boundary) is worth it; an elaborate cumulative-Layers tree to save tokens is scaffolding a stronger model has outgrown. Adopt scoping-of-safety-rules; reject scoping-as-token-optimization. This is a real UPHELD-CUT with a named failure mode, not conservative bias.

### Move: A curated internal tool registry — the "Toolshed" — small default tool set, expand on demand

- **Plain-English what & why:** Stripe runs a centralized internal MCP server ("Toolshed") hosting **~500 tools**; agents get a *small curated default set* and engineers add more on demand. The failure it prevents: dumping every available tool/MCP into every agent's context dilutes attention, wastes tokens, and gives an unattended agent capabilities it doesn't need (each extra tool is extra surface for a wrong action). Pass1 §4.3 reports it as one of the four load-bearing Minions properties; pass2 §D lists it among the things that *actually made Minions work* (vs the markdown that didn't).
- **The mechanism:** A curated, per-agent default MCP/tool allowlist with on-demand expansion, rather than the current pattern of a large deferred tool surface exposed broadly. For side-effect tools (deploy, open-PR, send-Slack), pair this with `disable-model-invocation:true` so they're removed from the model's context entirely unless a skill explicitly summons them — the resolved fact that makes autonomy safe. The Toolshed pattern *is* the discipline that `disable-model-invocation` enforces.
- **Citation:** Confirmed absence as a *named mechanism* — there is no curated tool-registry component in `[ground-truth §3e, §5]` (the declared hooks/mechanisms list contains no tool-curation layer). Adjacent fact: the global layer carries 15 generic symlinked skills `[ground-truth §2]` with no curation-by-agent.
- **Conservative disposition:** Pass3 **did not surface this as a candidate at all** — it mentioned the Toolshed only inside the "borrowed-credibility" critique (pass3 §c: Minions' value lives in "devboxes, selective CI, Toolshed, retry caps"), as evidence the three-repo split is over-credited, never as a move to adopt.
- **RE-JUDGMENT under the new charter:** **NEW — recover it as a first-class candidate.** The conservative synthesis named the Toolshed only to argue *against* the three-repo split, then dropped it. But under autonomy + `disable-model-invocation` (a resolved fact that maps *exactly* onto "small curated default, expand on demand"), curated tool scoping is a safety mechanism, not a token nicety: it's how you keep a side-effect tool (deploy, force-push, Slack-send, external-API mutation) out of an unattended agent's reach until a vetted skill summons it. Across a fleet calling connectors from cloud `/schedule`, an uncurated tool surface is how an autonomous agent does something irreversible the user never authorized — the PocketOS-class failure the destructive-operation rules already guard against, but at the tool-availability layer. This pairs the article's Toolshed insight with our own resolved `disable-model-invocation` fact to make a concrete safety primitive. First-class candidate.

### Move: Hybrid orchestration — "blueprints" that pin critical steps and free creative ones

- **Plain-English what & why:** Minions uses **blueprints**: a sequence of nodes where some are deterministic code ("run linters" = hardcoded) and some are agentic loops ("implement the feature" = LLM freedom). Critical steps *always* happen; creative steps get model latitude. Pass2 §F surfaces the real tension this creates with the article's other half: `agent-library` says "skills never auto-load, the human invokes everything," while blueprints say "the system automatically sequences steps." For an autonomy harness, the crux is: who decides when a procedure runs — the human (`/skill:x`) or a pinned orchestration that runs unattended?
- **The mechanism:** Encode the unattended workflows (bug→PR, scheduled self-improvement) as blueprints — pinned-deterministic floors (commit/push hooks, `/cr`, tests, the retry cap above) with agentic middles (diagnose, implement, fix) — so that when no human is present, the critical gates fire automatically rather than waiting for a `/skill` invocation. This is the difference between "a human runs the pipeline step by step" and "the bug→PR flow runs itself with the gates wired in."
- **Citation:** Confirmed absence of an *unattended-orchestration* primitive — `[ground-truth §3c]` ("No UNATTENDED branching" in the pass structure) and the autonomous trigger front-door is absent from disk (the central V2 fact, `[ground-truth §0, §8]`). Our deterministic floors exist as *human-invoked* hooks/skills, not as a self-sequencing blueprint.
- **Conservative disposition:** Pass3 §c filed the explicit-invoke-vs-blueprint question under "Weaknesses in the article's OWN reasoning" — *"'skills never auto-load' (library) vs 'blueprints automate the sequence' (Minions) are opposite agency stances the article never reconciles"* — i.e., treated it as the article's unresolved contradiction, **not as a decision we must now make**. The old "defer the trigger front-door" charter meant the unattended-orchestration side was out of scope by definition.
- **RE-JUDGMENT under the new charter:** **ELEVATE — the unmade decision the article dodges is the decision the new charter forces.** Pass3 was right that the article never reconciles explicit-invoke vs pinned-blueprint, but the old charter let us sidestep it by deferring autonomy. Now that bug→PR and self-improving loops are *designed in, never deferred*, we **must** pick blueprint-style pinned orchestration for the unattended path — because "human invokes every skill" cannot run when no human is present. The resolved facts already point here: cloud `/schedule` "runs committed skills" on a schedule (that's a blueprint executor), and `disable-model-invocation` lets us pin side-effect steps safely. So the move is: keep explicit-invoke for the human-present path, and build a blueprint layer (pinned floors + agentic middles + the retry cap) for the unattended path. This is the orchestration spine of the whole autonomy charter.

## Autonomy angle

This source is **richly autonomy-relevant** — it is, underneath, a report on how an industrial team runs 1,300 unattended-agent PRs/week, which is precisely the bug→PR-at-scale the new charter targets. Four of its load-bearing properties map directly onto autonomy primitives: (1) **hard retry caps** are the safety backstop that keeps unattended self-correcting loops from burning budget forever; (2) **devboxes** are the disposable, network-isolated execution substrate an agent must run in when no human is watching — moot-ed from "someday-spike" to "adopt cloud `/schedule`" by the resolved fact that the cloud runner already clones the repo and runs on restricted-network Anthropic infra; (3) **the Toolshed** + our resolved `disable-model-invocation` fact is how side-effect tools stay out of an autonomous agent's reach until a vetted step summons them; (4) **blueprints** are the pinned-orchestration pattern that lets the critical gates fire automatically in an unattended flow. The article says nothing about Slack/Linear summon specifically, but its retry-cap → "back to a human" handoff is exactly the page-a-human terminal state a summon flow needs. On self-improving loops and cloud scheduling, the retry cap and blueprint patterns are the two missing controls that make those loops safe.

## The single biggest move (one paragraph)

**The hard iteration cap with a defined REJECT / human-handoff state, generalized into a harness-wide `bounded-loop` contract that every agentic loop inherits.** Pass3 already ranked it the #1, most model-independent contribution and confirmed the absence (`[ground-truth §3c]`: "No REJECT tier, no UNATTENDED branching") — but it gated implementation behind a research pass and kept it framed as a CI tweak. Under the new charter this is the keystone, because it is the one control that makes *all* the other autonomy features survivable: a bug→PR agent, a cloud-scheduled self-improving loop, and a `/cr` auto-fix run each have the same failure mode at fleet scale — an unbounded loop that burns money and silently degrades the diff while looking productive, multiplied across 5+ repos with no human present. The principle needs no further research to adopt (only the *number* is model-dependent; ship a sane default 2–3 as a tunable constant), and it has a clean, named failure mode that satisfies the golden rule (`[§9]`). It is world-class because it is exactly what lets Stripe run unattended agents at industrial volume without them spiraling — the cheapest, most portable, most enabling control the article teaches, and the precondition every other autonomy move depends on.
