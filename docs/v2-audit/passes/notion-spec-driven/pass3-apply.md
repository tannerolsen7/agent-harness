# Pass 3 — Apply: Notion spec-driven workflow against CANONICAL-HARNESS-AS-IS

Building on pass2: I carry forward its five testable residues — (1) **autonomy is rationed by verifiability**, and the verification surface must be a *built artifact*, not prose; (2) the **spec is a per-feature behavioral contract written for a future cold-start agent**, distinct from both code and project-level context docs; (3) **spec-first deletes the adversarial clarity-generation step** and ships no built-in attacker on its own premises; (4) **CI-as-throughput is real but conditional on actually running a fleet**; (5) **keep the contract tool-agnostic, keep the infra thin and rebuildable.** I also carry pass2's warning that the page's headline facts are best-case anecdotes — import the *mechanism*, never the success rate.

Governing rule honored: **no gap is asserted without a citation to a CANONICAL-HARNESS-AS-IS section or a confirmed absence.**

## (a) What we ALREADY do

- **We already ration autonomy on a built gate (pass2 residue 1) — but ours gates on a *sentinel*, not a *verification surface*.** The `.cr-ok` sentinel chain, the pre-push human-confirm (interactive) / sentinel-validate (agent) split, and NEEDS-HUMAN tiering in `/cr` are real, built autonomy gates [§3c, §3e]. The non-interactive pre-push "validates `.claude/.cr-ok` sentinel (`branch:sha`); aborts if stale or missing" [§3e]. So the *shape* the page prescribes — earn unattended operation through a machine check — is present. (The gap is *what* the check verifies; see (b).)
- **We already keep prompts/specs as version-controlled artifacts (pass2 residue 5 — tool-agnostic contract).** SOUL.md, CONTEXT.md, AGENTS.md, CLAUDE.md, agent-contract.md, AI-WORKFLOW.md, docs/ARCHITECTURE.md, docs/TESTING.md all exist on disk as committed context [§3a]. The page's "spec as version-controlled behavioral contract, reviewed in PRs, diffable, blame history" is the same discipline we apply to harness docs.
- **We already have project-level "what the codebase is" (CLAUDE.md/CONTEXT.md).** The page's own taxonomy explicitly names CLAUDE.md as answering "what the codebase is"; we have both CLAUDE.md and a 15 KB CONTEXT.md [§3a]. The two of the page's three doc-layers (code = "how", CLAUDE.md = "what the project is") are covered.
- **We already run an AFK/unattended mode with scoped safety (pass1 Hot Potato "scoped permissions" analogue).** UNATTENDED worktree mode, the Tier-0 prod-key firewall (`worktree-create.sh` + `gen-local-env.sh` + `test-local.sh`), and the `permission-logger.sh` are real disk advances [§3e, §6] — a genuine credential-isolation layer the canon never specified. The page's "permissions = safety surface for autonomy" is something we implement *more* rigorously than Notion's view-only-DB model.
- **We already supply the adversary the page lacks (pass2 residue 3).** `/cr`'s 9 passes + adversarial/Devil's-Advocate review [§3c] and the 4 review lenses (assumption/composition/cascade/abuse) in the 23-agent roster [§3d] are a built-in attacker on the implementation. Where spec-first has *no* premise-attacker, our pipeline has one — for *code*. (It does not attack a *spec*, because we have no spec layer; see (b).)
- **Specs-as-anti-drift partially exists as `docs/adr/` + `docs/solutions/`.** Locked decisions (ADRs) and reusable positive patterns are committed, read-before-design artifacts [§4, and CLAUDE.md "skim docs/adr/README.md / docs/solutions/README.md"]. These cover *cross-feature* decisions and patterns — not *per-feature behavioral contracts with verification* (see (b)).

## (b) REAL gaps this article exposes (each cited)

- **No per-feature behavioral-contract layer with a Verification section (pass2 residue 2 — confirmed absence).** The map's full governance/context inventory [§3a] lists project-level docs (CLAUDE/CONTEXT/AGENTS/SOUL/ARCHITECTURE/TESTING/STRATEGY) and the memory model [§4] lists `memory.md`/`RECURRING-FINDINGS.md`/`PITFALLS.md`/`docs/solutions/`/`docs/adr/` — **none is a per-feature spec answering "what this feature IS and how to verify it still does that."** There is no `/agent-specs/`-equivalent anywhere in §3a or §4. ADRs capture *decisions*, solutions capture *patterns*, PITFALLS capture *traps* — the feature-lifetime behavioral contract is a confirmed structural absence. This is the article's single most transferable, tool-agnostic idea and it maps to a real hole. **Real gap.**
- **Our autonomy gate verifies a sentinel, not behavior (pass2 residue 1 — cited weakness, not absence).** The page's thesis is that the gate should execute a *verification surface*; ours validates a `branch:sha` token written by `/cr` [§3e] and CI "never verifies `.cr-ok`" — the sentinel is "gitignored, never reaches CI" [§3f, "Node 8.5(c) gap"]. So our built gate certifies *that review ran*, not *that the feature behaves as specified*. The article exposes that `.cr-ok` is a process-completion signal masquerading as a correctness signal — which is **exactly** what §9 already pre-authorized cutting: "The `.cr-ok` sentinel as a capability gate → document as a readiness signal, not a capability unlock" [§9 Replace list]. The article independently arrives at the §9 judgment. **Real gap, and it converges with a pre-authorized §9 cut.**
- **No executable per-feature verification harness for agent self-checking (confirmed absence).** Notion's CLI lets an agent toggle a feature and assert behavior against the spec. Our testing layer is Vitest unit/integration against a real Supabase instance [§3f scripts: `test-local.sh`, `seed.ts`] — real and good, but it is *developer-authored test files*, not a *spec-derived verification surface an agent runs to certify a feature matches its contract.* The §3f/§3e inventories contain no such tool. The gap is narrower than "we lack tests" (we have them) — it is "we lack a verification artifact bound to a feature contract." This gap is **downstream of the spec gap above** and should not be built before it. **Real gap, correctly sequenced.**
- **CI is not on the agent-throughput path, and we are not yet at the fleet scale that makes it existential (pass2 residue 4 — cited, with scope discipline).** Ground truth: CI is `ci.yml` + `integration.yml` running tsc/lint/vitest [§3f]; the harness "has never been installed anywhere but event-vendor" [§8] and there is no webhook/cron/parallel-trigger fleet surface [§2, §3e]. We *do* run parallel worktrees via `/queue` [§3b skills list; §1 couplings], so the throughput argument is **not** irrelevant — but per pass2 it is *conditional on parallelism* and is a **late** investment. The honest finding: CI speed is a real lever the moment `/queue` saturates, but the map gives no evidence CI latency is the current bottleneck, and §8 says the *install* gap dominates. **Real but low-priority gap — flag, do not prioritize; cite §8 over the article's urgency.**
- **Spec-first's missing premise-adversary maps to a gap only for the spec layer we don't have (pass2 residue 3).** Our `/cr` adversary attacks *code* [§3c, §3d], so we are *not* exposed where the article is — for code. But if we adopt the spec layer in (b), we would inherit spec-first's exact blind spot: a Verification section written by the same agent that implements, with no independent attacker on the spec's premises [pass2 "no built-in adversary"]. The map already names the analogous failure: the project audit artifact itself rots and any absence-claim sourced to it "must be re-verified" [§0 Correction log] — i.e., we have *lived* the cost of an unverified authoritative doc. **Conditional gap:** only real *if* we build (b), and it tells us the spec layer must ship with an independent review pass from day one — do not copy Notion's self-verification.

## (c) Weaknesses / blind-spots in the article's OWN reasoning

- **Verification generalized from a verifiable domain (pass2).** The CLI-checkable Notion-AI-output case silently selects for features with a cheap machine oracle; the "verification before autonomy" law is asserted universally but demonstrated only where "done" is inspectable from a shell. For UI aesthetics, external side-effects, or latent regressions, the Verification section collapses back to prose and a human.
- **Clarity-required vs. clarity-generated contradiction (pass2).** The page claims spec-first "replaces the design meeting" *and* that the process "requires clarity as input, doesn't generate it." The design meeting's job was to *generate* clarity through disagreement; spec-first **displaces** that onto one author's pre-existing mental model and ships **no adversary on the spec**. Presented as compression; partly deletion.
- **Self-verification by the implementer (pass2).** Codex writes the spec and builds against it; the oracle's author is the implementer — a basic test-design violation the page never flags.
- **Best-case anecdotes as evidence (pass1/pass2).** The 10:40→10:51 timeline, "several thousand lines one-shotted," and Stripe's "1,300 PRs/week" are single-narrator, selection-biased, and quality-denominator-free. No transcript exists; one of four sources mislabeled the agent [pass1 source-reliability note]. Import the mechanism, never the rate.
- **"DX = Agent DX" overstated (pass2).** The throughput math is *conditional on running a fleet*; below that scale, CI speed is ordinary DX. The page universalizes a parallelism-gated claim.
- **Self-configuring agent vs. "scoped permissions = safety" (pass2).** Hot Potato rewrote its own MCP instructions from a screenshot yet "scoped permissions" is the whole safety story; a self-modifying agent with write access to even one DB is a larger surface than the page admits. Our own §9 keeps the PocketOS destructive-operation rules precisely because permission-scoping alone is not the safety floor.

## (d) Does it warrant fresh external research?

**Mostly no — synthesize, don't re-research.** The transferable core (spec-as-behavioral-contract, verification-as-autonomy-gate, CI-as-throughput) is already legible against our map, and the article's empirical claims are unverifiable anecdotes not worth chasing. Two narrow, *internal* checks — not literature reviews — would pay off, and both are decisions, not discoveries:

1. **Scope a thin `/agent-specs/`-equivalent against §3a/§4 before building.** The open question is purely internal: does a per-feature behavioral-contract-with-verification belong as a new doc class, or can it be absorbed by extending `docs/adr/` (decisions) + a verification section in existing tests? This is a Phase-3/5 design decision citing §3a (no spec layer) and §4 (memory model), not external research. Resolve by synthesis with the other articles in this corpus (Linear/Ramp/Stripe specs work), which the v2-audit already collects.
2. **Confirm whether `.cr-ok` should be re-typed per §9 *because* of this article's verification-gate argument.** Already a pre-authorized §9 cut ("readiness signal, not capability unlock"); the article supplies the *reason* (a gate should certify behavior, not process). This is a one-line decision to fold into the §9 re-audit, not new research.

Everything else (CI-throughput, AFK cadence, scoped-permission safety) is adequately covered by this map plus the disk advances already built [§6]. The article's value to us is **one durable, tool-agnostic idea** — the per-feature behavioral contract with an executable Verification section (b) — plus **independent confirmation of a §9 cut** (the `.cr-ok` re-typing). Both are mapping-and-decision work, not discovery.
