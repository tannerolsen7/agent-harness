Building a new feature (the part we spent the most care on)

The riskiest moment in building a feature is the very first one, before any code: the robot quietly decides what gets stored and what the screen looks like — and if it guesses wrong, you don't find out until everything's built on top. So we put a hard stop there.

1 · You ask for a feature.
2 · Before it writes ANY code, the robot prepares two things for you to approve:
  • The data shape — exactly what gets stored, shown as the real tables and columns (not a vague description).
  • A rough mockup of the screen — using your existing colors and building blocks, so it doesn't invent a new look.
A second robot pokes holes in both first ("what did you miss? what are you assuming?"), so what reaches you is already sharpened. It also lists any open questions — and it is not allowed to answer those itself.
3 · You approve or fix the data shape and the look. Coding literally can't start until you do.
4 · The robot builds in small pieces, tests as it goes, then takes a picture of the finished screen so you can confirm it matches the mockup. Opens a pull request.
5 · You merge.

Why this shape: the data shape and the look are the two things that are both expensive to change later and impossible to judge from reading code. So we spend a few cheap robot passes to lock them down up front. (Tiny tweaks skip the mockup — no screen, nothing to lock.)

What we're building (the now-pile)

Grouped by what each part is for. Everything here is started by you.

Keep it safe

  • The strongest locks — no deleting real data, no surprise deploys, no touching its own safety files. Built in so the robot can't switch them off. (One-time setup you paste in per project.)
  • The locks are the only net — for every project. You decided to assume no project has a throwaway practice copy, so the locks (which the robot can't switch off) carry all the safety. A practice copy is a bonus a human can add to a project that supports it (like event-vendor), never something the safety plan counts on. Because there's no sandbox to catch a slip, the "block dangerous commands" lock has to be exhaustive — and built first.
  • A retry limit + "ask a human" — if it keeps failing, it stops and pages you instead of thrashing.

Make the output trustworthy

  • The un-fakeable review check — a real check-mark that blocks the merge unless the tests passed on the exact final code, plus a plain-English note saying what was checked. (Broken today — the "passed" mark never reaches the server.) The keystone.
  • The 4-angle reviewer + one honest "how good is it" number — independent review that hunts for bugs, plus a measured catch-rate so you know how much to trust it.

Get smarter over time

  • The learning loop — lessons from past mistakes load into the next job; a 3rd repeat of the same mistake becomes a hard block.
  • The progress dashboard — a page you open (no auto-emails, since there's no clock) that answers, per project, "is the robot getting smarter?" at the top — then how often it needed do-overs, how often it stopped itself, and whether changes are staying small.

Get the 5 projects healthy pulled forward

  • One shared rulebook — share the parts that agree now; hold back the parts that contradict until you've settled them.
  • Lock the 15 borrowed tools to versions you've checked, so they can't change under you without warning.
  • A broken-link check that catches when the rulebook points at a file that doesn't exist (a real bug today).

A small free win pulled forward

  • Name-tag the buttons and fields — an automatic rule that helps screen-reader users today and lets the robot reliably click the right thing later. Nearly free.
