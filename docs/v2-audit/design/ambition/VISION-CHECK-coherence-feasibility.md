## VERDICT: SEQUENCING-OR-CAPABILITY-GAPS

The vision is coherent at the pillar level — the five-way cut (find/start/finish · keep-safe · check-well · get-smarter · travel) composes, the overlap-resolution note (§"Why these five") is honest and the keystone is owned once (FLOOR-6) and referenced elsewhere without duplication. ## TIER 1 — MUST FIX (a move assumes a capability that doesn't exist, or a load-bearing mechanism is dropped)

### T1-1. C10 asserts a hook capability `capability-facts.md` explicitly denies — "requires a before/after screenshot."
**Draft:** C10 (line 85) — the Stop/PostToolUse hook "runs `npm run test` + `npx tsc --noEmit`, **blocks on red, requires a before/after screenshot for any UI diff**." The source it elevates from (`lens-craft.md:100`) says the same: "for any UI-touching diff **requires** a Chrome-MCP before/after screenshot."
**Ground truth:** `capability-facts.md:18-20` — "**No hook can REQUIRE an artifact (screenshot) to exist before completion.** → MOVE 1's render-gate payload is weaker than the verification payload: a Stop hook can *check an artifact exists* only if the agent was already instructed to produce one; it cannot *compel* production. **Scope render-gating as 'verify-if-present + advisory,' not a hard gate.**"
**Why it matters:** This is the exact failure mode the brief named ("a hook compelling a screenshot"). C10 is tagged P0/P1 and "gates the autonomous PR." A gate that the platform cannot actually enforce is a forgeable gate masquerading as deterministic — the precise anti-pattern Pillar 2 exists to kill. C8 (line 81) gets the analogous problem *right* (it routes the unattended verify leg to a CI job against a preview deploy, since "chrome-devtools-mcp is headed-only"); C10 does not inherit that discipline.
**Note the citation gap:** C10's *Citation* line reads "confirmed absence — §3e, §5" and never cites `capability-facts.md` at all — so the contradiction was never reconciled against the capability constraint that governs it.
**Fix:** Re-scope C10's screenshot clause to "verify-if-present + advisory" (a Stop hook checks the artifact exists *only if the agent was instructed to produce it*), and move the *hard* render gate to the CI leg exactly as C8 does (CI can require a screenshot-diff job to pass; a Stop hook cannot compel the artifact). The test+typecheck "block on red" half is fine (per `capability-facts.md:11-13`, Stop hooks can run the suite and block) — subject to T1-2.

### T1-2. L2 (`/goal`) and C10 silently depend on force-continue Stop-hook semantics that `capability-facts.md` flags as empirically unverified.
**Draft:** L2 (line 37) installs `/goal` as a continuation primitive that "self-continue[s] until a separate grader confirms a verifiable end-state." C10 (line 85) and the thesis (line 9, "a continuation engine that runs until a separate grader says done") both lean on a hook that *blocks on red and feeds the reason back so the model keeps working*.
**Ground truth:** `capability-facts.md:13-16` — "⚠️ The guide was *internally hedged* on whether 'block' forces the model to keep working vs. just erroring… **Verify empirically before relying on force-continue semantics.**"
**Why it matters:** The continuation engine is Pillar-1 spine. If `decision:block` only errors rather than forcing continuation, `/goal`'s "run until graded" loop and C10's "block-on-red-then-re-run" both need a different driver (e.g. an external orchestrator re-invoking, not a self-continuing hook). The draft nowhere surfaces this as a precondition or a probe-this-first item.
**Fix:** Add an explicit Phase-0 empirical probe ("verify `decision:block` force-continue semantics on the target CLI version before building L2/C10") as a named precondition, and state the fallback driver if the probe fails (external re-invocation via the L1 front door / cloud `/schedule`). This is a one-line de-risk, not a redesign — but leaving it implicit means the spine's core loop rests on an unverified assumption.

### T1-3. The incident→hotfix/migrate/post-mortem subsystem and its cross-skill doc-travel protocol — the #1 carry-forward alert — has no move.
**Draft:** No move (L*, F*, C*, CMP*, P*) covers the incident/hotfix/migrate/post-mortem subsystem. `incident`, `hotfix`, `migrate`, `post-mortem` appear only incidentally inside *failure-prevention prose* (e.g. F1 line 47 names `@hotfix-guard` only as a `block-dangerous-bash` example; C13 line 91 lists `@hotfix-guard`/`@investigator` only for a model re-audit). P10 (line 127) is a generic catch-all: "the roster ships inside the plugin… cross-skill hand-off contracts (TASK-TEMPLATE)… embedded mechanisms living in sibling files."
**Ground truth (the dropped mechanism):** `skills-B.md` CARRY-FORWARD ALERT #1 (its top alert): "**The cross-skill document-travel protocol (incident → hotfix/migrate/feature).** `incident/SKILL.md:269-287`: the `.claude/incident-[slug].md` triage doc literally travels to the receiving skill and 'replaces the normal orient step.' This is a wired state-machine handoff, not prose. **Lose it and incident/hotfix/migrate become disconnected skills instead of one routed subsystem.**" Reinforced by `agents-A.md` alert #6 (the incident-responder routing brain + security short-circuit) and `skills-B.md` alert #2 (the exact `[~]` TASKS.md entry shapes `@hotfix-guard` gates on).
**Why it matters:** This is the brief's named example ("the cross-skill triage-doc-travel protocol"). It is *the* canonical bug→reviewed-PR production-incident path — exactly the loop the charter centers on (Slack/Linear "prod is down" → `/incident` → route → `/hotfix` → guard → PR). L1's trigger trifecta routes into "worktree → `/feature` → `/cr` → `pr.sh`" (line 35) — i.e. the *feature* path — and never names the incident path or its doc-travel handoff. P10's TASK-TEMPLATE catch-all names the *feature/debug* handoff contract but not the incident triage-doc-travel-as-orient-replacement, which is a distinct, more specific state machine.
**Fix:** Add an explicit move (Pillar 1 or a Craft/carry-forward slot) preserving the incident-subsystem state machine: the triage-doc-travels-and-replaces-orient protocol, the 8-type routing brain, the security-signal short-circuit (isolation-only, never auto-fix), and the exact `[~]` TASKS.md entry shapes the guard reads. At minimum, L1 must name *which* downstream path each trigger type routes into (a CI-red or `fix-me` label often *is* an incident, not a feature) and that the incident path is wired, not flattened to `/feature`.

## TIER 2 — SHOULD FIX (real precision/sequencing gaps that weaken a move but don't break it)

### T2-1. P2 risks materializing autoMode into committed project settings — the exact ignored-at-runtime gap the corpus diagnosed.
**Draft:** P2 (line 111) — `/init` "materializes per-repo files from a committed canonical template — `CLAUDE.md` skeleton… the `permissions.allow`/`deny` baseline… and **the auto-mode policy placed where the classifier reads it**."
**Ground truth:** `capability-facts.md:42-46` — "**autoMode is NOT read from committed project `.claude/settings.json` by design**… On disk the autoMode block IS in `.claude/settings.json:6-32` (added #99) — so it is being *ignored at runtime*… **the correct home is local (personal) or managed (enforced), never committed project.**"
**Why it matters:** The draft *is* mostly aware — F5 (line 218) wrestles with managed-settings, line 201 keeps the self-edit boundary, killlist E#8 (which P2 cites) diagnoses the placement bug. But P2's actual mechanism phrasing ("placed where the classifier reads it" via "a committed canonical template") is ambiguous-to-wrong: if `/init` writes autoMode into committed project settings, it reproduces the precise inert-config gap. "Where the classifier reads it" = local or managed, neither of which a *committed* template can be.
**Fix:** P2 must state that the autoMode policy is materialized into `settings.local.json` (personal) or `managed-settings.json` (enforced, human-applied) — never committed project settings — and that the committed template carries the *content* for a human/`/init` to place locally, consistent with F5 and the no-self-edit boundary. Reconcile P2's phrasing with F5 so they don't read as contradictory.

### T2-2. L1 fires "after FLOOR-1/2/5/6/7/9 are wired" but omits FLOOR-3 (egress) and FLOOR-8 (circuit breaker) from its named companions — and FLOOR-3 is the only defense for L1's own injection class.

F3 is tagged "P0/P1 — after one bounded check," so it may legitimately trail by a hair — but then L1's first-shipping trigger must be the lowest-injection-surface one (the GitHub label, per Fork F3 line 214) until F3 lands, and the draft should say so.

### T2-3. F4 is "a guard clause inside F1," but F1 is the absent-3rd-guard *build* and F4 is the migration-credential *architecture* — a real ordering knot the draft underplays.
**Draft:** F4 (line 53) "encode in an ADR + enforce with a guard clause inside F1." F1 (line 47) lists "destructive `supabase db push`" in its block scope and says "full scope including the FLOOR-4 `supabase db push`-from-worktree block."
**Why it matters:** F4 is not just a clause — it is a credential-architecture decision (agent verifies on a throwaway local stack via `test:local`; human applies to prod) that must be *resolved* before F1's guard can know what "non-local target" means. The draft tags both P0 and co-locates them, which is right, but the F4 mechanism (the verify/apply split + the ADR) is the *precondition* for the F1 clause, not a child of it. Stated as "a clause inside F1," it risks being built as an afterthought to the guard rather than the architecture the guard enforces.
**Fix:** State explicitly that F4's verify/apply split + ADR is resolved *first*, and F1's `supabase db push` clause is the *enforcement* of that decision — so the build order is F4-decision → F1-clause, not F1-with-an-F4-clause-bolted-on.

### T2-4. The 4-lens isolation/context-passing contract is named only loosely; the load-bearing "stay-in-lane" + "reviewer pre-reads and passes context" invariants are not explicit.
**Draft:** C2 (line 69) elevates "isolated solution context but full project-canon" and the 3-4 round loop. C13 (line 91) and the thesis name "4 lenses." 
**Ground truth:** `agents-A.md` alert #2 and `agents-B.md` (reviewer line 59, lens-assumption line 142): the 4-lens architecture has *three* wired contracts — (a) `@reviewer` pre-reads CONTEXT/AGENTS/PITFALLS and **passes them into each lens** (lenses don't re-read); (b) each lens attacks exactly one failure class; (c) the **stay-in-lane rule** that keeps lenses non-overlapping. "A summary like 'reviewer runs adversarial review' loses all three."
**Why it matters:** C2 correctly elevates the *independence* thesis but the draft's lens treatment is at the "reviewer runs lenses" altitude the grounding warns against. This is forgivable in a vision-level doc (it's not a spec), but C2 is the "largest evidenced pre-human quality jump" and the rebuild will inherit whatever altitude the vision sets.
**Fix:** In C2, name the three invariants explicitly as do-not-drop (pre-read-and-pass-context; one-class-per-lens; stay-in-lane) so the design rebuild preserves them rather than re-deriving a single shared-context reviewer.

### T2-5. F6/C1 "same plumbing, owned jointly" — verify the keystone isn't double-counted or split-brained across two owners.

Four moves (F6, C1, C7, A6) all touch the same CI-gate plumbing; if the rebuild treats each as a separate deliverable, the single enforcement boundary fragments.
**Fix:** State that F6 owns the *enforcement boundary* (CI fails unless sentinel-SHA == head-SHA AND checks green + branch protection) as one deliverable, and C1/C7/A6 are *consumers/surfaces* of that one gate, not parallel implementations.
