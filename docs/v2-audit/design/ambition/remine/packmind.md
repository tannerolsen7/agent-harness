# Ambition Re-mine — Packmind ("Context Engineering / Engineering Playbook" governance for AI agents)

## What this source is (plain English, 2-3 sentences)
Packmind is a commercial platform that captures an engineering team's standards, architectural decisions, validated patterns, and conventions into a single "engineering playbook" and automatically distributes it (in each tool's native format) to every AI coding agent the team uses (Cursor, Claude, Copilot, Kiro). Its blog/docs are marketing-with-a-thesis, but the thesis is sharp: the model and IDE are a commodity everyone shares, while the *context layer* is the only non-commoditizable, compounding asset you own. The article's most portable contributions are three named failure modes — **context drift**, the **bootstrapping illusion**, and the **process-vs-knowledge skill** distinction — plus the framing that maintaining context is *investment, not overhead*.

## The full-ambition moves this source teaches

### Move: A real drift detector that catches BOTH drift directions (doc-stale AND doc-fiction)
- **Plain-English what & why:** "Context drift" is when your codebase and standards evolve but your AI context files (CLAUDE.md, AGENTS.md, skill descriptions) don't — so the agent keeps generating code to rules that no longer exist. The team moves forward; the AI stays behind. It's invisible until it surfaces as repeated review comments and rework. Packmind only names *one* direction (the doc fell behind the code). Pass2(B) recovered the second, more dangerous one: **doc-fiction drift** — the context file asserts a rule the code *never actually followed*. The agent then confidently builds to a fictional codebase. A world-class detector catches both: it diffs doc-vs-code (staleness) *and* rule-vs-observed-behavior (ghost rules).
- **The mechanism:** Build `/scan-context` for real (it is canon-documented but absent on disk). It runs in two modes against our own repo: (1) **staleness** — every CLAUDE.md/AGENTS.md/canon claim about a file, path, command, or skill is checked to still exist (catches `/cr-feature` retired-v0.85-but-still-referenced); (2) **fiction** — every named artifact reference is checked to actually exist on disk (catches phantom refs `learned-patterns.md`, `review-log.md`, `triage-inbox.md`, `skills-lock.json`, `agentic-system-enabled`). Output: a list of drifted lines, each tagged staleness-vs-fiction, with a proposed delete or fix. Wire it into `/compound` and as a scheduled cloud `/schedule` job (laptop-closed durability is now moot).
- **Citation:** Confirmed absence — canon §5 / §166: "`/scan-context` (full template) … Documented skills with no disk dir." Doc-fiction is our LIVE failure class — canon §6/§295 phantom refs ("Referenced on disk, never built"); canon §169 `/cr-feature` RETIRED v0.85 yet still referenced in canon's Page-11/Page-14.
- **Conservative disposition:** §C deferred / scaled-down. Pass3 correctly upgraded the curator's "frame `/scan-context` better" extrapolation into "the mechanism is missing," and called for a "focused internal spike" — but it explicitly de-scoped it: "Does it warrant FRESH external research? — Disciplined answer: mostly NO … a doc edit, not a research task," and "Prefer synthesize over re-research." It framed `/scan-context` as a single design spike reading our own repo, gated behind "do not research it now."
- **RE-JUDGMENT under the new charter: ELEVATE.** The pass3 disposition was honest about the gap but small about the build. Under the new charter this is **in-scope-now, first-class, and bidirectional**. The conservative framing treated drift detection as a synthesize-not-build doc edit with a deferred spike; the reality (our own §6 proves it) is that we are shipping a harness whose canon references five artifacts that do not exist and a reviewer name retired a version ago. That is not a "frame it better" problem — it is a self-correcting-context mechanism that should run on every `/compound`, every `/cr`, and on a cloud schedule. The conservative bias was treating "we have the principle in prose" as near-equivalent to "we have the mechanism." We do not: canon §4 says the freshness rules are "encoded in no tooling." World-class scale (parallel fleets across 5+ repos) makes this *worse*, not optional — N repos each drifting independently is exactly Packmind's "compounds silently every day," and there is no human who can watch N canons by hand.

### Move: Close the observed-failure → rule loop with an automated capture trigger (and make it self-improving)
- **Plain-English what & why:** Packmind's core growth discipline (the cure for the bootstrapping illusion) is: start with four things only, then **add a rule only when something fails repeatedly**. That loop has two halves — *observe a failure* and *write the rule*. Our harness endorses the rule-writing half in prose ("when a mistake is corrected, add a rule to memory.md") but the *capture* half is fully manual: every memory entry is hand-typed by the human. So the discipline that makes the whole playbook work can't actually run unattended.
- **The mechanism:** Build the canon-specified `session-end.sh` Stop hook: at session end it proposes memory/PITFALLS candidates from corrections observed during the session (review comments that recurred, a fix the user explicitly asked for, a rule the agent violated then corrected). Human confirms; the rule lands with a `last_seen` date. The autonomy upgrade Packmind cannot see (pass2 F): the *same* drift detector from Move 1 feeds this — when `/scan-context` finds a recurring fiction, it proposes the rule that would prevent re-introducing it. This is the agent maintaining its own context, the loop the article has no model for.
- **Citation:** Confirmed absence — canon §209: "`session-end.sh` (Stop → memory candidates) … Canon's memory-capture hook — absent; disk's memory is fully manual." Listed as a build item in canon §5/§279.
- **Conservative disposition:** §C deferred. Pass3 listed it as gap (b)2 — "the observed-failure→rule loop has no trigger" — but bundled it into the general "synthesize, don't re-research" disposition and did not elevate it to an in-scope build; MASTER-FINDINGS collapsed it into the cautious wiring-tweak set.
- **RE-JUDGMENT under the new charter: ELEVATE.** This is the single most direct lever for *self-improving loops*, which the charter names as first-class autonomy. The conservative read treated it as a deferred hook. Under "autonomy is designed in, never deferred," the capture trigger is the engine of the entire bootstrapping discipline — without it, a parallel fleet generates failures faster than a human can hand-transcribe lessons, and the playbook ossifies. Bigger than pass3 scoped it: pair the Stop-hook capture with the cloud `/schedule` so an unattended overnight fleet still proposes (gated, human-confirmed) memory candidates. The old reasoning ("fully manual is fine, endorse the principle in prose") is exactly the conservative bias the charter retires.

### Move: A decay/expiry rule that runs — break the monotonic add-only ratchet
- **Plain-English what & why:** Pass2(C) found a real contradiction the article never resolves: "add a rule on every observed failure" only ever *adds*. Run it for two years and you rebuild the exact bloated context file the bootstrapping illusion warned against — now with every line individually defensible by a past incident. The missing primitive is **decay**: a rule earns its place by a failure *and must re-earn it* — if the failure stops recurring for N days, the rule is demoted or deleted. Our canon already has this judgment in prose ("ghost rules if unobserved 90 days; collapse + quarterly audit") but, exactly like the article, no mechanism runs it.
- **The mechanism:** Add a decay pass to `/scan-context` (Move 1): every rule/memory entry carries a `last_seen` date; the pass surfaces entries unobserved >90 days as demotion candidates and flags the triple-duplication (the same corrected-mistake fact living in `.claude/memory.md` + `PITFALLS.md` + auto-memory `feedback_*` simultaneously). The moat is accuracy/currency, not volume (pass2 G) — so the tool that adds rules must also be the tool that retires them.
- **Citation:** Canon §4 / §243: 90-day `last_seen` decay rule exists but is "encoded in no tooling"; §260 "freshness rules exist for only 3 stores"; §334 "ghost rules if unobserved 90 days; collapse + quarterly audit." Triple-duplication: canon §4 (same facts in memory.md + PITFALLS + `feedback_*`).
- **Conservative disposition:** §C / §D. Pass3 gap (b)3 said it "is real for us and only half-solved" and explicitly noted "the article doesn't expose a new gap here; it *confirms* a gap our own map already flags." It used this to "strengthen the case to build the decay side of `/scan-context`" — but still left it inside the deferred, synthesize-not-build disposition.
- **RE-JUDGMENT under the new charter: ELEVATE (as a required half of Move 1, not a separate optional).** The conservative framing was right that this is our own map's gap, but wrong to leave it as prose-only doctrine. At fleet scale, an add-only context layer across 5+ repos becomes unreadable for both agent and human — the bloat *is* a per-token tax on every session. The failure mode the decay rule prevents is concrete: capable rules drowning low-frequency dead rules, which dilutes the high-priority ones (the bootstrapping illusion's actual harm). Build the decay pass into the same detector. Old reasoning's conservatism: treating "we wrote the judgment down" as sufficient when canon §4 itself says it runs in no tooling.

### Move: The process-vs-knowledge skill taxonomy — WITH a "does the model already infer this?" gate
- **Plain-English what & why:** Packmind splits skills into *process* (how to run command Y) and *knowledge* (how to think about X in this codebase) and treats knowledge skills as the higher form, recommending you encode "20 years of expertise" / head-knowledge into them. Pass2(D) caught the undefended assumption: a knowledge-skill is the artifact *most* prone to doc-fiction drift, and it's the one most likely to narrate things a capable model already infers from the code. The world-class version keeps the distinction but adds the gate the article lacks: write a knowledge-skill only when the model demonstrably *cannot* infer the judgment from the code, and tie it to a failure you observed.
- **The mechanism:** When authoring any skill, classify it process-vs-knowledge; for knowledge-skills, require a one-line justification of the failure it prevents AND a check that the judgment isn't already inferable (our canon §9 golden rule: "if you can't name a failure mode the constraint prevents, it's overhead"). This is a small authoring-discipline addition, not a new subsystem — it's the bootstrapping illusion applied to skills specifically.
- **Citation:** Canon §9 (Page 13 Model Capacity Audit golden rule); skills surface — canon §3b "26 project skill dirs." The taxonomy itself: pass1 concept 5 / Application-claim 3.
- **Conservative disposition:** §F-adjacent / partially rejected. Pass3 (c) treated Application-claim 3 critically: "Adopting Application-claim 3 ('encode 2-3 pieces of Tanner's head-knowledge') without a 'does the model already infer this?' gate would manufacture exactly the ghost rules our §6/§9 warn against." It correctly rejected the *naive* version.
- **RE-JUDGMENT under the new charter: UPHELD-CUT on the naive form; NEW (small) on the gated form.** Pass3 was right to reject "go encode 2-3 pieces of head-knowledge" — the named failure mode is real: a knowledge-skill describing judgment the model already has is a ghost rule that drifts and dilutes (canon §6/§9). That cut stands even at fleet scale. BUT the *gate* is a genuine first-class addition the conservative synthesis didn't carry forward as a build item: a process-vs-knowledge classification + capacity-gate at skill-authoring time. It's cheap and it prevents the exact bloat the charter cares about. So: keep the rejection of the naive version (UPHELD-CUT with named failure mode), and recover the gated authoring discipline as a NEW small candidate.

## Autonomy angle
The article itself teaches **nothing** about bug→PR, Slack/Linear summon, or cloud scheduling — pass2(F) names this as its central blind spot: "the agent is the consumer and the human is the author … no model for the agent *maintaining its own context* — the loop where the agent that detects drift also proposes the fix." But that blind spot is precisely the autonomy opening. Two of the moves above become self-improving loops once you invert the article's assumption: (1) the drift detector (Move 1) that runs on cloud `/schedule` and *proposes its own fixes* is the agent maintaining its own context; (2) the session-end capture trigger (Move 2) fed by that detector closes the observed-failure→rule loop without a human in the inner loop. The article makes the autonomy requirement *visible by omission* — for an unattended harness, "who maintains the context when the human is asleep" is the question, and Packmind doesn't even ask it. That is the move to steal: not Packmind's mechanism, but the loop Packmind couldn't see.

## The single biggest move (one paragraph)
Build `/scan-context` for real as a **bidirectional, self-improving context-maintenance loop**: it detects both doc-stale drift (code moved, doc didn't) and doc-fiction drift (the doc asserts a rule the code never followed), runs a 90-day decay pass that demotes rules whose failures stopped recurring, and — the autonomy upgrade the article cannot see — proposes its own fixes and memory candidates, gated by human confirmation, on a cloud `/schedule`. This is world-class because it unifies the three things our own ground-truth map proves we're missing in tooling (canon §5 detector absent, §209 capture hook absent, §4 decay rule prose-only) into one mechanism that does what Packmind only *names*: it makes the context layer self-correcting. The conservative synthesis treated this as a doc edit plus a deferred spike ("synthesize, don't re-research"); under the new charter it is the keystone autonomy primitive — the harness that maintains its own playbook across a parallel fleet while the laptop is closed is exactly the "build the autonomous car, not the cage" thesis, applied to the one asset Packmind correctly identifies as the only thing that's actually yours.
