# Ambition Re-mine — Bug-to-PR Automation (Automated Bug Triage, 2026)

## What this source is (plain English, 2-3 sentences)

A broad, well-sourced industry survey (15+ named deployments: Stripe Minions, Coinbase Forge, Ramp Inspect, LangChain Open SWE, Linear Agent, Sentry Seer, GitHub Copilot Cloud Agent + Agentic Workflows, Cursor Automations/BugBot, Ona, Devin, Greptile) documenting how 2026 teams turn a bug signal into a reviewed pull request automatically. Its real finding — recovered in pass2 — is not "buy these tools" but an **architectural convergence**: every serious deployment is a *deterministic state machine with one stochastic transition (the LLM), gated front (trigger + context prefetch + tool curation) and back (review contract + risk classification)*. This is the most directly autonomy-relevant source in the corpus: it is literally about the bug → reviewed-PR pipeline the new charter names as the north star.

## The full-ambition moves this source teaches

### Move: The autonomous trigger front-door (bug signal → agent summoned)

- **Plain-English what & why:** A bug appears somewhere — an error monitor fires, a CI run goes red, an issue gets a `fix-me` label, someone types `/minion fix` in Slack — and *that event itself* starts an agent. No human opens a terminal, picks a worktree, and types `/feature`. The failure it prevents is the one the whole new charter is built to kill: the agent can build, but a human is still the only thing that can *start* it, so the engineer remains the scheduler. Pass1 §3 ranks five trigger surfaces by signal quality (error-monitor threshold > issue-tracker webhook > CI failure > label > Slack command); pass2-A elevates this to the load-bearing insight: "the agent is the cheap, interchangeable middle... the two ends — trigger quality and review contract — are where all the engineering value lives." A low-signal trigger guarantees a review queue full of noise no contract can rescue; the *front* door is as load-bearing as the back.
- **The mechanism:** Build the front door our harness has never had. Concretely: (1) a GitHub Issues label trigger (`fix-me` / `agent`, OpenHands-style, pass1 §3.4) wired through a GitHub Action that provisions a worktree, runs the existing `/feature` → `/cr` → `pr.sh` shell, and opens a draft PR; (2) a Slack/Linear summon (`/fix <issue>`, Ramp-Inspect-style, pass1 §2) so a bug can be dispatched from where bugs are reported; (3) a CI-failure → self-heal trigger (GitHub Agentic Workflows' "transient vs permanent" triage, pass1 §2). Each reuses our isolated-worktree shell unchanged — only the *entry* is new. Pair with cloud `/schedule` (resolved fact: runs on Anthropic infra, clones repo, runs committed skills, calls connectors) so the front door fires even with the laptop closed.
- **Citation:** Confirmed absence — ground-truth §3e: the only triggers on disk are `SessionStart` / `WorktreeCreate` / `post-checkout` hooks, which "fire on *human* actions, never on a *bug signal*." Pass3 §b(1): "**No trigger front-door exists at all**... nothing in §3e–§3f ingests a Sentry event, a GitHub issue label, or a CI failure... **This is the single largest gap the article exposes**." Also §5 (canon-only registry has no trigger-ingestion mechanism either).
- **Conservative disposition:** §C DEFERRED, hypothesis-gated, and explicitly fenced off. Pass3 §d gates it hard: "do **not** spike until V2 has decided a trigger front-door is in scope — building the classifier before deciding we want autonomous triggers is the speculative build the harness rules forbid." Pass3 §b(1) names it the single largest gap *and then defers it* on the "hypothesis-before-speculative-build" memory rule. The conservative bias is naked here: it found the biggest move in the article and put it behind a decision gate that was never opened.
- **RE-JUDGMENT under the new charter: ELEVATE — maximally. This is in-scope-now and it is the headline deliverable.** The new charter makes autonomy first-class ("bug → reviewed PR... designed in, never deferred. This REVERSES the old 'defer the trigger front-door'"). The old deferral rested on two pillars both now demolished: (a) "machine asleep / durability" — MOOT, cloud `/schedule` exists; (b) "hypothesis-before-speculative-build / wait until V2 decides" — the charter *is* that decision, made affirmatively. This is not "a bit bigger" — it inverts from deferred-indefinitely to the **primary workstream**. World-class scope: not one trigger but the trifecta (label, Slack/Linear summon, CI self-heal), all routing into the existing worktree+`/cr`+`pr.sh` shell, with a `disable-model-invocation:true` open-PR skill as the safe side-effect actuator (resolved fact: this removes the skill from model context, making the deploy/PR/Slack action safe). The reasoning that suppressed it was pure solo-conservatism: "no Sentry, no triage queue, the trigger question collapses" (pass2-F) — false at fleet scale, where the front door is exactly what lets one engineer run parallel agent fleets across 5+ repos without being the per-repo dispatcher.

### Move: The structural (not confidence-based) review contract — fixed PR template + risk classifier

- **Plain-English what & why:** When an agent opens a PR, a human (or a second agent) has to decide whether to trust it. Trusting a *human* PR and trusting an *agent* PR are different questions: did it find the real root cause or patch a symptom; is the diff proportional to the claim; were tests *modified* in a way that could mask the failure; does the stated blast radius match reality (pass1 §7). The world-class answer is a **fixed PR template** — Problem / Root Cause / Solution / Test Coverage / Blast Radius / Evidence / Confidence (pass1 §6) — backed by **deterministic structural gates**, not a self-reported confidence number. Pass2-D is the sharp insight: the article tells you to gate on a confidence score *and* tells you (in its own "hallucinated root cause" failure mode) that agent confidence is uncorrelated with correctness — an unreconciled contradiction. The mature deployments gate on *structural proxies* that don't ask the model to grade its own homework: test-count-never-decreases, blast radius (callers/files touched), keyword denylist (`payment`, `db/migrate`, `auth`), P-level. The failure this prevents: the "test deletion" failure mode (pass1 §11, "most insidious") and the silently-merged wrong fix (pass2-I, "escaped-defect cost × volume").
- **The mechanism:** Two deterministic pre-push/CI checks our shell lacks. (1) A **test-count floor**: parse the test count before and after the diff; block if it decreased or if `skip`/`only` annotations were added — exactly pass1 §11's "test count never decreases." (2) A **blast-radius / keyword risk classifier**: a script that flags diffs touching `payment`, `auth`, `db/migrate`, RLS, or > N files and routes them to mandatory-human, never auto-approve. Bolt both onto the existing pre-push hook and `ci.yml`. Add the structured PR template to `pr.sh` so every agent PR ships Problem/Root-Cause/Blast-Radius/Evidence by construction. This makes `/cr` (a strong *advisory* reviewer) sit on top of a *structural* floor.
- **Citation:** Pass3 §b(2): ground-truth §3e states "**Both agree the system is overwhelmingly advisory** — neither has a deterministic backstop." Confirmed absence of any test-count-floor or risk-classifier script in §3f's script list (`pr.sh, worktree-add.sh, gc.sh, gen-local-env.sh, test-local.sh, seed.ts`). Pass2-D (confidence is the wrong gate); pass1 §6 (PR template); pass1 §11 (test-deletion defense).
- **Conservative disposition:** §C DEFERRED / narrow-yes-spike. Pass3 §d allowed "a lightweight deterministic implementation" spike for the test-count floor + blast-radius classifier *only if* the trigger front-door is built first — chained to the same deferred decision. So a genuinely cheap, standalone safety win was held hostage to the autonomy decision it doesn't actually depend on.
- **RE-JUDGMENT under the new charter: ELEVATE — and decouple it from the trigger gate.** The conservative synthesis correctly identified the structural gate as superior to confidence (pass3 §c(2) keeps this), but wrongly chained it to the trigger decision. A test-count floor and a keyword/blast-radius classifier are valuable *the moment agents open PRs at all* — which they already do. Under "clarity beats minimalism" and the §9 golden rule, each names a concrete failure mode it prevents (test-deletion; payment/auth/migration touched without human eyes; escaped-defect × volume) — so each earns its place as a first-class deterministic hook *now*, independent of whether the front door ships this week. World-class scope: this is the CodeRabbit/Ramp-grade "structural review contract" the article says is "still being standardized" — building it makes our back-gate world-class rather than advisory-only.

### Move: Ona's cost-ordered auto-approval (static → semantic → agentic) with public-channel observability — the `.cr-ok` replacement

- **Plain-English what & why:** Ona classifies every PR's risk in three escalating stages, cheapest first: a static file-pattern match (no LLM at all), then a semantic check, and only if those are inconclusive does it spend an expensive agentic blast-radius exploration (Claude Code) (pass1 §2, §7). Low-risk PRs get auto-*approved* (the review gate passes without a human), which dropped Ona's time-to-first-approval from 2h49m to under 5 min and cut lead time 74%. Two details carry the safety: **10% of low-risk PRs still get a human "to prevent drift"** (deliberate noise injection so the classifier can't silently degrade), and **every auto-approval posts to a public Slack channel** (observability is the backstop for automation). Pass2-E: this is "the one genuinely transferable engineering pattern," and it generalizes past bug-fixing — it is how you'd gate *any* agent-authored change, "including, pointedly, an agent editing the harness's own config." Pass2-H clarifies the safety model: auto-*approve* ≠ auto-*merge*; "never auto-merge" really means "never let the agent be the last deterministic gate before main" — auto-approval is safe iff a deterministic CI gate sits downstream.
- **The mechanism:** Replace the binary `.cr-ok` sentinel with a **risk-tiered, observable readiness signal**. Tier the gate: static keyword/file-pattern check first (free), then `/cr`-grade semantic, then agentic blast-radius only when inconclusive. Low-risk → auto-approve into the existing pre-push+CI floor (which stays as the deterministic last gate — satisfying pass2-H). Every auto-approval (and the 10% human-sampled drift check) writes to an **agent-PR observability log** (the move below). This is the static→semantic→agentic cost-ordering applied to *our* gate, and it is the directly-reusable design pass3 itself flagged.
- **Citation:** Pass3 §b(3): ground-truth §9 Model Capacity Audit explicitly lists "**The `.cr-ok` sentinel as a capability gate → document as a readiness signal, not a capability unlock.**" The §8(c) hole ("CI never verifies `.cr-ok`", gitignored, never reaches CI) means it's "not even enforced server-side." Pass2-E/H; pass1 §2 (Ona), §7.
- **Conservative disposition:** §C DEFERRED. Pass3 §b(3) named both the design weakness (the §9 row) and the concrete better pattern (Ona) — then carried it as a gap to "synthesize into the V2 build plan" rather than build. It is the most rigorously-diagnosed item in the pass and was still parked.
- **RE-JUDGMENT under the new charter: ELEVATE.** Pass2-E itself said this pattern "generalizes past bug-fixing" to "an agent editing the harness's own config" — which is exactly the self-improving-loop the new charter wants. The old disposition treated it as a tidy diagnosis to file; the charter makes it the *governance mechanism for autonomy itself*. World-class scope: cost-ordered risk tiering + 10% drift sampling + public observability is the Ramp/Ona-grade auto-approval contract — strictly better than our binary present/absent token, and the prerequisite for any safe self-improving loop. The §9 row *already pre-authorized the downgrade*; the only thing missing was the will to build the replacement, which the new charter supplies.

### Move: The agent-PR observability log (public channel as automation backstop)

- **Plain-English what & why:** Every autonomous action an agent takes — every auto-approval, every PR opened, every escalation — gets posted to one visible, append-only channel a human can scan. Ona posts every auto-approval to a public Slack channel; the article's Action Item #4 is literally "Slack channel as the agent-PR log" (pass1 §12). The failure it prevents: automation that runs in the dark. Once agents open and approve PRs without a human in the loop per-PR, the *only* way to catch a degrading classifier or a runaway is to have a single feed where the pattern becomes visible. Pass2-E: "observability as the backstop for automation."
- **The mechanism:** A notification/log sink — a dedicated Slack channel or a GitHub-hosted append-only log — that every autonomous skill writes to: trigger fired, PR opened (link), risk tier, auto-approved vs escalated, outcome. This is the prerequisite for the auto-approval move above; you cannot safely auto-approve without it.
- **Citation:** Pass3 §b(6): confirmed absence — "no notification/log sink in §3e–§3f; `permission-logger.sh` exists [§6] but logs permission calls, not PR outcomes." Pass1 §12 Action Item #4; pass2-E.
- **Conservative disposition:** §C DEFERRED — "If we move toward any auto-approval (#2/#3), this is the prerequisite observability and we don't have it." Conditional on the deferred auto-approval move, so doubly parked.
- **RE-JUDGMENT under the new charter: ELEVATE.** Once the trigger front-door and auto-approval are in-scope-now (above), their prerequisite observability is in-scope-now too — by simple dependency. At fleet scale (parallel agents across 5+ repos) this is *more* load-bearing, not less: one engineer cannot watch N repos' PR queues individually; the consolidated feed is how a fleet stays legible. World-class scope: a single cross-repo agent-action feed, the legibility layer for the whole autonomous fleet. The conservative disposition wasn't wrong that it's a prerequisite — it was wrong to treat the thing it's a prerequisite *for* as deferred.

### Move: `block-dangerous-bash.sh` — the safety floor that becomes load-bearing under autonomy

- **Plain-English what & why:** A deterministic guard that blocks dangerous shell actions (deploys, `rm -rf`, writes to `.git`/`.husky`/`.claude`) before they execute. The article's "tool-misuse cascade" is named the **fastest-growing failure mode of H1 2026** (pass1 §11); its defense is task-scoped tool restriction + circuit breakers. While a human drives every run, an advisory rule mostly holds; the *moment* an autonomous trigger fires unattended, an advisory rule is a suggestion and a hardcoded guard is the only real floor. The failure it prevents: an unattended agent, mid-cascade at step 40+ (intent drift, pass1 §11), running a destructive command with no human to stop it.
- **The mechanism:** Build the canon's third bash guard `block-dangerous-bash.sh` (deploys, `rm -rf`, boundary writes to `.git`/`.husky`/`.claude`), wired as a PreToolUse Bash hook alongside the existing `block-dangerous-git.sh` and `block-npm-install.sh`. This is the non-negotiable companion to the trigger front-door.
- **Citation:** Pass3 §b(4) + ground-truth §3e, §5: the canon's 3rd structural guard `block-dangerous-bash.sh` is "**ABSENT on disk.** Disk has no safety-floor bash guard." Pass1 §11 (tool-misuse cascade, fastest-growing failure mode).
- **Conservative disposition:** §C DEFERRED-conditional — "If we ever wire any autonomous trigger (gap #1), this guard becomes load-bearing." Parked behind the same deferred trigger.
- **RE-JUDGMENT under the new charter: ELEVATE — and reorder it as a *blocker*, not a follow-on.** The new charter wires the autonomous trigger. By pass3's own conditional ("*if* we wire any autonomous trigger... this guard becomes load-bearing"), the antecedent is now true, so the guard is load-bearing *now*. This is the one move where the conservative reasoning was correct-but-inverted: it said "build this only after autonomy," but the right ordering is "this ships *before or with* the first trigger, never after." It clears the §9 golden rule trivially — it names a precise failure mode (unattended destructive command during a tool-misuse cascade) and aligns with the keep-verbatim PocketOS safety floor. This is the rare item where ELEVATE means *raise its priority and make it a precondition*, not "make it bigger."

### Move: `session-end.sh` — memory capture so autonomous runs compound (self-improving loop)

- **Plain-English what & why:** A Stop-hook that, when an agent run ends, proposes memory candidates — what was learned, what failed, what root cause recurred — so the next run starts smarter. Cursor's BugBot has a memory tool and "learns across runs" (pass1 §2); pass2-G examines the tension (memory should inform *triage/root-cause*, never *scope of the change*). The failure it prevents: an autonomous bug-fix loop that re-learns the same lesson every night and never compounds. Pass3 §b(5): "An autonomous bug-fix loop that can't write back what it learned is the un-compounding version the article implicitly warns against."
- **The mechanism:** Build the canon's `session-end.sh` (Stop → memory candidates), with the pass2-G boundary encoded: memory informs root-cause/triage, never licenses scope creep. Wire it so autonomous runs (not just human sessions) write back, turning the bug-fix loop into a self-improving one.
- **Citation:** Pass3 §b(5) + ground-truth §3e, §5: canon's `session-end.sh` is "**absent; disk memory is fully manual.**" Pass1 §2 (Cursor memory tool); pass2-G.
- **Conservative disposition:** §C DEFERRED — carried as gap #5, tied to the un-built autonomous loop.
- **RE-JUDGMENT under the new charter: ELEVATE — this is literally the "self-improving loop" the charter names as first-class.** The new charter lists "self-improving loops" among the designed-in autonomy primitives. A memory-capture hook on run-end is the minimum mechanism for compounding. World-class scope: not just human-session capture but *autonomous-run* capture, with the root-cause-vs-scope boundary (pass2-G) encoded so the loop gets smarter at diagnosis without getting sloppier at scope. Caveat to keep it honest: do *not* let memory widen the diff (pass2-G's tension) — the §9 "ghost rules" discipline applies, so the captured memory must be observed-useful or pruned. With that guard, ELEVATE.

## Autonomy angle

This source is the corpus's *primary* autonomy text — it is the bug → reviewed-PR pipeline rendered as an industry survey. It teaches all four charter autonomy dimensions concretely:

- **Bug → PR:** the entire spine (pass1 §1: surface → trigger → triage → fix-or-escalate → PR → review). The five ranked trigger surfaces (pass1 §3) and the fix-vs-escalate logic (pass1 §5) are a direct blueprint.
- **Slack/Linear summon:** Ramp Inspect integrates with Slack + Linear rather than new interfaces (pass1 §2); the `/minion fix <ticket>` Slack command is the lowest-friction trigger (pass1 §3.5); Linear Agent turns the tracker into "an agent work queue" (pass1 §2).
- **Self-improving loops:** Cursor BugBot's memory tool learns across runs (pass1 §2); Ona's 10% human-drift sampling stops the classifier silently degrading (pass1 §2) — a self-correcting governance loop. Maps to our absent `session-end.sh`.
- **Cloud scheduling:** the "overnight operation" section (pass1 §8) is exactly cloud `/schedule`'s use case — queue curated labeled issues before EOD, run in isolated sandboxes with no prod access, morning Slack digest, hard 2-retry cap, PR-queue cap (~10). With cloud `/schedule` confirmed real, this whole section moves from aspirational to buildable.

The safety model for all of it is also here: auto-approve ≠ auto-merge (pass2-H — "never let the agent be the last deterministic gate before main"), the deterministic sandwich (pass2-B), and the failure-mode/defense table (pass1 §11) that tells you exactly what guards an autonomous loop needs (retry cap, token budget, test-count floor, tool-scoping, reproduction-before-fix).

## The single biggest move (one paragraph)

**Build the autonomous trigger front-door — the label/Slack-Linear/CI-failure entry that summons an agent into the existing worktree → `/cr` → `pr.sh` shell — and ship it with its non-negotiable safety companions (`block-dangerous-bash.sh`, the structural review contract, and the agent-PR observability log).** This is the move because the article's deepest finding (pass2-A) is that the agent is the cheap interchangeable middle and the two *ends* — trigger quality and review contract — are where all the value lives, and our harness already has a world-class middle (isolated worktrees, deterministic pre-commit/pre-push/CI, strong `/cr`, full context files) but **no front door at all** (pass3 §b(1): "the single largest gap the article exposes"). The conservative synthesis correctly located this gap and then deferred it behind a decision gate the new charter has now affirmatively opened: cloud `/schedule` kills the durability objection, `disable-model-invocation:true` makes the side-effect open-PR skill safe, and the structural back-gate (test-count floor + blast-radius/keyword classifier + Ona-style cost-ordered auto-approval) turns the existing advisory reviewer into a world-class one. Wiring the front door is what converts a build-capable harness into an *autonomous* one — it is the exact "bug → reviewed PR" north star, and everything else this source teaches (the safety floor, the structural contract, the observability log, the memory-capture loop) is the scaffolding that makes the front door safe to open.
