# Ambition Re-mine — Claude Code Auto-Mode Configuration (Reliable Long-Running Agents)

## What this source is (plain English, 2-3 sentences)

A primary-source study of Claude Code's **auto-mode** — the feature that lets an agent run unattended by replacing the human "allow this tool call?" prompt with an automatic classifier that judges each action against rules plus a prose description of your environment. The article's spine: auto-mode does not delete the trust decision, it *relocates* it from a runtime prompt a human answers to config-time prose an operator wrote hours earlier — so the new failure mode is silent misclassification (the classifier quietly blocks legit work, or quietly allows something dangerous). It ships a copy-paste `autoMode` settings block and explicitly assigns — but does not build — a pre-flight verification script that proves the config is correct before a run.

This source is the **single most autonomy-relevant article in the entire v2-audit corpus**: auto-mode *is* the mechanism that makes "keep working when the laptop is closed" safe, and pass3's live machine check found the project's auto-mode config is currently sitting in a file the classifier ignores — meaning every unattended /queue run today is governed by bare defaults.

## The full-ambition moves this source teaches

### Move: Auto-mode as the safe-autonomy substrate (relocate the trust gate, then re-build verification around it)

- **Plain-English what & why:** When an agent runs unattended, there is no human to answer "allow this push? allow this DB write?" Auto-mode replaces that human with a classifier that reads each tool call plus a prose description of your infrastructure ("here is my GitHub org, my Supabase URL, my npm registry") and decides allow/block on its own. The failure it prevents is the *unattended stall* — the old world where an unsafe-looking op produced a prompt no one was there to answer, so the whole overnight run froze. The new failure it introduces is *silent misclassification* — the classifier blocks a legit `gh pr create` because your org isn't described, and the run dies with no error anyone sees until morning. The world-class team treats the trust decision as a thing that *moved*, not a thing that *vanished*, and rebuilds the verification the prompt used to give for free.
- **The mechanism:** Adopt auto-mode as the *deterministic enforcement layer for autonomy* in V2. Concretely: (1) author the `autoMode` block — `environment` (prose: GitHub org, Supabase project, npm registry, local services), `allow`, `soft_deny`, `hard_deny`, each list led by `"$defaults"`; (2) place it in the file the classifier actually reads (`~/.claude/settings.json` or — pending Open Q#1 — `.claude/settings.local.json`); (3) verify with `claude auto-mode config` that custom entries appear in the *effective* config. This is the gate that lets bug→PR, Slack-summon, and cloud /schedule run without a babysitter.
- **Citation:** Confirmed absence — pass3 (b)(1) [live-check]: `claude auto-mode config` shows **defaults only**; the project's custom entries (tanner-dev, event-vendor, registry.npmjs) appear **0 times** in effective config; `~/.claude/settings.json` has **no `autoMode` key**. `autoMode` appears in **no §3 row** of `CANONICAL-HARNESS-AS-IS.md` — the as-is map predates auto-mode entirely. `§3e` confirms the system is "overwhelmingly advisory… no deterministic backstop for the bulk of skill bodies, CLAUDE.md rules, or the autoMode lists."
- **Conservative disposition:** The conservative synthesis collapsed this into a narrow "wiring tweak" — relocate the block, re-run the verify command. Pass3 itself frames it as "mechanical" ("the fix is mechanical: relocate to `~/.claude/settings.json`, verify"). It is filed as a config-placement bug, not as a pillar.
- **RE-JUDGMENT under the new charter: ELEVATE — dramatically.** Calling this a "wiring tweak" is the single worst piece of conservative under-scoping in the corpus. Under the old "defer the autonomy front-door" charter, auto-mode was just hygiene for the occasional overnight run. Under the new charter — *autonomy is first-class; cloud /schedule EXISTS and runs committed skills on Anthropic infra* — auto-mode is the **load-bearing safety substrate for the entire autonomy program**. Every other autonomy move (bug→PR, Slack summon, self-improving loops, scheduled runs) is unsafe-to-impossible without a correctly-configured, *verified* classifier perimeter. The mechanical fix is real but it is the *smallest* part: the world-class version is "auto-mode is a designed-in V2 pillar with its own author→verify→distribute lifecycle," not "move a JSON block." This should be in-scope-now and treated as foundational, roughly 10x the weight the conservative synthesis gave it.

### Move: The pre-flight verification gate (the un-typed config gets a compile step)

- **Plain-English what & why:** The environment description is **prose**, not code — so there is no compiler, no type-checker, no test that can tell you before a run whether the classifier will actually allow the destinations your tasks need. A greedy regex you can lint; a paragraph of English you cannot. The failure this prevents is exactly the one pass3 found live: an `autoMode` block that *looks* complete but is inert (wrong file, or missing a `"$defaults"`, or missing the org), discovered only after an overnight fleet has silently stalled. The world-class team treats the prose policy like untrusted input and builds the verification the language can't give them: a script that parses the *effective* config and asserts every destination the run touches is actually trusted, exiting non-zero if not.
- **The mechanism:** Build the script the article assigns but never writes. It (1) runs `claude auto-mode config`, (2) checks every external destination in a /queue destination manifest (GitHub org, Supabase URL, npm registry, local ports) against the effective `environment`, (3) asserts `"$defaults"` is present in each custom list (catches the silent-strip footgun), (4) exits non-zero on any miss. Wire it as a **mandatory /queue pre-run gate and a cloud /schedule pre-flight** — no unattended fleet launches without a green pre-flight, the same way no push happens without `.cr-ok`.
- **Citation:** Confirmed absence — pass3 (b)(2): "No pre-flight verification mechanism exists — the article's own Design Challenge is unbuilt, and nothing on disk fills it." `CANONICAL §3e` documents `session-start.sh` and `worktree-create.sh` but **no hook/script checks effective `autoMode.environment` against a destination manifest.** Maps to `§5` (canon-only items to build) as a *new* row the map doesn't have. Pass1 §10 (the Design Challenge), pass2 §A ("config-time trust written in prose has no compile step — so the operator must build their own").
- **Conservative disposition:** Pass3 (d) lists building this script as one of four "cheap executions" but the conservative synthesis folded it into the same single "wiring" move as the relocation — it was not elevated to a standing gate. It reads as a one-off chore, not a permanent mechanism.
- **RE-JUDGMENT under the new charter: ELEVATE.** Pass2 §A nailed the real thesis: "the deliverable is not 'an autoMode block' — it's a **verification discipline around the autoMode block**." The conservative synthesis adopted the artifact and dropped the discipline — which is precisely backwards, because pass3 (c)(5) shows the *missing verification is what let the live misconfiguration go unnoticed.* Under "clarity beats minimalism, more mechanisms is fine when each earns its place," a permanent pre-flight gate obviously earns its place: it is the compile step for an un-typed safety policy that now governs autonomous fleets across 5+ repos. This is not a chore, it is the second-most-important autonomy mechanism in the source. In-scope-now as a standing /queue + /schedule gate.

### Move: Resolve the storage-vs-distribution conflict (make the safety policy that runs unattended also committable/distributable)

- **Plain-English what & why:** Here is the structural bind. The classifier only honors `autoMode` config that lives **user-level** (`~/.claude/settings.json`) or in a **gitignored** local file — it ignores the committed, shared `.claude/settings.json`. But the entire V2 thesis is a *global, GitHub-hosted, version-controlled, self-distributing* harness. So the one safety policy that actually governs unattended autonomy is the one policy the harness **cannot commit, review, or distribute** the way it ships CLAUDE.md, skills, and hooks. Install the harness in a new repo and the autoMode block *doesn't travel with it* — every machine silently runs bare defaults until a human hand-pastes it. The failure this prevents: a fleet expanding to repo #4 and #5 where, unknown to anyone, the safety classifier is uncongfigured because the policy couldn't ride along.
- **The mechanism:** Pick and build one of: **(a)** an `autoMode` *generator the plugin ships* — committed source-of-truth (e.g. `autoMode.template.json` in the harness repo) plus a `/install` step that writes the rendered block into `~/.claude/settings.json` once per machine and immediately runs `claude auto-mode config` to confirm it took; or **(b)** if Open Q#1 resolves that `.claude/settings.local.json` *is* read, a committed template + a `.local` materializer (still per-machine, but driven from a versioned source). Either way the goal is: **the policy has a single committed canonical source, a deterministic materialization step, and a verification step** — so it distributes like everything else in the harness instead of being per-machine tribal knowledge.
- **Citation:** Pass2 §C (the unresolved storage-vs-distribution conflict); pass3 (b)(4). `CANONICAL §0`: "Every binding principle for V2 — global, GitHub-hosted, bidirectional self-update, compounding — is a response to this gap." `§8`: the harness "has never been installed anywhere but event-vendor"; "Multi-project is a goal, not a state." Confirmed absence: no row in the as-is map covers autoMode distribution because auto-mode isn't in the map.
- **Conservative disposition:** Pass3 (b)(4) surfaces it as a "V2 decision item" with two options and leaves it *undecided* — "either (a) accept user-level autoMode as un-synced per-machine setup… or (b) build a generator." The conservative synthesis carried it as an open decision, not a build.
- **RE-JUDGMENT under the new charter: ELEVATE — and decide it.** The charter resolves the fork the conservative synthesis left open: "Distribution = plugin + marketplace + thin /init template. A plugin physically can't carry permissions." That is the exact same constraint as auto-mode (a plugin can't carry the user-level safety policy either) — and the charter's *answer* is the thin per-repo /init template. So option (b) — a shipped generator/materializer invoked at install — is mandated by the chosen distribution model, not optional. Leaving this as "accept un-synced per-machine setup" (option a) directly contradicts "parallel agent fleets across 5+ repos": un-synced means repo #5 silently runs bare defaults. This is a first-class V2 build item: the autoMode policy gets a committed canonical source + an /init materialization step + a post-install verify, exactly like the permissions story the charter already settled. The conservative bias was treating "auto-mode storage is user-level" as a wall rather than as the same plugin-can't-carry-permissions problem the harness already knows how to solve.

### Move: Defaults-over-block audit for single-tenant-prod (the classifier will stall the exact migration work you're trying to unblock)

- **Plain-English what & why:** Everyone assumes the danger of a safety classifier is that it's *too permissive*. For this project the real danger is the opposite. The built-in `soft_deny` defaults block "running production database migrations" and "persistent changes to database records… without clear affirmative user consent." But this project's own environment description declares "the Supabase project IS production — treat all Supabase mutations as production," and there is no staging/prod boundary to hand the classifier (a genuine infra fact, not a config oversight). Put those together and the correctly-configured classifier will read every `supabase migration up` and every `src/data/` write during a /queue run as an unconsented production mutation → soft-block → unattended stall. The failure this prevents is subtle: a *perfectly safe-looking* config that silently kills the precise autonomous work it was built to enable.
- **The mechanism:** Before any unattended migration/data work, run `claude auto-mode critique` on the project's `soft_deny` plus a representative `supabase migration up` description, and resolve one of: an explicit `allow` carve-out for CLI-driven migrations against the configured remote, or a real local(`127.0.0.1:54321`)/prod(`*.supabase.co`) distinction the classifier can reason over (Open Q#3). This becomes a standing item in the autoMode template: "what legitimate autonomous work do the defaults over-block, and what's the narrowest carve-out?"
- **Citation:** Pass2 §G; pass3 (b)(3) [§9 + live-check]. Maps to `CANONICAL §9` (Model Capacity Audit) and its golden rule: "If you can't name a failure mode the constraint prevents, the constraint is overhead" — here the constraint *does* name a failure mode but also catches *legitimate* work, the inverse case. Live `claude auto-mode defaults` confirms the production-deploy and modify-shared-resources soft_deny entries exist.
- **Conservative disposition:** Pass3 (b)(3) calls it a "V2 decision item" and "the central operational risk for THIS project specifically" — but it is filed *under the article's Open Question #3* and not promoted to a designed mechanism. The conservative synthesis under-weighted it as an edge case, mirroring the article's own "extend, don't subtract" frame which pass2 §G calls "too benign for a single-tenant-prod codebase."
- **RE-JUDGMENT under the new charter: ELEVATE.** Under "autonomy is first-class," the whole point is unattended migration/data tasks in /queue and /schedule runs. A classifier that soft-blocks every migration is not an edge case — it is a *direct denial of the core autonomous workload*, fleet-wide, across every repo that touches a single-tenant-prod DB. The conservative "extend, don't subtract" frame is exactly the wrong mental model for the autonomy era: the operative risk is over-block, not under-block. This must be a designed, tested carve-out shipped in the autoMode template, not an open question — otherwise the bug→PR loop dies the first time the bug fix touches the database. The world-class move is to resolve the local/prod distinction *as part of the environment prose* so the classifier can tell `127.0.0.1` from prod and trust CLI migrations against the configured remote.

## Autonomy angle

This is **the most autonomy-relevant source in the corpus** — auto-mode is *literally the autonomy enabler*. Specifics it teaches, all directly load-bearing for the new charter's autonomy program:

- **Cloud /schedule + bug→PR + Slack summon all run *through* auto-mode.** The key resolved fact "cloud /schedule clones the repo, runs committed skills, calls connectors" means an unattended agent will push branches, open PRs, and hit Supabase/npm with no human at the prompt. Every one of those calls is judged by the auto-mode classifier. If the classifier isn't configured (pass3 (b)(1): it currently isn't), the scheduled run either stalls on the first un-described destination or — worse — the operator loosens it carelessly and a self-improving loop gets silent over-permission. Auto-mode is the gate that makes all three autonomy patterns *safe* rather than *reckless*.
- **`disable-model-invocation: true` + auto-mode are complementary safety layers** (per the resolved facts): the former removes side-effect skills from the model's context; the latter judges the side-effects that *do* fire. Together they are the autonomy safety floor.
- **The pre-flight gate is the autonomy launch check.** Just as no push happens without `.cr-ok`, no unattended fleet should launch without a green auto-mode pre-flight. This is the missing "is it safe to run unattended?" gate (pass3 (b)(2)).
- **The defaults-over-block risk is an autonomy-killer specifically:** it silently denies the database work that bug→PR and scheduled migration tasks depend on (pass3 (b)(3)).

In short: this source doesn't merely *touch* autonomy — it is the configuration layer that determines whether autonomy is safe or a liability.

## The single biggest move (one paragraph)

**Promote auto-mode from "a settings block to relocate" to a first-class V2 pillar: the verified, committed-and-distributed safety substrate for all autonomy.** This is the move the vision synthesis must pick up first because it is the precondition for every other autonomy ambition — bug→PR, Slack/Linear summon, self-improving loops, and especially cloud /schedule, which the resolved facts confirm runs committed skills on Anthropic infra with no human at the prompt. The conservative synthesis fatally under-scoped this as a "mechanical wiring tweak" (relocate the JSON, re-run a verify command), but pass2 §A recovered the real thesis: auto-mode *relocates the trust decision from a runtime prompt to config-time prose*, and the world-class deliverable is the **verification discipline** around that prose, not the prose itself. World-class means three things shipped together, none of which the conservative synthesis built: (1) the `autoMode` policy placed where the classifier actually reads it and proven via `claude auto-mode config` (the live machine is currently broken — bare defaults — pass3 (b)(1)); (2) the **pre-flight gate** that compiles the un-typed prose policy before every unattended launch (pass3 (b)(2)); and (3) a **committed canonical source + per-repo /init materializer** so the policy distributes with the harness across the 5+ repo fleet instead of being hand-pasted tribal knowledge (pass3 (b)(4), resolved by the charter's plugin+/init distribution model). Get this pillar right and autonomy is safe to turn on everywhere; skip it and the first scheduled run either stalls in the dark or over-permissions itself silently.
