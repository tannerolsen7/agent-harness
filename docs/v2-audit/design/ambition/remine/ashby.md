# Ambition Re-mine — Ashby: AI-Native Engineering Process & Practices (2026)

## What this source is (plain English, 2-3 sentences)
Ashby (an HR/recruiting SaaS) published an engineering account claiming >50% of new production code since Aug 2025 is AI-generated "without quality degradation," built on a deliberate apparatus: two operating modes (Sidekick / Delegate keyed to blast radius), a thick verification net (65 Playwright E2E tests in four weeks, fuzzing, static analysis, DangerJS + CodeRabbit + a custom in-house edge-case-bug reviewer), a SQLite mirror of all issues/PRs/comments so engineers and LLMs can ask "has anyone seen this bug before?", weekly-updated committed skill files, and Claude-Code bug-triage that cut some Support fixes from hours to ~10 minutes. The deeper, unstated thesis (recovered in pass2) is that defensibility migrates from *writing* code to *judging* it — the whole apparatus exists to make cheap generation safe — and that accountability quietly gets redefined from "I read the diff line-by-line" to "I judged the risk."

## The full-ambition moves this source teaches

### Move: Autonomous bug-triage front-door (incoming bug → diagnostic report → fix)
- **Plain-English what & why:** When a bug or support ticket lands, an agent automatically reads it, reproduces it where it can, reads the relevant code and history, and produces a diagnostic report — sometimes the fix itself. Ashby cut some Support fixes from *hours to ~10 minutes* this way. The failure it prevents: a human burning an hour on the mechanical part of triage (which file, what changed, who touched it last, is this a known class of bug) before any judgment is even possible. The agent does the legwork; the human judges and ships.
- **The mechanism:** A `/triage` (already exists as a skill name) wired into a real *trigger*: a GitHub Issue label or a Linear/Slack inbound fires a cloud `/schedule` (or webhook → background agent) that reads the bug, greps the codebase + git history + PITFALLS/solutions corpus, reproduces against the test stack, and opens a draft PR or posts a diagnostic comment. The side-effect skill (open-PR / post-comment) is marked `disable-model-invocation:true` so it only runs through the deterministic front-door, never freelanced mid-conversation. This is the canonical bug→reviewed-PR loop the new charter puts first.
- **Citation:** pass1 lines 38-39 ("Bug-triage automation: Claude Code reads incoming bugs, produces diagnostic reports; cut some Support fixes from hours to ~10 minutes"). Ground-truth absence: no trigger/front-door anywhere in the harness — §3b skills registry lists `/triage` etc. but every entry is human-invoked from a session; there is no inbound-event → agent wiring in §2 (global machine layer) or §3e (hooks are all git-lifecycle, none inbound).
- **Conservative disposition:** §C DEFERRED. pass3 treats the bug-triage automation only as evidence that "lens-* agents are Ashby's reviewer-as-prompts" and as part of the latent-tension argument; it never proposes building the *trigger*. The whole front-door (bug→PR, Slack/Linear summon) is exactly what MASTER-FINDINGS deferred as "the autonomous trigger front-door." pass3's net contribution explicitly excludes it: "four citable gaps" — runtime logging, PII, blast-radius tier, rejected-approaches log — none of which is the trigger.
- **RE-JUDGMENT under the new charter: ELEVATE.** This is the single largest suppression. The new charter makes autonomy first-class and confirms cloud `/schedule` exists on Anthropic infra (clones repo, runs committed skills, calls connectors) — so the old "machine asleep / no durable runtime" objection is moot. Ashby is the source that *demonstrates the ROI* of this exact loop with a hard metric (hours → 10 min). The conservative pass under-read it as "we already have lens agents" — a category error: an adversarial *reviewer* invoked inside a session is not an *inbound trigger* that turns a filed bug into a reviewed PR with no human in the loop until judgment time. This should be in-scope-now and built large: a `/triage` front-door bound to GitHub Issues + Linear + Slack, fanning to a background worktree agent, gated by `disable-model-invocation` side-effect skills. It is the spine of the V2 autonomy story, not a deferred nicety.

### Move: Explicit blast-radius tier declared at task-start (Sidekick vs Delegate)
- **Plain-English what & why:** Before starting work, the agent classifies the change by *blast radius*: high (migrations, security, architecture) runs in **Sidekick** mode (human decides, AI assists); low (prototyping, local tooling) runs in **Delegate** mode (AI runs, human spot-checks). The failure it prevents: an agent silently treating a high-blast-radius change (an RLS policy, a destructive migration) with the same casual autonomy as a throwaway script. Mis-tiering is *the* failure the scheme exists to catch.
- **The mechanism:** Add a **blast-radius column** to the work-state table in `.claude/AI-WORKFLOW.md` (currently keyed only on signal → work state → entry point), and require the agent to *declare the tier in its first message* — the tier then selects the autonomy envelope (which side-effect skills are allowed, whether a human gate is mandatory, whether the run can go unattended overnight). At fleet scale this is the routing key that decides which of N parallel agents may auto-merge and which must stop for a human.
- **Citation:** pass1 lines 30-31 (two operating modes); pass2 lines 64-69 ("blast-radius must be legible at task-start … the article offers no mechanism that *enforces* the tier — it's a cultural norm, not a guardrail"). Ground-truth §3b + disk: pass3 verified "blast radius" appears in `AI-WORKFLOW.md` only once, incidentally, in the hotfix row — never as a declared classification.
- **Conservative disposition:** §D-minor / partially applied. pass3 gap-b3 *did* keep this but shrank it to "a real, small, well-targeted addition … add a blast-radius column." It is framed as a documentation tweak, not as an enforcement primitive.
- **RE-JUDGMENT under the new charter: ELEVATE (moderately).** The column is right but the conservative framing under-builds it. pass2's own insight is that the tier is *unenforced* — and the §9 golden rule demands a constraint name a failure mode (mis-tiering a destructive change is that failure mode, and it maps directly to the PocketOS incident the harness already treats as sacred). So the move is not "add a column"; it is "make blast-radius a *declared, enforced routing key* that gates autonomy level." At fleet scale across 5+ repos, this is the dispatcher that decides which agents may run unattended — that is structural, not cosmetic. Still an ELEVATE rather than a giant new build, because the mechanism is small; what changes is its *status* (enforcement primitive, wired to the trigger front-door above and to `disable-model-invocation`).

### Move: Verification-as-the-bottleneck — fund the test/observability net to match generation throughput
- **Plain-English what & why:** Ashby's whole thesis is "writing is cheap, *verification* is the bottleneck, and investment must follow." Concretely they shipped 65 Playwright E2E tests in four weeks (70% by non-QA engineers), added fuzzing and static analysis, and — critically — their defense-in-depth *ends in feature flags + runtime observability*, not at the merge gate. The failure it prevents: cheap AI code outrunning the net that catches its mistakes, so volume rises but nobody can see when a generated change silently breaks in production. A pre-merge-only stack is *structurally blind* to runtime — a category gap, not a quality gap.
- **The mechanism:** Two parts. (1) **Runtime failure-logging** below the merge gate: a Supabase error-log table the public `/p/[token]` renderer writes to on a caught render failure (the `error.tsx` boundary already exists but records nothing), plus an optional boolean feature-flag column so a broken renderer can be dark-launched. (2) **Property-based / generative testing** for money-math (recipe pricing, $30k proposals) — the fuzzing analogue — so verification scales with generation instead of staying hand-written-example-only.
- **Citation:** pass1 lines 40-41 (65 E2E tests, fuzzing, static analysis); pass2 lines 76-78 ("a pre-merge-only stack is structurally blind … runtime ≠ merge-time"). Ground-truth confirmed absence: pass3 gap-b1 verified no Sentry/observability/feature-flag dependency in `package.json` or `next.config.ts`; §3e/§3f are entirely pre-merge; the property-based-testing piece is the deferred item MASTER-FINDINGS named.
- **Conservative disposition:** Split. The runtime-logging half is §C-deferred-then-promoted to gap-b1 ("four citable gaps" #1) — kept but scoped to "a table + error boundary, no vendor yet." The property-based-testing half is §C DEFERRED in MASTER-FINDINGS ("property-based testing for money-math") and pass3 does not raise it at all for Ashby.
- **RE-JUDGMENT under the new charter: ELEVATE.** The runtime-logging gap is correctly identified but the conservative "no vendor, just a table" scoping is the over-engineering reflex over-correcting. Under "world-class is the only goal," the move is a *real observability layer* feeding the autonomy loop: runtime failures become inbound triggers (move 1) — a render error on a client's proposal auto-files a triaged bug. That closes verification→autonomy into a loop, which is the world-class shape. The property-based-testing half should be recovered as in-scope-now for money-math specifically (the $30k-client blast radius is precisely where example-based tests under-cover); pass2's fuzzing citation makes it a cited gap, not a phantom. The "table is enough" framing is conservative bias because it treats observability as a checkbox rather than the trigger substrate the autonomy charter needs.

### Move: Queryable institutional memory — "has anyone seen this bug before?"
- **Plain-English what & why:** Ashby clones every issue/PR/comment into SQLite so engineers *and in-house LLMs* can query the full history: "has anyone seen this specific bug before? what was the fix?" The failure it prevents: re-debugging a problem the team already solved, because the prior solution is buried in a closed PR no one remembers. It is a *search* capability over historical incidents, distinct from "what rules apply" (which curated markdown answers).
- **The mechanism:** A retrieval layer over the harness's own history — git log + closed PRs + PITFALLS/solutions/post-mortems — that an agent queries before debugging. At solo-to-fleet scale this is *not* a SQLite mirror of hundreds of engineers' PRs; it is closer to "index PITFALLS.md + docs/solutions + post-mortems + git history into something an agent retrieves from at triage time."
- **Citation:** pass1 lines 35-36 (git-metadata → SQLite substrate); pass2 lines 71-74 (it is "a *search* problem born of *volume*"). Ground-truth §4 memory model: five/six stores, all re-read whole, none *queried* — confirmed absence of a retrieval/search layer.
- **Conservative disposition:** §F REJECTED-as-over-engineering. pass2 line 72: "The article's Pass 3 correctly flags this as over-engineering at solo scale — the substrate is a proxy for 'I can't read my whole history,' which a curated markdown corpus that agents re-read every session already solves at small N." pass3 gap-c reinforces: "we shouldn't *build* the SQLite DB at solo scale."
- **RE-JUDGMENT under the new charter: UPHELD-CUT (with a recovered sliver).** The *SQLite mirror of all PRs* is a genuinely bad fit even at fleet scale across 5+ repos: the named failure mode it prevents (re-debugging buried history) is, for a corpus this size, already covered because agents re-read the entire PITFALLS/solutions/memory corpus every session — there is no volume problem to solve, so building a search index is overhead with no failure mode it uniquely prevents (§9 golden rule). **However**, pass3 itself flags the *equivalence-by-assertion* problem honestly: markdown answers "what rules apply," not "has anyone seen *this specific bug*." The recoverable sliver: when the triage front-door (move 1) fires, it should retrieve from git history + closed PRs, not only the curated markdown — i.e. retrieval *at trigger time*, scoped to the bug, not a standing indexed database. That sliver is NEW-adjacent and cheap; the full substrate stays cut. This is the honest UPHELD-CUT the prompt asks for: a real failure mode justifies cutting the big version even at fleet scale.

### Move: Redefine accountability from "I read the diff" to "I judged the risk" (the unstated mechanic)
- **Plain-English what & why:** As AI's share of code rises, the "a human combs every PR line-by-line" accountability model becomes the bottleneck the thesis says to eliminate. Ashby resolves this *implicitly* by moving review up an altitude — "does this change make sense / where's the risk / are the abstractions sound" — but never admits this *redefines* accountability. The failure it prevents: pretending line-by-line review still scales while autonomy quietly removes the human from the diff, leaving accountability theater with no real backstop.
- **The mechanism:** Make the redefinition *explicit* in the harness. `/cr`'s 9-pass review already operates at the "does this make sense / where's the risk" altitude — so the move is to *own* that this is the accountability model, and to bind the human gate to *risk tier* (move 2) rather than to "a human read every line." For autonomous worktrees where "a human combs the PR" is not even available, the agent must declare what risk it judged and what it could not verify — a structured risk-attestation in the PR body, not a claim that a human read it.
- **Citation:** pass2 lines 51-62 (the contradiction the article does NOT name — net-new analysis: "redefines accountability from 'I read the code' to 'I judged the risk' … event-vendor will have to make it *explicit* because, with autonomous worktrees, 'a human combs the PR' is not even available").
- **Conservative disposition:** §C effectively DEFERRED / dropped. pass3 carries the *category gap* (runtime) forward but does not carry the *accountability-redefinition* mechanic into any of its four gaps. It is pass2's strongest net-new insight and the conservative synthesis summarized it away.
- **RE-JUDGMENT under the new charter: NEW.** This is a first-class candidate the conservative pass lost. Under autonomy-first, it is *the* governing question: if no human reads the diff, what exactly is the accountability unit? The mechanism is a **structured risk attestation** the agent must produce (what tier, what it verified, what it could not, what it is asking a human to judge) — wired to the blast-radius tier (move 2) so high-tier changes demand attestation + human gate, low-tier may auto-merge. This is precisely the auto-merge-on-confidence question MASTER-FINDINGS rejected, reframed correctly: not "merge when the agent feels confident" but "merge when the declared risk tier permits and the attestation is complete." World-class because it is the only honest answer to "who is responsible when the fleet ships."

## Autonomy angle
Yes — Ashby is one of the most autonomy-relevant sources in the set, and the conservative pass suppressed exactly that dimension.
- **Bug → PR:** directly taught. The bug-triage automation (Claude Code reads incoming bugs → diagnostic report → fix, hours→10min) is the bug→reviewed-PR loop, with a *measured* payoff. Move 1.
- **Slack/Linear summon:** implied by the inbound-bug front-door — the trigger that fires the triage agent is exactly a Slack/Linear/GitHub-Issue inbound. The mechanism Ashby demonstrates is the *agent side*; the charter supplies the summon side (now buildable via `/schedule` + connectors).
- **Self-improving loops:** the "skill files committed and updated weekly" practice (pass1 line 37) plus the verification-net investment is a compounding loop; closing runtime-failure → triaged-bug → fix → new test → updated skill is the self-improving loop the charter wants. Moves 1 + 3.
- **Cloud scheduling:** Ashby doesn't name a scheduler, but its triage loop is precisely the workload `/schedule` was built to run unattended (clone repo, run committed `/triage`, call GitHub/Linear connectors). The resolved fact that cloud `/schedule` exists is what flips Ashby's loop from "deferred durability spike" to "build now."

## The single biggest move (one paragraph)
**Build the autonomous bug-triage front-door (move 1): an inbound trigger — GitHub Issue label, Linear ticket, Slack summon, or a runtime failure from the new observability layer — that fires a cloud-scheduled background agent which reads the bug, retrieves relevant git history + PITFALLS/solutions, reproduces against the test stack, and opens a draft PR or diagnostic comment, with all side-effect skills (open-PR, post-comment, deploy) marked `disable-model-invocation:true` so they only ever run through this deterministic door.** This is the move the vision synthesis should pick up first because it is the one place Ashby supplies a *hard ROI metric* (hours → ~10 minutes) for the exact loop the new charter makes first-class, and because the single resolved fact that killed it last time — "the machine is asleep / no durable runtime" — is now moot (cloud `/schedule` runs on Anthropic infra). The conservative synthesis read this only as "we already have lens-* review agents," which confuses an in-session adversarial reviewer with an inbound autonomous trigger; they are different instruments. Everything else Ashby teaches (blast-radius routing, runtime observability, risk-attestation accountability) is in service of making *this* loop safe — the tier decides which triaged bugs auto-merge, the observability layer feeds the trigger, and the attestation answers "who is responsible." It is the spine, and it is world-class precisely because it closes verification, autonomy, and accountability into one loop instead of three deferred fragments.
