# Ambition Re-mine — Basis: "Making Our Monorepo Ergonomic for Agents" (Deep Analysis)

## What this source is (plain English, 2-3 sentences)
Basis is a production accounting-AI company whose internal "Atlas" team spent three months re-engineering their monorepo so that *agents*, not just humans, are first-class consumers of the codebase. Their central reframe: a codebase is now two things at once — source that runs in production AND context that agents read to make decisions — and a human onboards once while an agent re-onboards every single trajectory, so small inconsistencies that used to go unnoticed now compound across thousands of agent onboardings a month. The article enumerates a canon/not-canon authority taxonomy, a six-layer context architecture, AGENTS.md authoring rules, and — most importantly — an "Automatic Context" maintenance machine (CI checks, a daily scanner, daily worker agents) that keeps the canon self-consistent.

---

## The full-ambition moves this source teaches

### Move: Canon/not-canon authority taxonomy as the spine (not a doc-organizing nicety)
- **Plain-English what & why:** Every artifact in the repo is declared as exactly one of two things: *source-of-truth-about-today* (canon) or *intent/history/hypothesis* (not-canon — `.specs/`, tickets, `.notes/`). Never both. The failure this prevents: an agent treats a stale design note or an old ticket as a description of how the system works today, and reasons wrong about the whole codebase. Pass 2 (§A, §B) recovers the deeper thesis the article half-buries: the *only* reason this matters is that it makes documentation **machine-checkable** — once you've declared a corpus "supposed to agree with itself," a contradiction becomes a failing assertion, a broken reference becomes a failing assertion, staleness-vs-recent-change becomes a failing assertion. Canon/not-canon is what turns prose-you-hope-is-right into a falsifiable target. It is the test-harness pattern, applied to context.
- **The mechanism:** A `docs/standards/canonicity.md` (owner-stamped) that maps every artifact type in OUR repo to an authority level — `CLAUDE.md`/`AGENTS.md`/`CONTEXT.md`/`ARCHITECTURE.md`/skills/inline docs = canon; `docs/research/`, `docs/adr/` (intent), `TASKS.md` (intent), the auto-memory `feedback_*` store, PITFALLS war-stories = not-canon or mixed. Critically: this is the ontology that lets a checker collapse our known triple-duplication (same fact living in `.claude/memory.md` + `PITFALLS.md` + auto-memory `feedback_*`), which `/compound` already flags as "redundant" by hand.
- **Citation:** Confirmed absence — ground-truth §4 names the triple-duplication the canon "both sanctions and forbids" and states the Phase-3 target is "ONE coherent model … every store one writer/one reader/one freshness rule." No canon/not-canon authority map exists on disk (pass3 §b.1).
- **Conservative disposition:** §C-adjacent / partial-elevate. Pass3 §b.1 names it "a real gap" and ties it to the Phase-3 crux, which is more honest than a deferral — but MASTER-FINDINGS folded the maintenance machinery downstream of it into the cautious "lightweight tier only" framing (pass3 §b.3), which functionally caps the ambition of the taxonomy to "a doc that helps humans dedupe."
- **RE-JUDGMENT under the new charter: ELEVATE.** This is the load-bearing move of the entire source and it should be in-scope-now at full size, not capped. The conservative read treated the taxonomy as a documentation-hygiene improvement; pass2 §B proves it is actually the *enabling precondition for a self-improving context loop* — "automated maintenance is only possible because we agreed on what is canonical." Under a charter where self-improving loops are first-class, you cannot adopt the loop (next move) without adopting this at full strength first. Bigger than the conservative framing by one whole tier: not "write a standards doc," but "declare an invariant over the canon so a machine can certify it and a worker agent can fix it." This is the spine the whole vision synthesis should build on.

### Move: Automatic Context — the daily scanner + worker self-improving loop
- **Plain-English what & why:** Basis runs three layers of maintenance on their context corpus: (1) a CI/CD check on every merge validating frontmatter, prose, owners; (2) a *daily scanner* that sweeps all skills + AGENTS.md for staleness, contradictions, duplicated instructions, broken references, and missing context for recent code changes — filing tickets; (3) *daily worker agents* that pick up those tickets and implement the small scoped fixes. The failure this prevents: canon rots silently. A doc claims to describe today, the team believes it's canon, but it quietly went stale — and now every agent that onboards inherits the rot. Pass2 §G sharpens this into the missing third state: canon is really *declared-canon-failing* (a scanner ticket) vs *declared-canon-passing* (trustworthy), and **canon is a liability until the scanner certifies it.**
- **The mechanism:** A scheduled cloud agent (`/schedule`) that clones the repo and runs a committed `context-scan` skill: detect contradictions across `CLAUDE.md`/`AGENTS.md`/`CONTEXT.md`/skills, broken cross-references, entries duplicated across memory stores, and skills/docs not updated after a code change touched their subject. It files GitHub issues. A second scheduled (or summoned) worker agent picks up `context-debt` labeled issues and opens scoped PRs. Plus a CI frontmatter/owner check on every merge.
- **Citation:** Confirmed absence — pass3 §b.3 cites ground-truth §5 + §3e: "no `session-end.sh` memory hook (memory is 'fully manual'), no daily scanner, no owner-frontmatter CI check anywhere in §3a–§3f." Basis layer = pass1 §8.
- **Conservative disposition:** §C deferred / scaled-down-as-"doesn't-apply-to-solo." Pass3 §b.3 explicitly cuts the worker tier: "per pass2 §C1 the *daily-worker* tier is scale-amortized and not yet justified for a single-project harness — so the real, sized gap is the **lightweight tier**: a manual/periodic consistency check." Pass2 §C1 frames the whole automation as "amortization-derived" overhead below thousands-of-onboardings/month.
- **RE-JUDGMENT under the new charter: ELEVATE, hard.** This is the single most suppressed move in the file, and the suppression rests entirely on the two reasonings the new charter retires. (1) "Daily-worker automation is scale-amortized / not justified for a single-project solo harness" — struck: the real scale is parallel agent fleets across 5+ repos, where context rot compounds *faster* than at Basis because each repo's canon drifts independently and no human is watching all five. (2) "Machine might be asleep / durability" — moot: cloud `/schedule` runs on Anthropic infra, clones the repo, runs committed skills, and calls connectors with the laptop closed, which is *exactly* the daily-scanner/daily-worker shape Basis describes. The conservative synthesis literally could not have built this when it ran; now it can. This should be in-scope-now as a flagship autonomy loop: scheduled scanner → GitHub issues → scheduled/summoned worker → reviewed PR. Bigger than the "lightweight periodic check" by the full distance between "a human remembers to run a lint" and "the harness keeps its own context true while you sleep."

### Move: Diff-scoped `verifier` sub-agent that closes the loop inside the task
- **Plain-English what & why:** Basis has a dedicated `verifier` sub-agent role with its own context window that runs *diff-scoped* tests + pre-commit hooks and reports pass/fail with actionable detail, plus a `standards-enforcer` that validates a diff against every applicable AGENTS.md and skill. The failure this prevents: an agent finishes a trajectory, declares success, and hands a human a diff that never ran the relevant tests — verification happens too late and at the wrong scope (whole-suite at feature-end instead of just-this-change in-loop). Verification is treated as a first-class role, not a hope.
- **The mechanism:** A `verifier` agent that, given a diff, runs only the tests + hooks touching the changed files and returns structured pass/fail before the work reaches `/cr` or a human. Distinct from `/cr` (9-pass, feature-end) and `/tdd` (authoring). It closes *inside* the task.
- **Citation:** Confirmed absence — pass3 §b.4 cites ground-truth §3c/§3e/§3f: "`/cr` runs at feature end … CI never verifies `.cr-ok` (the 'Node 8.5(c) gap'). There is no in-loop, pre-human, diff-scoped test/hook runner." Basis = pass1 §5.4.
- **Conservative disposition:** §E-adjacent / "we already have the review layer." Pass3 §a credits our 23 disk agents + `/cr` 9-pass as already exceeding Basis's "more than half a dozen roles" in count, and pass3 §b.4 acknowledges the gap but frames it narrowly as a missing diff-scoped runner.
- **RE-JUDGMENT under the new charter: ELEVATE (genuine weak-version upgrade).** The "we already have 23 agents and a 9-pass /cr" framing is exactly the §E existence-bar trap the charter warns about. Count is not the metric; *closing the loop inside the task* is. We have a world-class *feature-end* review and zero *in-loop diff-scoped* verification — and there's a confirmed hole where CI never even checks the `.cr-ok` sentinel, so the one gate we do have is bypassable. For autonomous bug→PR (charter north star), an in-loop `verifier` is not optional: an unattended agent cannot summon a human mid-trajectory, so the verification that a human currently provides by reading the `/cr` output must become a sub-agent the working agent calls itself before opening the PR. This moves from "nice diff-scoped optimization" to "required component of the autonomy front-door." Real upgrade of a weak version, not a phantom.

### Move: Push-context vs pull-context discipline (default-no for the root; uniform correctness for the tree)
- **Plain-English what & why:** Pass2 §D recovers a distinction the article itself never names but depends on. "Default-no" (auto-loaded context must earn its place; tokens that earn no behavior are a tax) and "every file is context, demands more local correctness" sound contradictory — until you split context into *push-context* (auto-loaded every session: minimize aggressively) and *pull-context* (read on demand during a trajectory: must be uniformly correct because you can't predict what gets pulled). The failure this prevents: conflating them either bloats the always-loaded root (treating every-file-is-context as license to auto-load everything) or starves the tree (cutting on-demand docs to honor default-no). Different loading mechanisms, different rules.
- **The mechanism:** A `default-no` audit of *push-context* only — `CLAUDE.md`, `CONTEXT.md` (15 KB), root `AGENTS.md` — stripping any line that describes rather than instructs (Basis's "SRC is where we put source code" defect) and any line the model already knows. Separately, a *correctness* pass over pull-context (skills, nested docs, `src/` inline) where size is not the constraint but truth is. Plus Basis's authoring rules: instruction-not-description, resilient references (descriptive names over exact paths — "paths change, descriptions are stable"), hierarchy-first placement.
- **Citation:** Confirmed absence of a discipline — pass3 §b.6 cites ground-truth §3a: `CLAUDE.md` "Aligned in purpose, but nothing in the map asserts a default-no / instruction-not-description audit has ever run against it." Basis = pass1 §3.5, §6; distinction = pass2 §D.
- **Conservative disposition:** §D minor / confirmed-absence-of-discipline. Pass3 §b.6 lists it last and frames it as "a confirmed absence of a discipline, not a missing file" — accurate but low-energy.
- **RE-JUDGMENT under the new charter: ELEVATE (modestly) — and note "shrink root to 200 lines / front-load trigger words" was a §F reject that this rehabilitates.** Our `CLAUDE.md` is ~hundreds of lines and `CONTEXT.md` is 15 KB, both auto-loaded every single session across the fleet. At parallel-fleet scale, every wasted push-context token is paid on *every trajectory in every repo* — the tax compounds exactly the way Basis says onboardings compound. This isn't cosmetic. The right elevation is to make the push/pull split a *standing authoring rule* in the harness (and a check in the scanner above), not a one-time audit. It does not need to become a 200-line hard cap (that specific §F reject stays cut — see below), but the discipline behind it — instruction-not-description, audit the auto-loaded surface — is world-class hygiene that the fleet pays for if skipped.

### Move: Unified MCP server for in-task external context
- **Plain-English what & why:** Basis runs one MCP server exposing Linear, Slack, Better Stack logs, PostHog, and the dev DB, so an agent mid-debug can pull a ticket, check prod logs, and query the DB without a human pasting context. The failure this prevents: an agent stalls mid-trajectory because the evidence it needs lives behind a tool it can't reach, and a human has to babysit the context-paste.
- **The mechanism:** A single MCP surface exposing GitHub issues + Supabase logs/advisors + Vercel runtime logs + analytics, callable by a debugging agent in one trajectory.
- **Citation:** Confirmed absence — pass3 §b.5 cites ground-truth §2/§1: "global MCP is `notion` only; project layer adds Supabase tooling but there is no single server exposing GitHub issues + Supabase logs + analytics for an agent mid-debug." Basis = pass1 §5.5.
- **Conservative disposition:** §C deferred. Pass3 §b.5 + §d.2: "defer until a second project exists (ground-truth §8: harness has 'never been installed anywhere but event-vendor') … it would be premature per the build-what's-needed-now rule." Severity downgraded for "single project, no Linear/Slack/PostHog stack."
- **RE-JUDGMENT under the new charter: UPHELD-CUT (partial), with a named caveat.** This one I will *not* reflexively elevate. The specific failure mode that justifies the cut: a *unified custom MCP server* is an integration surface you must build, host, and keep credentialed — and pass2 §F flags MCP-as-architecture as the deepest vendor lock-in in the whole article ("they've decoupled the vocabulary, not the architecture"). At fleet scale the *unified-server* shape is a liability: cloud `/schedule` runs with restricted network and no local MCP servers (only claude.ai connectors), so a self-hosted unified MCP is precisely the thing the autonomy substrate can't reach. The world-class move at OUR scale is not "build Basis's one server" — it's compose the *already-present* claude.ai connectors (GitHub, Supabase, Vercel, Notion all available as MCP) into the debugging agent's toolset. So: the *unified-custom-server mechanism* is upheld-cut (failure mode: unreachable from cloud autonomy, lock-in, hosting tax); the *capability* (debugging agent reaches issues+logs+DB in one trajectory) is already satisfiable via connectors and should be wired, not built. Honest split rather than a blanket elevate.

## Autonomy angle
Yes — substantially, and it is the most under-mined part of the source. Basis's **Automatic Context** system *is* a self-improving loop in production: a daily scanner detects context debt and files tickets; daily worker agents pick up those tickets and ship scoped fixes (pass1 §8). That is a bug→PR loop applied to the *context layer* instead of the code layer — the exact shape the new charter wants as a first-class front-door, and the article's own "what's next" (pass1 §10) extends the same machinery from instructions to code itself ("automatic code maintenance, redesigning code review"). The conservative synthesis cut the worker tier as "scale-amortized," but cloud `/schedule` (clones repo, runs committed skills, laptop closed) removes the only real objection — the loop is buildable now. The `verifier`/`standards-enforcer` sub-agents (pass1 §5.4) are the autonomy-safety component: an unattended agent that can't summon a human must self-verify its diff before opening a PR, which is precisely what these roles provide. Slack/Linear summon is not directly taught here (Basis's MCP exposes Linear/Slack as *read* context, not as a trigger front-door), so on summon specifically: none. On self-improving loops and cloud scheduling: strongly present.

## The single biggest move (one paragraph)
The vision synthesis should pick up the **canon/not-canon authority taxonomy as the enabling spine for a scheduled self-improving context loop** — taken as a unit, not split into a "lightweight check" cap. It is world-class because it is the one move that converts our context layer from prose-we-hope-is-right into a *falsifiable corpus a machine can certify and a worker agent can repair*: declare each artifact canon-or-not-canon, declare that canon is supposed to agree with itself, and you have manufactured an invariant — contradictions, broken references, and post-code-change staleness all become failing assertions that a cloud `/schedule` scanner can detect and a worker agent can fix via reviewed PR. This directly attacks our documented Phase-3 crux (the triple-duplication across memory stores that `/compound` currently dedupes by hand) and it generalizes across the 5+-repo fleet where context rot compounds independently and silently. Every other move in this source — the verifier, the push/pull discipline, the owner frontmatter — is an enforcement arm of this one cut, which is exactly why the conservative synthesis's instinct to cap it at "a doc that helps humans dedupe" suppressed the largest win on the table.
