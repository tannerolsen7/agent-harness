# Pass 2 — Penetrate: "12-Factor Agents"

Building on pass1: I take the pass-1 claims — F12-as-axiom, the corollary chain (F12→F1/F4/F6/F5), "F3 is the skill / model choice is a rounding error," "F8 = frameworks are evil," and the page's own self-application — and ask what is actually being assumed, what the load-bearing thesis really is beneath the 12-item list, where it contradicts itself, and what it silently takes for granted. The goal is to get past the listicle to the worldview.

## The real thesis (deeper than "12 principles")

Pass-1 records the surface framing ("engineering principles, not a framework"). The deeper thesis is narrower and more radical: **the LLM is not the system; the LLM is a single pure function inside a system you fully own.** Everything in the document is downstream of one move — *demoting the model from "the agent" to "the `determine_next_step` call."* Pass-1's F1 ("LLM = decision, code = action") and F8 ("keep if/else in your code") and the while-loop reference implementation are three statements of the same demotion. The 12 factors are not 12 ideas; they are 12 places where people accidentally let the model (or a framework wrapping it) reclaim authority the deterministic program should keep. Read this way, the document is a **boundary-policing manual**: it is obsessed with one boundary — the seam between "the part you wrote and can debug" and "the stochastic part."

## What the corollary chain actually buys, and what it smuggles

Pass-1 lists the derivations (F12→F6 "pause/resume is free"; F12→F5 "unified state is a prerequisite"). The hidden move is that **F12 is doing rhetorical work the engineering doesn't fully support.** "Stateless reducer" is true only at the granularity of *one step*: `determine_next_step(context) → action` is deterministic-ish. But the *agent* is emphatically not a pure function — it accretes context across iterations, and the model is not actually deterministic given identical context (temperature, sampling, model-version drift). So "test it like a function" is a useful discipline, not a literal property. The author conflates **"the step is a reducer"** (nearly true, very useful) with **"the agent is a reducer"** (false, but rhetorically load-bearing). Pass-1's F6 claim that pause/resume is "free" inherits this: serialization is free only if *all* state lives in the context window — which F5 then has to mandate precisely because it usually doesn't. So the chain is partly circular: F12 makes F6 free *only because* F5 forces the precondition that F12 assumed. The factors lean on each other; pulled apart, several are weaker than the page's "everything derives from F12" framing admits.

## The biggest hidden assumption: a single-loop, single-process agent

Pass-1 records F10 ("one agent, one job, hand off cleanly") and F11 ("trigger from anywhere") as peers. They are in tension, and the document never resolves it. The entire model assumes **one agent loop, one context window, one process** — that is what makes F12/F1/F4/F8 clean. But F10's "hand off cleanly to the next [agent]" and F11's "trigger from anywhere" describe a *multi-agent, multi-surface, orchestrated* world, which is exactly where the single-reducer abstraction breaks: hand-offs need shared state (whose context window?), and multi-surface triggers need a router/dispatcher that is itself a stateful controller the reducer model doesn't describe. The author treats orchestration as out of scope ("plumbing problem, not architecture" — pass-1 F11) precisely to keep the reducer abstraction intact. **The clean part of the model is the part that doesn't scale past one agent; the parts that do scale (F10 handoff, F11 triggers) are hand-waved.** This is the document's central blind spot.

## "Context engineering > model choice" — the assumption that ages

Pass-1's strongest opinion is F3: model choice is "almost a rounding error," context engineering is everything. This is true *at a fixed capability level* and was a defensible 2024–2025 stance. It quietly assumes **the model is a roughly fixed substrate you optimize around.** But the ground-truth map's own §9 (Model Capacity Audit) is built on the opposite premise: model upgrades (Sonnet 4.6 → Opus 4.8) *retire scaffolding* — i.e., capability change moves the optimum, sometimes deleting the very context-engineering you carefully built. So "context engineering dominates" and "re-audit your scaffolding on every model bump" are both true but in tension: the more the model improves, the more your hard-won context engineering becomes overhead rather than leverage. The article takes for granted that context-engineering investment compounds; in a fast-moving-capability regime it can *depreciate*. This is the single most important thing the article does not see, and it is exactly the axis our V2 effort cares about.

## F9 (errors as context) — a stance, not a free lunch

Pass-1 flags F9 as "a complete inversion of exception-handling instincts." The unexamined cost: **feeding raw errors back into context is itself a context-pollution and infinite-loop risk.** If a tool fails the same way three times and each failure is appended, you've spent budget teaching the model its own failure and invited a retry-loop with no circuit breaker. The author presents "error → context" as obviously superior to "error → throw," but the honest position is that it *moves* the problem from control flow into context engineering (F3) — you now need compaction, dedup, and a max-retry escape that the model can't be trusted to enforce on itself. The document's own F8 ("keep control flow in code") actually argues *against* a naive F9: the retry/give-up decision is control flow and belongs in deterministic code, not in the model's reasoning over accumulated error text. **F9 and F8 are in latent conflict and the article doesn't notice.**

## Internal contradiction: "own everything" vs. "small modular concepts into your existing product"

Pass-1 records both the anti-framework absolutism (F8: frameworks are "evil") and the pragmatic key quote ("take small modular concepts into your existing product, not adopt a framework wholesale"). These are sold as the same point but aren't. "Own your prompts/context/control-flow" is a maximalist build-it-yourself stance; "incorporate small modular concepts" is a minimalist incrementalism. The document never says *where* the line is — which parts you must own (it implies: all of them) vs. which framework pieces are safe to borrow. In practice every team uses *some* framework surface (an SDK, a tool-call parser, a harness like Claude Code). The article's rhetoric ("evil") would condemn the very harness it's being read inside. The usable version of the claim is narrower than the stated one: *own the seams you debug across* — prompts, context assembly, and the retry/branch decisions — and borrow the rest.

## What the author takes for granted

1. **That you are building the agent loop yourself.** The whole document assumes you own `determine_next_step`. A team operating *inside* a vendor harness (Claude Code, our case) doesn't own the loop — it owns skills, hooks, and context files that sit *on top of* someone else's reducer. Most of the factors then become "influence" not "own," which changes the advice materially. The page's own Pass-3 (pass-1) papers over this by mapping factors to skills/hooks as if they were the loop.
2. **That "the agent" is one thing.** No notion of a fleet, a queue, parallel worktrees, or sessions that outlive a single context window — all of which our harness has.
3. **That the prompt/context is the only authority surface.** No concept of *document authority levels* (canon vs not-canon, live doc vs stale spec). The page's Pass-3 (pass-1) correctly notes F3 maps to canon/not-canon, but the *article itself* has no theory of authority-within-context — it treats the context window as a flat bag whose only properties are order and compression. That flatness is a real gap when applied to a knowledge-doc harness.
4. **That determinism is achievable enough to "test like a function."** True for the parser, aspirational for the model.

## Net: what survives scrutiny

The durable core, after this pass: (a) **demote the model to a decision function and keep control flow, prompts, and state assembly in code you can debug** — this is genuinely load-bearing and correct; (b) **unify state (F5)** is the most concrete, least hand-wavy, most testable claim and the one with the clearest mapping to a real bug class; (c) **context engineering matters enormously (F3)** — true, with the depreciation caveat above. The weaker, more rhetorical layer: F12-as-grand-axiom (a useful discipline oversold as a property), the frameworks-are-evil absolutism (contradicted by the article's own pragmatic quote), and the silent assumption of a single-loop world that makes F10/F11 cheaper than they are. Pass-3 will hold our harness against the durable core, not the rhetoric.
