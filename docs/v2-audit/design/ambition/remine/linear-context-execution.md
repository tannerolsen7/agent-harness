# Ambition Re-mine — Linear: Context-to-Execution, Issue Tracking's End & Agent-Native Product Development

## What this source is (plain English, 2-3 sentences)

Linear's CEO (Karri Saarinen) argues that "issue tracking is dead" — but the deeper, more defensible thesis buried under that slogan is that the issue has been *promoted* from a coordination ticket into a **typed context object an agent executes against**. The source documents Linear's own end-to-end loop (Intercom feedback → Triage → PM synthesis → coding agent → Codex review → customer follow-up, with an agent at every seam and a human at every irreversible gate), and lands two structural ideas worth more than the product machinery: a **permanent accountability gate** (the human owns the merge regardless of who wrote the code, *because* accountability requires a human, not because the model is weak) and a **promotion ladder** (a one-off useful prompt → a saved team skill → "the floor rises" for everyone).

## The full-ambition moves this source teaches

### Move: The task object is a typed context container the agent executes against — promote it, don't fragment it

- **Plain-English what & why:** Linear has exactly ONE canonical object an agent reasons from — the issue. Description, labels, linked feedback, related code, history all hang on it, and Ramp's coding agent reaches 60% of merged PRs *because* it executes against that single structured object, not against a freeform Slack message. The failure this prevents: when "the task" is smeared across five half-objects (a TASKS.md line, a TASK-TEMPLATE file, an AGENTS.md open decision, a per-session ad-hoc prompt), the agent starts from a worse, inconsistent context every time and there is no single place to invest in making the spec better. pass-2 sharpens this: the real Linear lesson is the *opposite* of the slogan — invest HARDER in the structure of the one task object, but only in fields an agent actually reads at execution time.
- **The mechanism:** Converge our scattered task surfaces into one canonical, typed task object (call it the issue-equivalent) that every entry point — `/dev`, `/feature`, `/queue`, an autonomous trigger — populates and every agent reads at execution. Make `enforce-scope.sh`'s `## ALLOWED FILES` one field of that object, not its only structured field, and wire the *other* fields (success criteria, constraints, references) into a deterministic read at task-start so they aren't merely present-but-ignored.
- **Citation:** `[as-is §3a AGENTS.md "None open" contradiction; §5 TASK-TEMPLATE is one of several task surfaces, not the canonical one]` — confirmed fragmentation. pass-3 (b)(4).
- **Conservative disposition:** Scaled-down to §D smaller-gap and deferred. MASTER-FINDINGS §D folds it into "governance coherence (… fragmented task object) [C1-G10]." cluster-findings-1 G10 explicitly says: "Defer to the AGENTS.md cleanup already on the map." pass-3 echoed: "defer #1 (task-object coherence — gap b4) to the AGENTS.md 'None open' cleanup."
- **RE-JUDGMENT under the new charter:** ELEVATE. The conservative move treated "one canonical task object" as a *documentation tidy-up* (clean up the AGENTS.md "None open" contradiction). Under autonomy-is-first-class it is *structural and load-bearing*. A bug→PR front-door, a Slack/Linear summon, and a cloud `/schedule` run all need a single typed object to instantiate and hand to the agent — you cannot route "context to execution" without a canonical execution target. The fleet scale makes it worse, not better: parallel agents across 5+ repos each spinning up from a different partial task surface is exactly the fragmentation Linear's product erased for itself. This is not D-tier doc work; it is the *substrate* MOVE 1 (the trigger front-door) and MOVE 6 (the compounding loop) both write to and read from. Make it a first-class V2 schema decision: define the canonical task object, name its fields, and gate which fields are agent-read.

### Move: Name the accountability binding as a PERMANENT gate, distinct from deletable capability gates

- **Plain-English what & why:** Linear binds the irreversible act — the merge — to a human, and the issue "stays assigned to the human" no matter who wrote the code. The genuinely new content (pass-2 §4) is *why*: the gate is permanent because it tracks **accountability** (the ability to understand, explain, and own a decision), NOT because the current model is too weak. That distinction has teeth: it tells you which gates you may delete as models improve (capability proxies) and which you may *never* delete (accountability bindings). The failure it prevents: when you run the Opus-4.8 capacity re-audit (MOVE 4) and start pruning scaffold, an un-named accountability gate looks identical to a capability proxy and gets cut "because Opus doesn't need the training wheels" — re-introducing the exact PocketOS class of incident our §9 keeps verbatim.
- **The mechanism:** Add a short, canonical "accountability rationale" statement to the governance layer (CLAUDE.md or a named doc) that classifies every STOP / human gate as either *accountability-binding* (never deletable: the merge gate, the destructive-op denylist, the `.cr-ok→human` review checkpoint) or *capability-proxy* (deletable as models improve: STOP-AND-SURFACE breadth, option-count forcing). This is the written distinction §9's pre-authorized cut needs before it prunes.
- **Citation:** `[as-is §9 "STOP-AND-SURFACE breadth → narrow"; absent: no named accountability-rationale doc in §3a governance inventory]` — confirmed absence. pass-3 (b)(2).
- **Conservative disposition:** §D smaller-gap, "naming it is the remaining step." MASTER-FINDINGS §D: "governance coherence (accountability rationale …) [C1-G10]." cluster-findings-1 G10: "the destructive-op/merge gate is enforced but no file states *why* it is permanent." pass-1/pass-3 both call the delta "small."
- **RE-JUDGMENT under the new charter:** ELEVATE — not in size (it's still a one-paragraph doc) but in *priority and timing*. The conservative synthesis treated it as a cheap doc chore to fold in whenever. Under the new charter it is a **precondition for two of the largest moves**: MOVE 4 (the deletion engine that makes V2 smaller) and the autonomy front-door. Autonomy is precisely when this matters most — a bug→PR loop running unattended on cloud `/schedule` will *open* PRs but the accountability binding is what guarantees a human still owns every *merge*. Without the written keep/never-delete classification, the §9 re-audit on Opus 4.8 has no principled stop-line and will over-prune. This should be sequenced *ahead of* MOVE 4, not folded into miscellaneous coherence cleanup. The old "small delta" framing is conservative bias because it measured the artifact's size, not its blast radius.

### Move: Add a skill-promotion rung above per-task memory ("the floor rises")

- **Plain-English what & why:** When a Linear PM finds that "synthesize themes across a feature catchall" produces useful output, they save it as a *skill*; the next time the pattern appears, it is available to the whole team — the floor rises. The principle (pass-2 §6, the one net-new structural idea the page lands): there is a *lifecycle layer above per-task memory* for **repeated multi-step workflows**, distinct from facts. Our promotion ladder promotes *facts* (correction → memory.md → RECURRING-FINDINGS → PITFALLS) but dead-ends there — it has **no rung that promotes a repeated workflow into a named skill**. The failure this prevents: workflows that recur get crammed into the fact-stores (which is part of why memory.md + PITFALLS + auto-memory triple-duplicate), and a genuinely reusable multi-step process never gets codified, so every agent re-derives it.
- **The mechanism:** Add a skill-creation rung to the promotion pipeline: when `/compound` (or a periodic review) detects the same multi-step workflow across N sessions, it proposes promoting it to a named skill — *with a retirement rule baked in* (a skill unobserved for 90 days is flagged for collapse, per §9's ghost-rule doctrine). This is the workflow-shaped escape valve the fact-stores lack.
- **Citation:** `[as-is §4 promotion pipeline has no skill-creation step; §4 triple-duplication]` — confirmed structural shape. pass-3 (b)(1).
- **Conservative disposition:** §C deferred (hypothesis-gated). MASTER-FINDINGS §C: "Per-feature spec layer + skill-promotion rung [C1-G8] — real, but sequence after the memory model; must ship an independent review pass + retirement rule." cluster-findings-1 G8 bundles it with notion-spec's behavioral-contract layer and defers behind MOVE 3.
- **RE-JUDGMENT under the new charter:** ELEVATE, with the §9 retirement rule kept as a real constraint (not a reason to defer). The conservative reasoning — "sequence after the memory model" — is *partially* sound (the rung does write into the memory model, so MOVE 3 is a genuine dependency). But "defer" overshot. Under "clarity beats minimalism / more skills is fine when each earns its place," a mechanism that *manufactures new earned skills from observed repetition* is exactly the compounding self-improvement the new charter wants — it is a self-improving loop applied to the harness's own skill registry. At fleet scale this is where the real leverage is: a pattern discovered in repo A's `/compound` should become a skill available across all 5 repos via the plugin+marketplace distribution (MOVE 5). So the move should be **in-scope-now as a designed-in rung of the MOVE 3 memory model**, not a deferred §C item — it ships *with* MOVE 3, gated only by the retirement rule. The retirement rule is the UPHELD half: a skill rung without it imports the page's costless-codification blind spot (pass-2 §"takes for granted" #4: "the floor rises is costless" is false — every saved skill is a maintenance liability and a ghost-rule candidate).

### Move: Run the Design Challenge — audit whether structured spec quality actually predicts agent outcome

- **Plain-English what & why:** The page poses its own test: audit the last five compound/agent sessions, classify each *starting spec* as S (structured) / P (partial) / A (ad-hoc), correlate spec quality to outcome (merged cleanly / rework / abandoned), find the single most consequential missing field, and write the one rule that would most improve average spec quality. pass-2 §2 supplies the reason this matters: the page *asserts* "structure → agent quality" as causation when it is at most correlation (a disciplined team produces both good structure and good outcomes). The failure this prevents: we invest in richer task-object fields that *no agent actually reads* — the exact "capability proxy" trap §9 warns about — because we never measured whether structure drives outcome in *our* workflow or is just present.
- **The mechanism:** A one-time internal probe: instrument or hand-classify the last N `/compound` / `/dev` / `/queue` runs by starting-spec quality, correlate to merge/rework/abandon, and let the result *decide* which task-object fields earn a deterministic read at task-start (feeding the first move above). It is a measurement against our own history, not external research.
- **Citation:** `[as-is §9 is model-capacity audit only; absent: no spec-quality→outcome correlation recorded anywhere in the map]` — confirmed absence of a measurement. pass-3 (b)(3).
- **Conservative disposition:** Deferred as a "candidate probe." pass-3: "schedule the Design Challenge as an internal probe (gap b3) … logged as a candidate probe, not a research task." Not surfaced in MASTER-FINDINGS' six moves at all — it falls under the §G "bounded capability checks" spirit but is not even listed there.
- **RE-JUDGMENT under the new charter:** NEW (effectively summarized away — MASTER-FINDINGS never names it among the six moves or the seven capability checks). Recover it as a first-class candidate, but as the *empirical input to MOVE 6's measurement spine*, not a one-off curiosity. The new charter wants self-improving loops and measurement-driven design; MOVE 6 already says "the precondition both halves need is measurement." This Design Challenge is the *seed dataset* for that — the first concrete read of whether our spec structure earns its keep. At fleet scale it is also the only honest way to decide which task-object fields to make agent-read vs. drop (preventing the capability-proxy bloat the deletion engine MOVE 4 exists to kill). It is cheap, internal, and decision-bearing; "candidate probe, schedule it later" undersells it. Promote it to a near-term measurement task that *gates* the task-object field-design decision.

## Autonomy angle

This source is one of the strongest autonomy teachers in the corpus, and the conservative synthesis discounted exactly that. Linear's documented five-stage loop is **customer feedback → shipped feature → customer confirmation, with an agent at every stage except the human judgment gates** — pass-1 literally calls it "the AFK north star expressed as a product development workflow," "the most complete end-to-end loop in this research." Concretely it teaches:

- **Bug/feedback → PR, summoned from the inbox:** Linear Agent creates a scoped issue directly from the Intercom inbox (the CX manager "rarely adds anything"), Triage routes it, a coding agent is delegated within Linear, Codex reviews the PR, and the human approves the merge. This is a working **summon-from-an-external-surface → reviewed-PR** loop — exactly the bug→PR / Slack/Linear-summon front-door the conservative synthesis put in §C hypothesis-gated ("harness can build but can't be summoned" [C4-G6]). The new charter reverses that deferral; Linear is the ground-truth proof that the full loop is buildable and that the right shape keeps a human only at the irreversible gate.
- **The accountability binding is what makes autonomy SAFE:** the loop runs agents end-to-end *because* the merge stays human-owned. This is the conceptual partner to `disable-model-invocation:true` for side-effect skills — the autonomous loop can open the PR but never owns the merge. Naming the accountability gate (Move 2) is therefore a *prerequisite* for shipping autonomy, not a doc afterthought.
- **Self-improving loop:** the skill-promotion ladder (Move 3) is a self-improvement mechanism — observed repetition is automatically codified into reusable capability — which is precisely the "self-improving loops" the new charter names first-class.

No direct teaching on *cloud scheduling* specifically (Linear's loop is event-triggered from the inbox, not cron-scheduled), but the event-trigger front-door it demonstrates is the complement to cloud `/schedule`.

## The single biggest move (one paragraph)

**Name the accountability binding as a permanent gate, distinct from deletable capability gates — and do it BEFORE the Opus-4.8 deletion engine runs.** It is one paragraph of doctrine, but it is the load-bearing safety primitive that makes the entire autonomy agenda shippable: it is the written rule that lets a bug→PR loop run unattended on cloud `/schedule` while guaranteeing a human still owns every merge, and it is the only principled stop-line that keeps MOVE 4 (the deletion engine that makes V2 smaller) from over-pruning a safety gate as if it were a capability proxy — the exact PocketOS failure class. The conservative synthesis got the artifact size right (small) but the priority wrong (folded into miscellaneous §D coherence cleanup); under a charter where autonomy is first-class, this distinction is the hinge the whole "remove the scaffold, keep the safety" doctrine swings on, and it must be written down and classified before any aggressive cut or any autonomous loop goes live.
