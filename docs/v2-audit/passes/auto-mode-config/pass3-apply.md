## (b) REAL gaps — each cites a ground-truth section or confirmed absence

1. **THE config is in the file the classifier ignores. [confirmed absence + live-check — highest severity]** The article's single most important claim is that the classifier does **not** read `autoMode` from committed `.claude/settings.json`. Live verification: `claude auto-mode config` shows **defaults only** — environment reads `"Source control: The trusted repo and its remote(s) only (no additional orgs configured)"`, `"Trusted cloud buckets: None configured"`. The project's custom entries (tanner-dev, event-vendor, registry.npmjs) appear **0 times** in the effective config (`grep -c` → 0). And `~/.claude/settings.json` has **no `autoMode` key** (`jq 'has("autoMode")'` → `false`). So: the project built the right artifact and placed it in the one location the tool ignores. The overnight-/queue problem the article exists to solve is, on disk **right now, unsolved** — the classifier is running on bare defaults. This is a confirmed absence not captured anywhere in `CANONICAL-HARNESS-AS-IS.md` (the as-is map predates auto-mode entirely; `autoMode` appears in no §3 row). **V2 build item: move the validated `autoMode` block from project `.claude/settings.json` to `~/.claude/settings.json` (or test `.claude/settings.local.json` per the article's Open Q#1), then re-run `claude auto-mode config` until the custom entries appear in the effective output.** This is the actionable core of the entire article.

2. **No pre-flight verification mechanism exists — the article's own Design Challenge is unbuilt, and nothing on disk fills it.** [confirmed absence] `CANONICAL §3e` documents `session-start.sh` (does remote npm install) and `worktree-create.sh`, but there is **no hook or script that checks the effective `autoMode.environment` against a /queue destination manifest before a run.** Given gap (b)(1), this absence is *why the misconfiguration went unnoticed* — there's no gate that would have caught "custom entries not in effective config." **V2 build item: the pre-flight script the article specifies (parse `claude auto-mode config`, check destinations + `$defaults` presence, exit non-zero), wired as a /queue pre-run check.** Maps to `CANONICAL §5` (canon-only items to build) as a *new* row the map doesn't yet have.

3. **Defaults will over-block the project's normal migration / `src/data/` write path. [§9 + live-check — project-specific, under-weighted by the article]** The live default `soft_deny` includes "Production Deploy: …running production database migrations" and "Modify Shared Resources: …shared databases… Persistent changes to database records… without clear affirmative user consent." The project's own environment artifact declares "the Supabase project IS production; treat all Supabase mutations as production." With no staging/prod boundary to hand the classifier (a genuine infra fact, not a config oversight), the default classifier will read `supabase migration up` and `src/data/` writes during a /queue run as production mutation → soft-block → unattended stall. This is the inverse of the article's "extend, don't subtract" frame. It maps to `CANONICAL §9` (Model Capacity Audit, "If you can't name a failure mode the constraint prevents, it's overhead" — here the failure mode is real but the constraint catches *legitimate* work). **V2 decision item: the project needs either an explicit `allow` carve-out for CLI-driven migrations against the configured remote, or a real local/prod environment distinction the classifier can reason over — Open Question #3, unresolved, is on the project's critical path, not an edge case.**

4. **The autoMode artifact has no commit/review/sync home — structural conflict with the harness's distribution model.** [pass2 §C; `CANONICAL §0`, §8] The canon's binding V2 principle is "global, GitHub-hosted, bidirectional self-update" (`§0`). But auto-mode config is only honored user-level or in a *gitignored* local file (article §scope-hierarchy; Open Q#1). So the one safety policy that actually runs unattended is the one policy the harness **cannot commit, review, or distribute** the way it distributes CLAUDE.md/skills/hooks. `CANONICAL §8` already says the harness "has never been installed anywhere but event-vendor"; auto-mode makes that worse — even if you install the harness elsewhere, the autoMode block won't travel with the repo. **V2 decision item: either (a) accept user-level autoMode as un-synced per-machine setup and document it in the install procedure, or (b) build a `~/.claude/settings.json` autoMode generator the harness ships and the operator runs once per machine.** No row in the as-is map covers this because auto-mode isn't in the map.

5. **Delivery mechanism collides with the no-agent-edits-to-guard-files invariant.** [pass2 §F; live `permissions.deny` blocks `Write(/.claude/settings.json)` and `.../settings.local.json`; harness memory "No agent edits to guard files"] The article's workflow is "paste this block into your settings." But the project forbids the agent from writing settings files — they're NEEDS-HUMAN handoffs. (Notably, the *project* `autoMode` block was clearly human-pasted — which is also how it landed in the wrong file with no agent to run `auto-mode config` and catch it.) **V2 process item: the autoMode artifact must be surfaced as paste-ready NEEDS-HUMAN content for `~/.claude/settings.json`, and a human must run the two verification commands — the agent can prepare and check, not write.**
