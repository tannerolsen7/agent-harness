## 1. Declared System Architecture — The Four Layers

`[CANON-DECLARES]` (02 · The Four Layers): "Every AI-native engineering system has four compounding layers. Skip any one and you have AI assistance. Build all four and you have a system that gets better every PR."

| # | Layer | What it is (canon's words) | What implements it (documents/components named) |
|---|---|---|---|
| 1 | **Context** | "Context is the moat. Agents without opinionated context produce generic code." The codebase-specific rules are the moat; generic rules are table stakes. | `CONTEXT.md` (the *why*), `AGENTS.md` (the *what*), `PITFALLS.md` (codebase-specific traps), `docs/adr/` (ADRs), `docs/solutions/` (solved problems, generated by `/compound`), `docs/TESTING.md` (confirmed behaviors/spec), `.claude/memory.md` (corrected mistakes, read at session start), `.claude/INDEX.md` (annotated external resources). Build/maintain → "04 · Context Docs". |
| 2 | **Pipelines** | "Pipelines enforce taste automatically. If review depends on humans remembering to check things, it doesn't scale." | Tiered by scope (table below): Pre-commit hook, `@reviewer`, `/cr-security`, `/cr` (full). Plus the recurring-findings loop writing to `docs/RECURRING-FINDINGS.md`, and the compound step (`/compound`) after merge. Build → "05 · Pipeline Skills". |
| 3 | **Memory** | "Three distinct documents. Easy to conflate — don't." A pattern can flow through all three: session correction → repeatedly caught in review → codified so agents avoid it at write time. | `memory.md`, `RECURRING-FINDINGS.md`, `PITFALLS.md` (table below). Build → "07 · Memory System". |
| 4 | **Workflow** | "Clear inputs produce predictable outputs." | The task spec, the feature loop, the sub-agent contract, the retry policy. Build → "06 · Workflow Skills". |

### Layer 2 — Pipeline tiers `[CANON-DECLARES]` (02)

| Tier | When | Auto-fix |
|---|---|---|
| Pre-commit hook | Every commit | No — lint, tsc, vitest --changed |
| `@reviewer` | End of each feature task | No — surfaces only |
| `/cr-security` | Any auth/RLS/db-boundary change | Yes — Opus |
| `/cr` (full) | Pre-merge against full branch diff | Yes — Opus |

`[CANON-DECLARES]` (02): recurring-findings loop — "After synthesis, the pipeline writes to `docs/RECURRING-FINDINGS.md`. At threshold (≥3) or by judgment, findings are promoted to `PITFALLS.md`."

### Layer 3 — Memory documents `[CANON-DECLARES]` (02)

| Document | Source | Read by | Grows |
|---|---|---|---|
| `memory.md` | Human corrects agent in session | Every agent at session start | When mistakes are corrected |
| `RECURRING-FINDINGS.md` | Pipeline catches a finding repeatedly | Pipeline synthesis step only | Automatically on every pipeline run |
| `PITFALLS.md` | Promoted from findings, or added directly | Implementing agents before writing code | Via human-confirmed promotion |

### Layer 4 — Workflow components `[CANON-DECLARES]` (02)

- **The task spec** (fill before every agent task). Fields: `TASK, SUCCESS CRITERIA, SCOPE (in/out), CONSTRAINTS, OPEN QUESTIONS, REFERENCES, SIZE ESTIMATE, COMPOUND QUESTIONS, BRANCH`.
- **The feature loop** (canon's exact block):
  ```
  Size → /design [explore →] contract (Small+)
       → /grill-with-docs → TESTING.md spec
       → tracer bullet first → /tdd (slice by slice)
       → /simplify → @reviewer → /cr-security (if triggered)
       → compound questions → tsc → commit → /cr (pre-merge) → /compound → merge
  ```
- **The sub-agent contract.** Fields: `GOAL, SCOPE (hard boundary), DECISIONS ALREADY MADE, REFERENCES, TDD REQUIREMENT, PIPELINE REQUIREMENT, BRANCH, STOP AND SURFACE conditions, SUMMARY FORMAT`.
- **The retry policy for MUST FIX items:** Stage 1 — re-prompt original agent (one retry); Stage 2 — fresh agent, no parent context, diff + MUST FIX list (one attempt); Stage 3 — surface to user. Bypass immediately if: open decision touched, architectural redesign required, bug in pre-existing code, NEVER rule would be violated.

## 4. Setup Sequence / Decision Tree `[CANON-DECLARES]`

### 4a. Top-level decision tree (00 · Start Here)

- **Step 1** — "Are you starting fresh or inheriting an existing codebase?" (two branches below)
- **Step 2** — One-shot readiness checklist (run against any codebase before adding more context docs)
- **Step 3** — Stack translation (patterns universal, file names adapt)
- **Step 4** — "What stage are you at?" (stage ladder)

### 4b. Starting-fresh build order (00) `[CANON-DECLARES]`

> "Build in this order. Don't skip ahead — each step enables the next."

**Day 1 — Personal config (once ever, applies to all projects)**
1. Create `~/.claude/CLAUDE.md` — personal behavior config across all projects
2. Expand the allowlist in `.claude/settings.json`
3. Set up stop hook (see 08 · Settings & Permissions)

**Day 1 — Project foundation**
1. Create `CLAUDE.md` — process rules, NEVER list, destructive-op rules
2. Create `AGENTS.md` — product context, architecture, open decisions
3. Vendor the Pocock skills needed into `.claude/skills/<name>/` (committed copies — NOT a global install or `.agents/skills/` symlinks; symlink approach breaks across git worktrees). "For these services that's `tdd`, `grill-with-docs`, `prototype`, `improve-codebase-architecture`, `to-issues`." Pull upstream once with `npx skills@latest add mattpocock/skills`, then `cp -R ~/.agents/skills/<name> .claude/skills/<name>` for each, and commit.

**Day 1-2 — Domain context**
1. Run `/grill-with-docs` on the domain → builds `CONTEXT.md` through questioning
2. Create `docs/TESTING.md` — start with confirmed behaviors as discovered
3. Create `PITFALLS.md` (empty — grows over time)

**Day 2-3 — Pipeline**
1. Build the `@reviewer` agent (per-task review)
2. Build `/cr` (full) skill
3. Build `/cr-security` if auth/data access is involved
4. Wire `docs/RECURRING-FINDINGS.md` into `/cr` Step 3b

**Day 3+ — Workflow**
1. Build `/feature` skill
2. Build `/design` skill (runs before /feature for Small+ tasks)
3. Create `.claude/TASK-TEMPLATE.md`
4. Create `.claude/memory.md` — seed with destructive-op rules
5. Create `.claude/INDEX.md` — annotated external resources, project-specific

**Once features are shipping**
1. Create `docs/solutions/README.md`
2. Create `docs/solutions/TEMPLATE.md`
3. Build `/compound` skill
4. Build `.claude/agent-contract.md` once spawning sub-agents
5. Designate golden exemplars in `AGENTS.md`

### 4c. Inheriting-existing-codebase order (00) `[CANON-DECLARES]`

> "Don't add docs to a codebase with competing patterns — fix the patterns first."

- **Step 1** — Run the one-shot readiness checklist
- **Step 2** — Fix blockers in this order: (1) Competing patterns (Priority 1 tech debt) — consolidate before documenting; (2) Missing boundaries — define + enforce layer rules; (3) Missing context docs (CLAUDE.md, AGENTS.md, CONTEXT.md via /grill-with-docs); (4) Missing pipeline (@reviewer per-task, then /cr pre-merge); (5) Missing memory (memory.md, PITFALLS.md, RECURRING-FINDINGS.md)
- **Step 3** — Build forward: follow the "Starting fresh" order from Day 2-3

### 4d. "What to build first (by stage)" (03 · File Structure) `[CANON-DECLARES]`

**Stage 3 minimum (plan-first, PR-only review):** CLAUDE.md; AGENTS.md; CONTEXT.md (via /grill-with-docs); docs/TESTING.md; .claude/settings.json; the @reviewer agent.

**Add for Stage 4 (idea to PR):** PITFALLS.md; .claude/memory.md; /cr skill; /cr-security skill (if auth/data); docs/RECURRING-FINDINGS.md (wired into /cr); agent-contract.md; .claude/INDEX.md.

**Add when features are shipping regularly:** docs/solutions/ + /compound skill; docs/adr/ (created by /grill-with-docs when needed).

**Add when enabling agentic orchestration (/queue, parallel worktrees):** .claude/SOUL.md; TASKS.md; .claude/agentic-system-enabled (sentinel, empty); .claude/agents/; .claude/hooks/ (auto-loader, auditor, session-end); /queue skill + /setup skill.

## 5. "Every project needs its own X" — project-specific vs transferable `[CANON-DECLARES]`

**Lead banner of 00 · Start Here (verbatim):**
> "This guide was built from two real production codebases. The patterns transfer. The specific file names, stack references, and golden exemplars do not. Every project needs its own CONTEXT.md, its own PITFALLS.md, its own golden exemplars. This doc tells you what to build — you build it for your codebase."
