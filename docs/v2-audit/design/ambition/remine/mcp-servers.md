# Ambition Re-mine — MCP Servers: What They Actually Are, What It Takes to Build One, and When It's Worth It (2026)

## What this source is (plain English, 2-3 sentences)
This source demystifies the Model Context Protocol — an MCP server is a thin, standardized adapter that lets an AI agent *discover and call* your tools at runtime instead of a human pre-wiring the calls. Its real argument is an asymmetry: **consuming** MCP servers is high-leverage and low-cost, while **producing** one is a security liability gated behind validated demand, because the first server event-vendor would build (search clients + create/send proposal) fuses private PII, untrusted input, and external egress — the "lethal trifecta." The durable yield is two reusable instruments (a two-question add-an-MCP gate, and the trifecta as a design invariant), not the time-bound "don't build yet" verdict.

## The full-ambition moves this source teaches

### Move: A consumed-tool trifecta gate (Instrument B made structural)
- **Plain-English what & why:** The "lethal trifecta" (Simon Willison) says an agent becomes a data-exfiltration vector the moment it simultaneously holds three things: (1) access to private data, (2) exposure to untrusted/attacker-controllable content, and (3) the ability to send data out. There is *no universal fix* — you have to make sure no single agent holds all three legs at once. The failure it prevents: an agent reads a poisoned Notion page or scraped venue page (leg 2), that hidden instruction tells it to read a client's PII out of the prod database via Supabase MCP (leg 1), and exfiltrate it through any write/send tool (leg 3) — and the human approving tool calls never sees the instruction because it lives in data, not in the visible prompt.
- **The mechanism:** A structural check — not advisory prose — that fires whenever an agent/worktree's *active toolset* covers all three legs simultaneously. Concretely: tag every consumed MCP tool and every harness capability with which leg(s) it grants (Supabase MCP read = leg 1; web-fetch / chrome / Notion-fetch of third-party content = leg 2; Supabase `execute_sql` / Notion `create-page` / any egress = leg 3). A `block-dangerous-bash.sh`-class guard (the canon's "3rd structural guard," ABSENT on disk) or a session-start hook computes the union of legs the current agent holds and refuses / forces human confirmation when all three light up. This is the leg-split discipline the harness already half-owns via the Tier-0 prod-key firewall — generalized from "credentials" to "capabilities."
- **Citation:** Pass2 §2 (consume side needs the same trifecta audit the build side gets); Pass3 (b)1 ("No map section encodes a trifecta gate for consumed tools — Instrument B is **unencoded** [absent]… the single most actionable yield"). Ground-truth: map §3e "block-dangerous-bash.sh — 3rd structural guard, ABSENT on disk" (line 206); `.env.local` points at **production** Supabase so leg (1) is *always present* (settings line 14).
- **Conservative disposition:** §C deferred / partially §D. MASTER-FINDINGS treated Instrument B as a yield to "pursue… as the genuinely new control," but Pass 3 framed it as a single advisory "wiring-tweak" against §3e's advisory floor, explicitly noting it would be "one more advisory rule unless tied to the (absent) block-dangerous-bash.sh-style structural guard" — and then did not commit to building that guard.
- **RE-JUDGMENT under the new charter: ELEVATE.** This is the single biggest suppressed move and it should be **in-scope-now as a structural, deterministic guard**, not an advisory line in `.claude/mcp.md`. The conservative bias is twofold: (1) it accepted "overwhelmingly advisory" as the harness's resting state and proposed an advisory addition that inherits the same impotence; (2) it sized the risk for a single agent under human supervision. Under the new charter — parallel agent fleets across 5+ repos, bug→PR autonomy, cloud `/schedule` running unattended with no human watching each tool call — the trifecta is no longer a supervised-edge-case; it is the *governing safety invariant for autonomy itself*. An unattended scheduled agent that can read prod PII, fetch a web page, and open a PR/send a Slack message is the textbook trifecta with the human-in-the-loop removed. This move is exactly what makes autonomy *safe* (alongside `disable-model-invocation:true` for side-effect skills). It deserves: a capability-tagging schema for every MCP tool and skill, a structural session-start/pre-tool guard that computes leg-union, and integration with the `disable-model-invocation` mechanism so an autonomous side-effect skill (deploy, open-PR, send-Slack) is the *only* egress and is never co-resident in context with an untrusted-content reader. World-class, not minimal.

### Move: Tool/MCP descriptions as a reviewed, pinned, diffed surface (rug-pull + tool-poisoning defense)
- **Plain-English what & why:** The model picks which tool to call by reading the tool's *description* — so a description is executable surface area, not documentation. "Tool poisoning" hides malicious instructions inside a tool's description (the model sees them, the user does not); the Invariant Labs demo is an innocent `add(a,b)` whose docstring secretly tells the model to read a credentials file and exfiltrate it. A "rug pull" is when an approved third-party tool *silently changes* its description after you trusted it. The defense the article names: descriptions live in your repo and "fall under `/cr` like any other code," and you must **pin and diff** tool descriptions so a silent change is caught.
- **The mechanism:** (1) Add a `/cr` pass (or a dedicated micro-skill) that reviews MCP tool descriptions and skill `SKILL.md` description frontmatter for injection/poisoning — the canon's 9-pass `/cr` has no such pass. (2) Snapshot the descriptions of every *consumed* third-party MCP server (Supabase, Notion, Figma, Vercel, chrome-devtools) into a committed lockfile, and a session-start hook diffs live descriptions against the snapshot, flagging any drift as a potential rug-pull before the agent can act on it.
- **Citation:** Pass1 "Security surface" (tool poisoning, rug pulls — "pin and diff tool descriptions"); Pass1 "Application" (descriptions "fall under /cr like any other code"); Pass3 (b)3 ("Tool/MCP descriptions are not in /cr scope… no map process pins or diffs [absent]"). Ground-truth: map §3c `/cr` is 9 passes over the branch diff with no tool-description pass.
- **Conservative disposition:** §C deferred, scaled to low-urgency. Pass 3: "With no event-vendor-authored MCP server today this is low-urgency for *authored* tools, but it bites now for **consumed third-party MCP descriptions**." MASTER-FINDINGS folded it into the cautious bucket rather than electing the pin/diff mechanism.
- **RE-JUDGMENT under the new charter: ELEVATE.** The "low-urgency because we don't author tools" reasoning is conservative bias — the live exposure is the *consumed* third-party descriptions (Supabase/Notion/Figma/Vercel MCP), and those are exactly the rug-pull surface, updated by vendors outside our control, with no pin/diff today. At fleet scale across 5+ repos, an unattended agent acting on a silently-poisoned vendor tool description has no human to catch it. The pin-and-diff snapshot is cheap, deterministic, and self-contained — it earns its place. Build the description lockfile + session-start diff now, and add the `/cr` tool-poisoning pass. (Note: this pairs naturally with the SDK/package supply-chain gate below — same trust boundary, different artifact.)

### Move: The dev-agent-only MCP server (the build variant the article skipped, that its own framework rates best)
- **Plain-English what & why:** The article's whole build/no-build debate assumes "building = customer-facing" (customers driving the product from their own Claude/ChatGPT; an in-app assistant). It never asks the one question most relevant to a *harness*: should we build an MCP server whose *only* consumer is our own coding-agent fleet? That variant has a completely different trifecta profile — no customer egress, no client-PII-to-outside path — and it is precisely the case the article's own decision criteria ("a non-deterministic agent will actually consume this") rate *most* favorably, because the harness *is* a fleet of non-deterministic agents (`/queue`, sub-agents, background agents, 23 agents).
- **The mechanism:** Evaluate (and likely build, scoped tiny, local stdio) an internal MCP server exposing the harness's own intent-level capabilities to the agent fleet — e.g. a reusable tool layer over `src/data/` queries, or over the harness operations (worktree lifecycle, sentinel status, queue state) — so every agent surface (`/queue`, background, cloud `/schedule`) shares one auth/error/schema layer instead of each re-deriving relative-path imports and ad-hoc bash. Start local stdio, one or two high-value tools, human confirmation on any write, no external egress from the reader.
- **Citation:** Pass2 §5 (article "never considers an MCP server whose only consumer is the team's own coding agents"); Pass3 (c)3 ("It never considers a dev-agent-only MCP server — the variant its own criteria rate most favorably… the article's build/no-build framing is binary-customer-facing and skips the category most relevant to a *harness* audit"). Ground-truth: map §1, §3d (23 agents) — the fleet is a confirmed non-deterministic consumer.
- **Conservative disposition:** §F-adjacent / unsummarized. Pass 3 named it as a *weakness in the article's reasoning* but MASTER-FINDINGS did not carry it forward as a build candidate — the conservative synthesis inherited the article's "consume/defer building" verdict wholesale and never separated the customer-facing build (correctly deferred) from the dev-facing build (never evaluated).
- **RE-JUDGMENT under the new charter: NEW.** The conservative synthesis summarized this away by accepting the article's binary verdict. Recover it as a first-class candidate. The new charter's distribution model (plugin + marketplace + thin `/init` template) and the parallel-fleet-across-5+-repos scale are *exactly* the "many heterogeneous agent surfaces sharing one tool layer" condition the article says earns an MCP server. This is not a phantom — there is no internal MCP server on disk (Pass3 (a)2, [absent]). Caveat to keep it honest: a plain function-calling layer over `src/data/` may still be simpler than a full stdio server until a *second distinct agent surface* genuinely needs the shared layer — so the move is "**evaluate and de-defer**," with the trigger being the second cross-repo consumer, not "build unconditionally." But it must move from "never considered" to "actively on the table," which is a real elevation.

### Move: SDK / MCP-package supply-chain trust gate
- **Plain-English what & why:** The article's "the SDK does the protocol, you never hand-write JSON-RPC" reassurance hides an assumption: that the SDK and the MCP server packages are trusted. The same rug-pull / supply-chain risk the article raises for tool *descriptions* applies to the *packages themselves* — a compromised MCP SDK or server package is a direct path into every agent that loads it. The failure it prevents: a poisoned dependency update to a consumed MCP server (or its SDK) executing inside the agent's trust boundary.
- **The mechanism:** A real `dep-update` discipline for MCP packages specifically — but the canon's `dep-update` skill is an **empty stub on disk** ("canon documents it fully but disk never built it"). Build it: pin MCP SDK/server package versions, review changelogs/diffs on update with audit-depth scaled to the package's trust level (an MCP server that runs in-agent gets the deepest audit), tie it to the description-diff snapshot above.
- **Citation:** Pass2 §5 (the SDK/package trust surface the article omits); Pass3 (b)4 ("No SDK / MCP-package supply-chain trust gate… our update discipline for it is unbuilt [absent — dep-update SKILL.md]"). Ground-truth: map §6 "dep-update/ empty dir — canon documents it fully but disk never built it" (lines 164, 293); only `block-npm-install.sh` exists (asks before install).
- **Conservative disposition:** §C deferred / §D minor. Pass 3 listed it as a gap but MASTER-FINDINGS did not elevate building the stub; it sat behind the two headline instruments.
- **RE-JUDGMENT under the new charter: ELEVATE (moderate).** "Asks before install" is not a supply-chain gate — it gates *intent*, not *trust*. At fleet/autonomy scale where unattended scheduled agents may pull dependency updates, an unaudited MCP package update is an unguarded path into the agent's full credential surface. The fix is bounded (build the already-documented `dep-update` skill, scoped to MCP/SDK packages first) and complements the description-diff move at the same trust boundary. Not as large as the trifecta gate, but genuinely in-scope-now rather than deferred — its current "unbuilt stub" status is a hole, not a deliberate choice.

## Autonomy angle
This source does not directly teach bug→PR, Slack/Linear summon, self-improving loops, or cloud scheduling. **But it teaches the safety substrate that autonomy is built on**, and that is the load-bearing autonomy connection. The lethal-trifecta invariant *is* the constraint that decides whether an autonomous loop is safe: a bug→PR agent, a Slack-summoned agent, or a cloud-`/schedule`d agent each runs with the human-in-the-loop removed — which is precisely the condition the article warns turns "consuming is safe" into "consuming is an exfiltration vector," because the article's entire safety claim for the consume side secretly rested on human approval and a read-mostly posture (Pass2 §2). So the source's instruments translate directly into autonomy-enabling controls: (a) the consumed-tool trifecta gate is what lets an unattended agent hold private-data + untrusted-content + egress *only if* they are structurally split (use `disable-model-invocation:true` to make a side-effect skill the sole, isolated egress, never co-resident with an untrusted reader — the resolved-fact mechanism the charter already names); (b) the leg-split it describes ("no external egress from the same agent that reads private data") is the architecture for splitting a *reader* agent from a *sender/PR-opener* agent in an autonomous loop. The article frames these as reasons to *defer building*; under autonomy they become reasons to *build the gates first* so the autonomy is safe by construction.

## The single biggest move (one paragraph)
**Build the consumed-tool trifecta gate as a structural, deterministic guard — and make it the safety substrate for autonomy.** This is world-class because it attacks the harness's real, *live* exposure rather than the unbuilt customer-facing server the article spends most of its words on: `.env.local` points at production Supabase, so every agent with Supabase MCP already permanently holds leg (1) private-prod-data — the only question is whether legs (2) untrusted content and (3) egress are ever allowed to co-reside, and today nothing structural prevents it (the canon's `block-dangerous-bash.sh`-class guard is ABSENT on disk, and the enforcement floor is "overwhelmingly advisory"). The conservative synthesis correctly identified this as "the single most actionable yield" but then sized it as one more advisory line and accepted the advisory floor as fixed. Under the new charter the move is bigger on both axes: it must be *structural* (capability-tagging every MCP tool and skill by which trifecta leg it grants, a pre-tool/session-start guard computing the leg-union and refusing or hard-gating when all three light up), and it must be *the enabling control for autonomy* (an unattended bug→PR or cloud-scheduled agent is the trifecta with the human removed; the gate, paired with `disable-model-invocation:true` isolating side-effect skills as the sole egress, is what makes "summon from Slack, ship a reviewed PR while the laptop is closed" safe instead of an exfiltration loop). It is the one move that converts the article's defensive "consume carefully, defer building" posture into the offensive safety infrastructure a world-class autonomous fleet requires.
