Version 2 — the Review Pack

The whole converged plan in one place, plain words. Read top to bottom: what it is → how it works for every job → the quality bar → what we build now vs. later → the record of every decision. A staff engineer reviewed this before it reached you.
The whole thing in one breath. You have an AI helper ("the robot") that writes code. Version 2 makes it: safe (locks it can't switch off, since it runs on your laptop with nothing behind them), trustworthy (it can't forge a passing grade, and independent fresh-eyes attack every change), tasteful (the robot builds only from your design system so the UI stays world-class and never drifts into slop — you keep the brand taste and the final call; plus real UX and speed), self-improving (every lesson compounds), and lean (it leans on the model's own growing smarts instead of burning tokens on busywork). You start every job; the robot finishes it; it only stops to ask about the few things that are expensive to get wrong. And it's built to drop into all 5 of your projects, not just this one.
New here? Day 1 — your first feature in 5 steps.
  1. Open your terminal in the repo (or your Claude Code session).
  2. Just describe what you want, in plain language: "Add a date picker to the booking form." You don't memorize command names — the harness picks the right skill for you. (The /feature, /cr names you'll see below are those skills running, shown so you can see what happened — you rarely type them.)
  3. It stops and asks you to approve the data shape, the flow, and the look. Reply to approve.
  4. It builds, tests, and reviews — handing you a checklist + the exact commands to see it.
  5. It opens a pull request. You review and merge.
That's the whole loop. Everything below explains why each step is shaped this way. (New? Read "A few words first" + "Every kind of job"; "Every call you made" is a decision record you can skip.)

A few words first

  • The robot — the AI helper + all the rules around it (you call it "the harness").
  • A skill — a written playbook the robot follows, run by typing its name (/feature, /cr).
  • A helper (sub-agent) — a focused mini-robot spun up for one job with its own fresh view. The point of a separate helper is the fresh pair of eyes.
  • The locks — automatic safety rules the robot literally can't turn off.
  • The feature doc — one permanent page per feature: what it does + how to check it still works. The single source of truth everything ties to.
  • The design system — your set colors, spacing, type, and building-block components. The robot builds only from these. (If a project doesn't have one yet, building it is step zero — see the quality bar.)
  • Free linting — fixed computer checks (no AI, no tokens, can't be faked) that catch mechanical mistakes.
  • The bug-catch test — a pile of code changes with bugs deliberately hidden in them (real bugs that actually happened in your projects), used to measure how often the robot's reviewer catches them. That number is the catch-rate — the dial that lets us trust the reviewer and safely trim duplicate checks. (Different from "golden examples," which are the best examples of good code — same word "golden", totally different thing.)
  • PR (pull request) — a proposed change, packaged for you to review and merge.
  • Tokens — what each AI step costs to run (think: the meter). "Free" / "zero-token" = a plain computer check, no AI, no cost.
  • Red-team — a helper that actively tries to break in or break the code, instead of just reading it for problems.

How it works — every kind of job

Steps you do are green; stops where the robot must ask you are gold. The amount of checking scales to the risk of the change. Each job's "Under the hood" box shows the real skills + helpers it uses.

1 · A new feature

You run one command (/feature). → Before any code, the robot prepares — and an independent helper pokes holes in — three things, in order: (a) the data shape (the real tables/columns); (b) the UX — how it works: the steps a person takes, how few clicks, does it read clearly; (c) the UI — how it looks: a rough mockup built from your design system. (UX before UI — agree how it works before how it looks.) It lists open questions and may not answer them itself. → You approve the data shape, the flow, and the look. Coding can't start until you do. → It builds in small pieces, test-first, handling every data state (no data / some / lots / bad / loading). → The right-sized review runs. → A picture of the finished screen is attached. → Opens a PR. → You merge.
The stops fire only when they apply: no database → skip the data-shape stop; no screen → skip the UX/UI stops; a tiny change → straight to building. Everything the feature should do + how to verify lands in its feature doc (the hub).
Under the hood — /feature (one command; sizes the job) → /design (one pass: schema + data/API layer + front-end architecture together, judged for your stack) → an independent grill helper → @spec-writer (writes the testable behaviors) → @implementer (builds one piece at a time, test-first) → the right-sized review (/cr) → a design-review helper + @ux-reviewer only if there's a meaningful screen change. Gates: the un-fakeable test gate before merge; /cr-security + the red-team pass if it touches login/permissions/payments; the project's database-safety skill first if it touches the database.

2 · A bug

You report it. → The robot finds the true cause and writes a test that fails because of the bug. → If the fix needs a database-shape change, it stops and asks you first (job 5's rule). → Otherwise it fixes it. → Review runs. → PR. → You merge.
Under the hood — usually /incident first (what kind of problem is it?) → /debug (reproduce, find the true cause, write the failing test — it does NOT write the fix) → the fix then runs through the same right-sized build path as a feature. Helpers: @investigator (bugs spanning several files) · @reviewer + its 4 attack-lenses.

3 · Production is down (emergency)

"Checkout is broken!" → The robot decides up front: quick safe patch now, or full fix? → failing test → fix → review → PR → you merge, fast. → A quick patch logs a proper full fix as follow-up. → Afterward it writes up what happened.
Under the hood — /incident first, always (classify before touching anything) → /hotfix (controlled quick fix) or /migrate (if the damage is bad data, not code) → /post-mortem after. Helpers: @incident-responder (gathers evidence, never writes code) · @reviewer · @hotfix-guard (won't let it merge without a follow-up + a failing test).

4 · A security scare

A leaked key, a strange login, possible data exposure. → The robot isolates the affected area, LOGS everything into a triage packet (what it found, where, what's affected), and STOPS. It never guesses a fix. → Hands you the packet. → You decide the next move.
The one job where the robot's job is to not act — a wrong guess destroys evidence or widens the breach. (Automating the response is deliberately a future, high-caution item. Separate thing: security-sensitive code changes get a red-team pass — that's the "Secure" row in the quality bar, not this live-incident response.)
Under the hood — /incident (on a security signal: isolate + log + stop). Helper: @incident-responder (proposes the lock-down, never acts destructively).

5 · A database change

You ask. → The robot writes the exact change as a file you can read, applied nowhere. → You approve that exact data shape first. → It writes the tests for it. → It never touches any database — there's no practice copy, so the locks are what stop it. → PR → You merge, then you (not the robot) run the change against the real database yourself.
Under the hood — the project's database-safety skill first (here that's /supabase; a Firebase project would have its own — the robot reads the project's setup) → /migrate (plan, back up, dry-run, your sign-off) → /feature for the surrounding code. Helper: @security-reviewer if it touches permissions.

6 · Cleaning up messy code

You ask. → Plan first → moves code without changing what it does → keeps "moving" and "changing" in separate commits → refuses lazy names → review → PR → You merge.
Under the hood — /refactor (safety test first; structure and behavior never in the same commit) → /tdd first if there's no test yet. Helper: @refactor-extractor for big multi-file splits.

7 · A hard "what's the right approach?" question

You ask. → The robot researches, double-checks claims, and writes a recommendation with its reasoning + one test that would prove or kill it. → You decide. No code until you pick.
Under the hood — /spike, run by @spike-orchestrator coordinating a small fleet: @spike-researcher (gathers sources) · @spike-synthesis (writes the recommendation) · @spike-adversarial-verifier (attacks it) · @spike-user-verifier (what it costs you if it's wrong) · @spike-slice (the one proving test).

Keeping outside libraries up-to-date is done by hand for now — no finished tool for it yet (a small future build). Throughout: any job that needs you ends with a handoff block — a short checklist of what to do by hand + the exact commands (go to the right worktree, start the dev server, open any file it built) so you can keep going.

The quality bar — every front-end change clears all of this

What "world-class, no slop" actually means, made into checks rather than hopes. Each scales to the change's risk.

DimensionHow it's held
Correct & safeOne smart review pass (matches the plan, safe DB use, right place, real tests) + the mechanical checks done by free linting + 4 independent "attack" helpers that try to break it from fresh angles. One part is un-fakeable: your server already runs the tests on every change, and now the merge waits for that result and ties the "passed" mark to the exact final code — so the robot can't forge it (the existing run becomes the gate; it's not a second run). The review opinion is trusted because we measure its catch-rate, not because it can't be faked.
Tests that actually catch bugsTests are written test-first, then verified two ways: the "delete-the-code" check (if you removed the real code, would a test fail? if not, it's a fake test that just mirrors the code) and break-the-code testing (deliberately introduce a bug — a test must scream). A test-writer plus a test-checker.
Clean & readableWell-structured, well-named code does the explaining. Comments are earned — last resort, one line, and only the why when it's non-obvious, never the what. (Agents over-comment; the review flags it.)
SecureA security review on auth/permissions/payments/public changes, plus a red-team pass that actively tries to break in (only on those security-sensitive changes). A live security incident is handled differently — the robot isolates, logs, and hands off to you; it never auto-responds (job 4).
Well-designedA design step (one pass) designs the schema, the data/API layer, and the front-end component architecture together — using best practices judged for this project's stack, never cargo-culted. An independent helper grills it.
World-class UI (no slop)Prerequisite: a design system must exist — if a project doesn't have one, building it is step zero. Then: the robot may only build from it (colors/spacing/components) — never invent styles; a token check fails the commit on any off-system value, plus a zero-token slop detector (the impeccable tool) that catches AI "tells" (purple gradients, bad easing, tiny touch targets) for free; a design-review helper looks at the rendered screen only on meaningful UI changes (it's token-expensive); you approve the mockup. Every fix/approval feeds /compound so it improves every project. You keep the brand taste and the final call.
Easy to use (UX)A usability reviewer counts clicks/steps, walks the flow, and checks it reads clearly — measuring what a machine honestly can, and never faking human numbers (real "does a person get it" stays a real person). Click/step targets live in the feature doc.
AccessibleA hard accessibility gate (blocks the merge on real violations) + a name-the-buttons lint rule. Free.
All data statesEvery change handles no data · some · lots · bad data · loading — with no page shift. (Loading strategy is per-project: architect the spinner away, or a layout-stable skeleton.)
FastSpeed (load / layout-shift / snappiness) is measured and logged with a warning if a change blows its budget — not blocking. /perf fixes real slowness.

Simple & powerful — how it stays lean on tokens

All that quality could blow through tokens if every job fanned out into dozens of helpers. So the harness runs its own prune, on one rule:

Spin up a separate helper only when it buys something one pass can't: a fresh independent set of eyes (catches what the author can't), true parallel work (separate, unrelated items at once), or something too big to hold (want the conclusion, not the file-dump). Otherwise — one capable pass. Never split work the model can hold; never stuff it with context it can already figure out (that actually makes it worse and costs more).
  • Scale to the risk. Tiny change → almost no checking. Only auth/payments/database/public changes get the full battery. A simple risk-classifier picks the set — minimal is the default.
  • Measure, don't assume. Wherever we could fold many checks into one pass (the review's many checks; the design specialists), we don't just decide it — we measure it: run the split version vs. the combined version against the bug-catch test (real bugs hidden in code, which grows every time one slips past), and keep separate helpers exactly where they catch more. If one pass catches just as much, combine and save the tokens; if the split catches more, the extra tokens are buying real quality — keep it. (The 4 attack-helpers always stay separate — their fresh-eyes value can't be faked by one pass.) The mechanical checks leave the AI entirely either way — free linting does those.
  • Reviewers run on the strongest model. Folding checks into fewer passes is only safe if the one doing the checking is the most capable model.
  • Feed it the slice, not everything. Each helper gets the relevant section of the feature doc + the past lessons about the files it's touching — not the whole rulebook. (Safety rules are the one thing always loaded in full.)
  • Get leaner as the model grows. Re-run this prune whenever you upgrade the model — scaffolding the smarter model outgrew gets re-checked and trimmed. Every helper spin-up is logged so you can see the fan-out.
  • Can't silently skip a safety step. Since the robot picks which skill to run, a guard double-checks it: if a change touches the database / login / payments but the matching safety step didn't run, it's blocked. And when the robot's unsure how risky a change is, it assumes more risk (more checking), never less.
