## (b) REAL gaps it exposes (each cites a ground-truth row or confirmed absence)

1. **No eval/test doctrine for probabilistic harness output — and the harness IS now probabilistic.** Pass1 §Testing and §"20–30% of budget to evals" demand property-based assertions, golden sets, judge models, and evals-in-CI for any production LLM path. Our test doctrine is entirely deterministic: CLAUDE.md §Testing mandates Vitest unit tests, real-DB integration tests, "NEVER mock the database," "no snapshot tests" — all premised on exact-match correctness. The harness's *own* probabilistic outputs (the multi-pass `/cr` review, the 4 adversarial lenses, `/queue` batches) have **no eval harness, no golden set, no regression detection**. CI [map §3f: `ci.yml` + `integration.yml`] runs tsc/lint/vitest only — it never evaluates whether `/cr` still *catches what it used to catch* after a model change. This is a confirmed absence: there is no eval-in-CI store anywhere in the map (§3f scripts/CI lists none; §3b skills lists no eval skill; `evaluate-solution` is a solution-quality skill, not an LLM-regression eval). **This is the article's sharpest contribution to the V2 audit.** Maps to a §6-style "build-or-reject" decision on an evals-in-CI mechanism.

2. **The Model Capacity Audit [canon §9] has no regression backstop — exactly the silent-degradation failure pass1 §"cost of untested LLM behavior" warns about.** Canon §9 states its keep/replace judgments were made against **Sonnet 4.6** and are "due for re-audit on a model update → now Opus 4.8." The article's compounding-reliability and silent-regression arguments (pass1 §Testing, §Compounding reliability) give the *missing mechanism*: without behavioral probes / a golden set, a model swap can silently change what the harness's reasoning passes catch, and "you will not know until support tickets arrive." The map confirms the absence — §9 schedules a *manual* re-audit and names no automated probe. Gap: the re-audit is a one-time human pass, not a standing behavioral-probe suite. Cites [canon §9].

3. **Compounding-reliability math is unaccounted-for in our multi-pass / multi-agent chains.** Pass1 §"Compounding reliability" (0.9³ = 73%) is a *fact* about chained probabilistic steps. The map describes `/cr` as **9 passes + an adversarial review** [map §3c] and a **23-agent roster** with 4 lenses [map §3d], plus `/queue` running parallel worktrees. Each pass/agent is a probabilistic step. The map records **no per-pass deterministic validation gate** between passes and no measured reliability for the chain — and the *only* deterministic backstop the map identifies is the bash guards + `.cr-ok` chain, which both agree is "overwhelmingly advisory… no deterministic backstop for the bulk of skill bodies" [map §3e "Net enforcement picture"]. Gap: long probabilistic chains with advisory-only validation between steps. Cites [map §3c, §3d, §3e].

4. **The `/cr` pass-count contradiction is, in article terms, an untestable-spec defect.** Pass1 §Gate 6 ("if you cannot define what correct looks like… you cannot detect regressions"). The map shows **three sources giving three different `/cr` pass counts** (canon P1–P9 with P9 adversarial; disk 1–9 + Pass 11, no Pass 10; runtime "9 plus adversarial") and `/cr-security` at canon-2 vs disk-3 [map §3c]. You cannot build a behavioral probe for a review skill whose own contract is ambiguous about how many passes it runs. So gap #1's eval work is *blocked* until this is reconciled. Cites [map §3c, §7 item 5].

5. **No "fallback obligation" doctrine for harness LLM steps.** Pass1 §"The fallback obligation": every product-path LLM call must have a defined behavior on failure/low-confidence, designed *before* the call is added. Our pipeline has deterministic *gates* (hooks block bad commits) but the map records **no defined low-confidence/failure behavior for a reasoning pass itself** — e.g., what `/cr` does when a pass returns garbage, or what `/queue` does when an agent silently fails. The closest analog, background-agent silent failure, is a *known* hazard in our own memory ("background agents fail silently without pre-committed Bash patterns") yet the map shows the mitigation is "pre-commit the allowlist" [map §2; memory: background agent Bash permissions] — that prevents one failure cause, not a general low-confidence fallback. Confirmed absence: no fallback-behavior spec for reasoning steps anywhere in §3b/§3c. Cites [map §3c, §2].

## (c) Weaknesses in the article's OWN reasoning
- **Single-addressee blindness (pass2 §2).** The article never distinguishes LLM-as-product-feature from LLM-as-development-substrate, yet uses our repo as its worked example. Its cost/latency/margin gates (Gate 4/5, §Cost Model) are calibrated to per-end-user transactions and **do not transfer to a harness** — applying them literally to our audit would be a category error. A reader who didn't perform pass2's split would mis-import the 10%-of-revenue heuristic and 50–65% margin math into a context where there is no per-call revenue.
- **"Stop at first NO" oversimplifies its own gray areas (pass2 §3).** The gates pretend a binary static decision; §Gray-Areas and §80/20-routing concede it's continuous, volume-dependent, and usually hybrid. The decision-tree form is pedagogically clean but operationally misleading.
- **Gate 6 silently weakens from "verify correctness" to "verify well-formedness" exactly where value is highest (pass2 §6).** Structured-output validation tests that the call *ran*, not that the prose was *good*. The framework is most confident on verifiable tasks it tells you to avoid, and weakest on the judgment tasks it recommends.
- **Cited constants will rot (pass2 §4).** Gartner 28%, 50–65% margins, $300K crossover, 2–5 s E2E, 3–5x output multiplier are point-in-time/provider-specific. The map already warns about exactly this failure mode at the meta level: "the project audit artifact itself rots" [map Correction log]. Inheriting the article's numbers would repeat that.
- **Treats human review as free and reliable (pass2 §4, §"human-in-the-loop").** At our scale (parallel agents, `/queue`) the reviewer is the bottleneck and least-tested component — the article's safety net is the thing it never inspects.
