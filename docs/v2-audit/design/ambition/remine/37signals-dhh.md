# Ambition Re-mine — 37signals / DHH: Agent-Accessibility Architecture & the Skeptic's Conversion

## What this source is (plain English, 2-3 sentences)

DHH (37signals) went from "I type all my code, no AI" (July 2025) to "I barely write code by hand" (April 2026) — and the architecture he built to get there is the load-bearing lesson. Rather than baking AI features *into* Basecamp, 37signals made the product *operable by external agents* through three surfaces: a revamped **API**, a dedicated **CLI** for every product, and a public **Skills** library (`house-skills`) that teaches agents how to use the product. The deepest claim is that **CLI surface area determines how deeply an agent can autonomously operate a system** — because agents *chain CLIs across vendors* (detect a Sentry error → find the Basecamp thread → write a fix → open a PR → update Basecamp) with no human handoff. A secondary, explicitly "load-bearing" warning: agent velocity removes the friction that used to force a human to rest, so burnout becomes an architectural concern, not just a personal one.

## The full-ambition moves this source teaches

### Move: The cross-vendor CLI-chaining loop IS the autonomous bug→PR front-door

- **Plain-English what & why:** DHH's worked example is not a side-note — it is the entire autonomy thesis in one sentence: an agent *detects a Sentry error → looks up the related Basecamp thread → writes a fix → posts a PR → updates Basecamp*, all by chaining command-line tools owned by different vendors, with **no UI, no browser, no human handoff for the routine steps** (pass1 §3). The failure it prevents: an autonomous agent that can *think* but can't *act end-to-end* because every step boundary (issue tracker → repo → review → notify) requires a human to copy state across a UI. The whole point of a text-first, chainable surface is that the agent can compose the *entire* incident→resolution loop in one orchestration without ever stopping at a screen a human has to drive.
- **The mechanism:** This is the harness's autonomous front-door. Concretely for us: an agent triggered by a signal (Sentry/Linear/GitHub issue, or a Slack summon) runs a **chain** — pull the error + linked context, branch via `worktree-add.sh`, write the fix, run `/cr`, open the PR via `pr.sh`, post the result back to the trigger source. Every link in that chain must be a non-interactive command the agent can call without a human: that is exactly what `pr.sh`, `worktree-add.sh`, `gc.sh`, `test-local.sh` already are [GT §3f], but the *front* of the chain (signal-in: Sentry/Linear/issue → agent) and the *back* (notify-out: post status to Slack/Linear) are the missing links. The move is to build the chain as a first-class skill (a `/triage→fix→PR` or "summon" pipeline) and treat any UI-required step in it as a defect to eliminate.
- **Citation:** Confirmed absence. [GT §3f] inventories the *internal* chain links (`pr.sh`, `worktree-add.sh`, CI) but there is **no signal-in / notify-out mechanism anywhere** in the map — no row for "Sentry/Linear/issue → agent" ingress or "post result to Slack/Linear" egress. [GT §8] confirms "the harness has never been installed anywhere but event-vendor" and the autonomous trigger is unbuilt. The closest as-is artifact is `worktree-create.sh` (the prod-key firewall), which exists *because* unattended runs happen [GT §3e] — i.e. the unattended loop is real but has no front-door.
- **Conservative disposition:** **§E already-built, scaled down to "largely already done."** Pass 3(a) reads the headline as "CLI-first dev tooling is already our reality, not an aspiration… the agent already operates the project through Supabase CLI, git, npm, and `scripts/*`." It collapses DHH's *cross-vendor autonomous chain* down to "we already have disk scripts" and never registers that the Sentry→Basecamp→PR→update example is a *trigger-to-resolution loop*, not a pile of scripts. The bug→PR front-door was explicitly deferred in the conservative charter (§C "DEFERRED").
- **RE-JUDGMENT under the new charter: ELEVATE — by a very large margin.** This is the single most consequential misread in the conservative pass. Having `pr.sh` on disk is *not* having DHH's chain — it is having *one link* of it. The new charter makes "bug → reviewed PR, summoned from Slack/Linear" first-class and never-deferred, and **this source is the cleanest articulation in the entire corpus of what that loop physically is**: a chain of non-interactive commands spanning the issue tracker, the repo, the reviewer, and the notification surface. The old reasoning was conservative bias of the purest kind — "we have the parts" mistaken for "we have the machine." How much bigger: from "already done, no action" to a **named V2 build** — the autonomous chain skill (signal-in → worktree → fix → `/cr` → `pr.sh` → notify-out), with the *cloud `/schedule`* (resolved-fact: runs on Anthropic infra, clones the repo, runs committed skills, calls connectors) as the durable executor. The restricted-network caveat of cloud `/schedule` even *reinforces* DHH's point: a text/CLI surface that works "in any shell without a running MCP host" (pass2 §C) is exactly what survives a restricted-network scheduled run where local MCP servers are unavailable.

### Move: Build the accessibility-tier map — but as the autonomy gap-finder, not a one-page audit

- **Plain-English what & why:** DHH's Design Challenge (pass1 §8) is to classify *every* operation the agent performs into a tier — **CLI-accessible / API-accessible / UI-required / not-possible** — because the UI-required and not-possible steps are the exact points where an unattended run stalls and silently waits for a human who isn't there. The failure it prevents: you launch a fleet of overnight agents, and one of them hits a step that needs a browser click or a manual confirmation, and the whole run hangs or fails with no signal. The map tells you, *before* you run unattended, every place the autonomy breaks.
- **The mechanism:** A living classification (not a doc that rots — see the map's own correction log, [GT lines 19-28], where the project audit artifact itself went stale) of every operation in the agent's loop: deploy, migrate, seed, env-rotate, screenshot-verify, Notion/Linear sync, Supabase dashboard ops, Vercel ops. Each row tagged CLI / MCP / UI-required / not-possible, with the UI-required rows becoming a **backlog of autonomy defects** to convert to CLI or MCP. This is the gap-finder that *feeds* the chaining move above — you can't chain a step that's UI-only.
- **Citation:** Confirmed absence. [GT §3a–§3f] inventory skills/agents/hooks/scripts/memory but contain **no operation-by-accessibility classification** — "there is no row that says 'operation X still requires a browser/human'" (pass3 §b1, verified against the map).
- **Conservative disposition:** **§D minor / fully-applied but shrunk.** Pass 3(b)(1) accepts this as a real gap but caps it hard: "Low-cost, diagnostic-only — fits pass2 §F1 exactly (a map, not a mandate to build CLIs)." The MASTER bottom-line frames it as "a one-time accessibility-tier audit… as a diagnostic." The word "one-time" is the tell.
- **RE-JUDGMENT under the new charter: ELEVATE (moderately).** The diagnostic framing is right but the "one-time / diagnostic-only / not a mandate to build" ceiling is conservative bias. Under autonomy-first + parallel fleets across 5+ repos, this is not a one-time audit — it is a **standing autonomy-readiness gate**: every UI-required row is a place a scheduled/summoned run breaks, and the map should *drive build work* to eliminate those rows (convert UI-required → CLI/MCP), not just describe them. How much bigger: from "write the audit once" to "a maintained tier registry whose UI-required rows are a tracked backlog of autonomy defects, re-run per repo at install time." The conservative pass shrank it to a diagnostic precisely because the old charter had no autonomous loop for the diagnostic to serve; now it does.

### Move: Selective friction removal — encode a hard stop into the autonomous loop (the burnout warning, inverted for agents)

- **Plain-English what & why:** DHH's burnout warning (pass1 §5) and pass2's penetration of it (pass2 §D) together produce the source's most original idea: **friction is not monotonically bad.** Some friction *gates action* (the API was "cumbersome, slow, expensive" — kill that). Other friction *gates pace/commitment* (the blocker that forces a human to rest, the natural stopping point) — **that friction is load-bearing and must be deliberately re-introduced once action-friction is gone.** For a *human*, the failure is burnout. For an *autonomous agent fleet*, the inverted failure is worse and concrete: an agent that never hits a natural stopping point will keep "steering" — keep committing, keep widening scope, keep spending tokens and touching prod — with no built-in commitment checkpoint. The friction that used to stop a tired human is exactly the friction a runaway autonomous loop lacks.
- **The mechanism:** Two things. (1) For the human: the `session-end.sh` Stop hook [GT §3e, §5] gets a *second* job beyond memory-capture — an explicit "this is a stopping point" signal (compound questions answered, changelog written, TASKS.md updated). (2) **The genuinely new, autonomy-relevant half:** a *commitment-friction gate inside the unattended loop itself* — a bounded budget per autonomous run (max commits / max files touched / max scope before it must stop and surface, not silently continue). This is the agent analogue of "the blocker that forces rest": a deliberate stopping point the loop cannot remove from itself.
- **Citation:** Confirmed absence. [GT §3e] records `session-end.sh` as **canon-declared, ABSENT on disk** ("disk's memory is fully manual"); [GT §5] lists it as a build-or-reject item — but *only* with a memory-capture rationale. There is **no run-budget / commitment-gate mechanism anywhere** in the map for the unattended path; [GT §3e net-picture] confirms enforcement is "overwhelmingly advisory… no deterministic backstop." [GT §9] golden rule ("name a failure mode the constraint prevents, or it's overhead") is the exact lens that *validates* a pace-gate: the failure mode is a runaway unattended loop.
- **Conservative disposition:** **§C deferred, then narrowed to "a second reason for an existing slot."** Pass 3(b)(2) calls this "the article's single best contribution: a rationale for [GT §5] `session-end.sh` beyond memory-capture." But it explicitly confines it to the *human session-end* slot and never extends it to the autonomous loop — because the conservative charter treated the unattended path as an edge case, not the north star.
- **RE-JUDGMENT under the new charter: ELEVATE — and split into two, one of which is NEW.** The human-session half (a stopping-point reason for `session-end.sh`) is correctly identified and should be built. But the conservative pass *missed* the bigger half entirely because it had no autonomous loop to apply it to: **a self-imposed commitment-friction budget inside the unattended/scheduled run.** Under autonomy-first, an agent that "removes blockers so it keeps steering" (pass1 §5) is not a burnout metaphor — it is a literal description of a runaway scheduled agent, and it directly threatens the Tier-0 prod firewall's intent [GT §3e, §6]. How much bigger: from "give `session-end.sh` a second sentence of rationale" to "build a run-budget / scope-cap stop condition into the autonomous executor, citing [GT §9]'s golden rule (the failure mode it prevents: an unbounded unattended loop)." This is the source's most under-rated gift to a *fleet* operator.

### Move: Resolve CLI-vs-MCP as a deliberate tool-surface doctrine, not an accident

- **Plain-English what & why:** Pass 2 §C found the article's deepest hole: DHH universalizes "CLI determines agent depth" while never weighing **MCP** — the *other* answer to the same problem (a typed, discoverable, per-call-permissioned tool surface). For a harness this is not academic. The two surfaces have opposite safety properties: a **CLI hides inside one allowed `bash` pattern** and is invisible to the per-tool permission gate, whereas an **MCP tool is gated per-call** by `permissions.allow`. The failure it prevents: blindly following DHH's CLI-evangelism would *widen the ungated surface* an autonomous agent runs against prod — exactly the risk the firewall exists to contain. The world-class move is to decide *per operation* which surface to use, on stated criteria, rather than defaulting to CLI by fashion.
- **The mechanism:** A short doctrine (a few lines in the agent contract / a decision rule the tier-map applies): **CLI when** the value is cross-vendor chaining in one bash call, plain-text inspectability/logging, or working without a running MCP host (the cloud-`/schedule` restricted-network case favors CLI); **MCP when** the value is typed schemas, discoverability, or — critically — **per-call permissioning for any operation that touches prod or is destructive**. Pair any CLI-first expansion with the missing `block-dangerous-bash.sh` guard so the ungated bash surface has a deterministic backstop.
- **Citation:** Verifiable from this session's own MCP surface (Notion/Supabase/Vercel/Figma MCP tools, gated via `permissions.allow` [GT §2]). The backstop dependency is a confirmed absence: `block-dangerous-bash.sh` is **canon's 3rd guard, ABSENT on disk** [GT §3e, §5].
- **Conservative disposition:** **§C deferred — explicitly punted.** Pass 3(d): "The one narrow, bounded lookup that could pay off is CLI-vs-MCP… but only if V2 actually proposes expanding the agent's tool surface… should be deferred until a concrete proposal needs it. Default: synthesize; trigger external lookup only on a live CLI-vs-MCP build decision."
- **RE-JUDGMENT under the new charter: ELEVATE — the trigger condition is now met.** The conservative pass deferred this because, under the old charter, V2 wasn't expanding the tool surface. Under the new charter, **the autonomous chain (Move 1) IS a concrete proposal to expand the agent's tool surface** — signal-in/notify-out, more chained ops — so the deferral's own precondition ("only if V2 actually proposes expanding the surface") is satisfied. This is no longer a someday-lookup; it is a doctrine V2 needs *now* to decide each new chain link's surface, and to pair CLI expansion with the absent bash guard [GT §5]. The safety stakes (ungated CLI vs gated MCP against prod) make it world-class-relevant, not academic.

## Autonomy angle

This source is **directly and richly about autonomy** — more so than the conservative synthesis admitted. The Sentry→Basecamp-thread→fix→PR→update chain (pass1 §3) is the canonical **bug→PR loop**, expressed as cross-vendor CLI orchestration with no human handoff. It maps one-to-one onto the new charter's "bug → reviewed PR, summoned from Slack/Linear": signal-in (Sentry/issue), self-driven fix + `/cr`, PR via `pr.sh`, notify-out (the "update Basecamp" step). It also teaches a **self-improving / sustainable-loop** discipline via the inverted burnout warning — a commitment-friction stop condition the autonomous loop cannot remove from itself, which is precisely what keeps a *self-improving* loop from becoming a runaway one. And the CLI-vs-MCP analysis is autonomy-critical for **cloud scheduling**: a text/CLI surface "works in any shell without a running MCP host" (pass2 §C), which is exactly the restricted-network, no-local-MCP environment cloud `/schedule` runs in (resolved fact). On Slack/Linear summon specifically: the source teaches the *shape* of the loop (chain across vendor tools) but not the summon ingress itself — that's the confirmed-absent front-door this source most strongly motivates building.

## The single biggest move (one paragraph)

**Build DHH's cross-vendor chain as the harness's autonomous front-door — and stop pretending `pr.sh` on disk already is it.** The conservative synthesis's worst error was reading "CLI-first dev tooling is already our reality" and closing the case; what 37signals actually teaches is that the *chain* — signal-in (Sentry/Linear/issue) → worktree → fix → `/cr` → `pr.sh` → notify-out — is the machine, and we have only the middle links. This is the cleanest concrete description of bug→PR in the entire 37-source corpus, it is exactly the new charter's never-deferred north star, and the resolved fact that cloud `/schedule` runs committed skills on Anthropic infra with a restricted network makes a *text/CLI-first chain* (which survives without a local MCP host) the right executor for it. Pick this up first: name the autonomous-chain skill as a V2 build, treat every UI-required step in it as a defect (Move 2's tier-map finds them), bound it with a commitment-friction stop (Move 3), and decide each link's surface CLI-vs-MCP on stated safety criteria (Move 4). The other three moves are the scaffolding that makes this one safe and complete.
