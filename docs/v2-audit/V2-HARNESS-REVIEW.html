The V2 Agent Harness — a plain guide you can teach from

Rewritten to be simple. Short sentences. No jargon — every special word is explained the first time it shows up, and there's a word-list in section 1. If you can read this once and then explain it to someone else, it did its job. (Nothing here is built yet — this is the plan, and it folds in your latest notes.)
The whole thing in one breath. A general AI can write code, but it doesn't know your rules or your codebase. The "harness" is the setup that turns it into your trained engineer: a rulebook it reads, safety locks on the dangerous tools, an inspector that checks its work, and a notebook where lessons get written down. Today (V1) you have the rulebook and the inspector — but you still have to hand the AI every job and watch it work. V2 lets a request from Slack, Linear, or your issue tracker start the work on its own, keeps the safety locks on so it's safe to walk away, makes the inspector's sign-off impossible to fake, and writes every lesson into the notebook so the next job is better — across all your projects, on GitHub or GitLab. And it tells you what it's doing the whole time.

0 · The one big idea

Picture hiring a brilliant contractor for your house. They can build anything — but they don't know your house rules, which walls are load-bearing, or where the water shutoff is. So you give them four things:

  • A rulebook — "we use these materials, we never touch that wall, here's how we like things done."
  • Safety locks on the dangerous tools — so even a tired worker can't cut the wrong pipe.
  • An inspector who checks every job before it's called done.
  • A notebook — every mistake gets written down so it never happens again.

That bundle is the harness. The AI is the contractor; the harness is everything that makes the contractor safe and reliable in your house.

The one problem V2 fixes

Right now (V1), you still have to walk the contractor to each job and watch them the whole time. You start every task. You notice every bug. You wait while they work. That makes you the bottleneck — and it doesn't matter how many contractors you can afford if you're the only one who can hand out work and check it.

V2 builds the missing piece: a way for the work to start itself (you file a request, the contractor gets to it), the locks to make it safe to leave them alone, an inspector sign-off you can't fake, and a notebook that actually teaches the next job. You go from "do this, now do this, now do this" to "here's the problem — show me the finished proposal."

The test for this whole document: after reading, you should be able to say this and mean it — "V1 has all the parts but no engine: a human starts every job, watches it, and the 'it passed review' stamp can be faked. V2 adds the engine (a request starts the work), the safety locks that make running it alone safe, an inspector stamp nobody can fake, the notebook that makes it smarter each time, and a way to ship all of that to every project — and you can watch it the whole way."

1 · The words you need (read once, refer back)

Eleven words show up a lot. Here they are in plain language. After this, the rest of the page avoids jargon or re-explains as it goes.

Harness — your .claude/ folder and a few rule files. The whole "make the AI safe and reliable for us" setup.
Skill — a saved routine the AI runs when you type a slash word. /cr = "review my code." /feature = "build this feature."
Helper agent — a focused sub-worker the main AI hires for one job (a reviewer, an investigator).
Auto-check (a "hook") — a small script the system runs automatically at a fixed moment, and the AI cannot skip it. Like a spell-checker that runs every time you hit save.
Scratch copy (a "worktree") — a separate copy of the code the AI works in, so it can never mess up your main copy.
Pull/merge request (PR/MR) — the "please add my change" proposal that gets reviewed before it joins the real code. GitHub calls it a pull request; GitLab calls it a merge request. Same thing.
CI — the robot on a server that automatically runs your tests every time the code changes. It's the same on GitHub and GitLab.
Production (or "prod") — the real, live system your real customers use. The opposite of a practice copy.
The floor — the safety rules that are enforced by code, not by politely asking the AI. The AI literally can't get past them.
The loop — the AI finding its own work and finishing it without you starting each step.
Spec — a short, plain write-up of what a feature should do and how you'll know it works. The target you aim at before writing code.

2 · Story: someone wants a new feature

This is the clearest way to understand V2 — watch it happen. You asked: how does someone submit a feature, and how do we make sure it's properly spec'd so the code is world-class? Here's the flow.

  1. A person writes a request where they already work: a message in Slack ("we need a 'duplicate proposal' button"), a Linear ticket, or an issue in the repo. All three are equal front doors — no special place to go.
  2. The harness picks it up and does the most important step first: it writes a short spec — what the feature should do, who uses it, and a checklist of "it works if…" lines. It does not start coding yet.
  3. It posts the spec back to the same Slack thread / ticket and asks you to confirm it. This is the gate that makes the code world-class: you can't build the right thing if nobody wrote down what "right" is. If the request was vague, this is where the AI asks its questions.
  4. You approve the spec (or fix it). Now there's a clear target.
  5. The AI builds it in a scratch copy — tests first (see section 9 for why that matters), then the code, in small steps.
  6. The inspector runs (/cr, the deep review — section 8) and fixes its own small mistakes.
  7. It opens a pull/merge request with a tidy summary: the problem, what it did, the tests, and how much could break. You review and merge.
Why this is the world-class part The order is the point: spec → your OK → code. Most AI coding skips straight to code, so you get something that runs but isn't what you meant. V2 forces a written, confirmed target first — that's the single biggest lever for "the code is actually good," and it's a human decision point on purpose. Honest detail: this "write the spec, get your OK" step kicks in for real features. For a tiny one-line tweak, the "spec" is just the failing test — a full write-up isn't worth it. So spec-first is the rule for anything non-trivial, not a tax on every change.

3 · Story: someone found a bug

You asked: how does a bug get submitted and kicked off, so it's reviewed at PR time — or earlier, if a human decision is needed? Two ways a bug arrives, and a key "stop early" path.

  1. A bug is reported from Slack, Linear, or an issue ("the total is wrong when there's a discount") — or the tests on the server go red on their own and the harness notices.
  2. The harness investigates in a scratch copy until it finds the real cause (not a guess), and writes a test that fails because of the bug. A failing test is proof it actually found the problem.
  3. The early-stop check: if fixing this means touching login/permissions or the shape of the database, the AI stops here and asks you first, before writing any fix. (Those two early stops are real today; money math currently gets its extra-careful check at review time instead — section 9 — and adding an early stop for it too is on the list.) This is the "reviewed earlier if a human decision is needed" path. You don't want an AI quietly redesigning your pricing rules at 2am.
  4. Otherwise it writes the fix, the failing test now passes, the inspector reviews it.
  5. It opens a PR/MR that shows the bug, the cause, the fix, and the test that now guards against it. You review and merge.
There are two places a human can catch a problem, not one: early (before coding, when the change is risky) and at the PR/MR (when it's done). The early stop is the cheaper, safer catch — it's much easier to redirect a plan than to unwind a finished change.

4 · Four more stories (the other ways it's used)

Production is down (an incident)

"Checkout is broken!" in Slack starts the urgent path. The harness picks one of two modes up front — a fast safe patch, or a full fix — writes a failing test, and a special guard double-checks before it merges. If it smells like a security problem, it isolates and stops instead of trying to fix — because the wrong "fix" to a security hole can make it worse.

"This file is a mess, clean it up" (a refactor)

The AI splits a big file safely: it writes down a plan first (so a crash mid-way doesn't lose its place), moves code without changing behavior, and refuses lazy names like "utils" or "misc." Structure changes and behavior changes are kept in separate steps, so review is easy.

"Keep our libraries up to date" (dependency bumps)

On a schedule, the AI reads what changed, makes the safe small updates into a PR/MR, and asks a human for the big risky ones. Replaces today's empty placeholder that does nothing.

"Find work nobody asked for yet" (scheduled discovery)

On a clock (even with your laptop closed — see section 11), the AI looks for trouble: rules that drifted out of date, the same bug reported three times, a slow page. It turns each find into one tidy PR/MR — never a dump of 30 raw to-dos a human has to sort.

5 · What writing these stories taught us

Writing real flows is half the value — it exposes what's missing. Five honest lessons:

  1. The spec-first gate is the whole ballgame for quality. Without "write it down and confirm it," the AI builds something that runs but isn't what you meant. This gate is now a required step in the feature flow, not a nice-to-have.
  2. "Stop and ask early" is as important as the final review. The most valuable human catch happens before coding, on risky changes. We made that an explicit, named stop.
  3. Every front door should produce the same shape. A Slack message, a Linear ticket, and an issue are different on the outside but should turn into one standard "work order" inside, or the parts downstream get messy. Today there is no such front-door router — the part that reads a request and sends it to the right place is one of the new pieces V2 builds, and it's what actually makes Slack and Linear first-class doors (not just talk).
  4. Some triggers are bugs, some are features — route accordingly. A failing test or a "fix-me" label is usually an incident, not a new feature, and should go down the incident path. We made the front door choose the right path.
  5. The "find work on a schedule" story only works if the clock is real. That pushed us to use the built-in cloud scheduler (section 11), not a timer that only runs while your laptop is open.

7 · The safety locks (what makes "leave it alone" safe)

This is the heart of "is it safe to run by itself?" There are two parts, in order: first take away the danger, then lock down what's left.

Part 1 — the cheapest safety trick: give it a practice copy

The most powerful safety move isn't a lock at all. It's this: don't let the AI touch your real, live system in the first place.

Right now, when the AI works, it can reach your real database — the one with real customer data. Because it can touch the real thing, we have to pile on locks to stop it from doing harm.

The simpler idea: give each job its own throwaway practice copy — a fresh database with no real data, no real passwords, and no way out to the internet. Now there's nothing dangerous for it to touch, so most of the locks stop being must-haves. And anything the AI tries to send out — an email, a Slack message, a deploy — gets caught in a list a person checks first, instead of actually happening.

It's the difference between handing a new worker the keys to the real bank vault and watching them like a hawk, versus giving them a practice room with play money. The practice room is simpler and safer. This is now part of the V2 plan (it came out of the "background agents" article you had us study). The one thing to check before building it: can we spin up a fresh practice database fast enough for each job? — a small build question, not a big decision.

Part 2 — the locks that stay on anyway

Even with a practice copy, a few locks stay on — belt and suspenders. The trick V2 gets right: the must-have list is short, not giant. A request can't start a job until these are in place.

The 5 must-have locks
  1. Block the dangerous commands. No deleting production data, no wiping folders, no deploying — these are stopped before they run. (And if the lock itself can't run for some reason, it blocks rather than letting things through.)
  2. Hide the real keys. An automatic run is refused if it can see the real production database keys. (Today, a misread setting can hand the AI the live keys — the #1 way real incidents happened, where the AI didn't even need a clever trick to leak them.)
  3. The un-fakeable review stamp. The server re-runs the checks itself (section 8). The AI can't forge "it passed."
  4. A retry limit + a "give up and ask a human" state. If the AI keeps failing, it stops after a few tries and pages a person, instead of thrashing all night and producing a weird mess.
  5. Lock the dangerous routines. Deploy / delete / send-message can only be fired by a trusted step, never picked by the AI on a whim.

The rest of the floor hardens specific paths and comes after the first job proves the loop works: limit what the AI can send out to the internet (so a tricked AI can't phone home), a rule that the AI checks a database change locally but a human applies it to production, a guard so two automatic jobs don't fight over the same branch, and a guard so the AI can never commit straight to the main code (it must go through a PR/MR). (Those last two were missing from an earlier draft — your review-style pass caught it; they're back.)

Here's how Part 1 changes this: once a job runs in a practice copy with no real keys, "limit the internet" and "hide the real keys" go from the only thing standing between the AI and your data to extra safety on top of an already-safe setup. That's the whole point of giving it a practice room first — fewer locks have to be perfect.

Why these are trustworthy

The safety locks point at real things that actually went wrong in the industry: a real production database getting deleted, real keys getting leaked in 24 of 25 break-in attempts with no clever trick needed. We're not guessing at scary stories — we're locking the doors that were actually kicked in.

How humans get the best shot at catching bugs

The review can't catch everything, so the second job is making the human review fast and sharp:

  • The PR/MR is built to be scanned quickly. Every one has the same shape: the problem, the cause, what it did, the tests, the evidence, and how much could break. A human reading a tidy summary catches far more than one squinting at a raw diff — and the harness keeps each change small on purpose, because reviews get much less effective once a change runs past a few hundred lines.
  • It points you at the risky lines. Instead of "here are 400 changed lines," it says "these 12 lines touch pricing — look here first."
  • It carries proof. A screenshot, the test results, the type-check — attached, so you're not taking "it works" on faith.
  • The human checklist stays. There's a short list of things only a person can judge: "did this do what I actually asked?", the "huh, why is this even here?" test, and a 60-second click-through of the real thing. The AI's review never replaces this — it sets it up.
  • The AI is never the last gate. "Auto-approved" is not "auto-merged." A code check on the server always sits between the AI and your real code.

The layered defense (the honest version)

Between "the AI thinks it's done" and "it's in your real code," here is every catch, in order: (1) the auto-checks block dangerous commands; (2) tests + type-check run and must be green; (3) the fresh independent reviewer hunts for problems and loops until clean; (4) the four lenses each attack one angle; (5) the "knows your history" reviewer checks against your past decisions; (6) the test-count and risk checks flag sneaky changes; (7) the render check confirms the page actually looks right; (8) the server re-runs the checks on the exact final code — this one can't be faked; (9) the tidy summary + a human's 15-minute scan and click-through.

Be honest about step 8: the server re-running the tests and type-check truly can't be faked. But the deep review's opinion ("I found no must-fix problems") is the AI's judgment, and judgment can be wrong — so we don't pretend it's un-fakeable. Instead we measure how often that judgment misses a real bug (the calibrator), and we only let the AI auto-approve low-risk changes once that measured number is good enough. Anyone who says "the AI can never merge a bad change" is overselling. Our honest claim: the tests can't be faked, and the judgment is measured, not assumed.

10 · How it gets smarter (the two notebooks)

You asked to see the process: how does one project's AI get better over time, and how does the shared harness get better so every project benefits? There are two loops, and they feed each other.

Loop A — one project gets smarter (the local notebook)

Follow one real example: the AI keeps forgetting to limit a database query to one customer's data (a privacy leak).

  1. The reviewer catches it once  →  it's written as a lesson (a human confirms it's real)
  2. The lesson sits in an "inbox"
  3. It happens a 2nd and 3rd time  →  now it PROMOTES to a real rule
  4. From now on, that rule loads automatically whenever the AI touches database code
  5. Because it's a checkable rule, we turn it into a hard auto-check  →  now the AI
     literally CAN'T open a PR with an unscoped query — it's blocked
  6. We watch the number: "first-try approvals" go up. The mistake is gone for good.

That's the journey from "the AI keeps doing this annoying thing" to "it is now impossible." The key idea: a lesson doesn't just get written down (which everyone does and nobody reads) — it gets read back into the next job, and if it can become a hard block, it does.

Loop B — the shared harness gets smarter (the global notebook)

That privacy rule is useful in every project, not just this one. So:

  1. The lesson gets tagged "everyone needs this" (not just "this project")
  2. That opens a "please add this to the shared harness" request  →  a HUMAN reviews it
  3. It's merged into the shared harness package
  4. Every other project pulls it down with one update command
  5. Now all 5+ repos refuse the unscoped query — a mistake made once, fixed everywhere

How the two loops feed each other

A lesson starts local (Loop A). Once it's proven useful in one project, it's promoted to global (Loop B) and shipped to all of them. And it runs the other way too: when a project installs the shared harness, a global rule arrives and immediately starts watching that project. The fleet gets smarter while you sleep: on a schedule, a worker scans every project for rules that drifted out of date or mistakes that repeated, and opens one tidy PR per find. Honest note: the fully-automatic "push to global" only kicks in once you actually have a second project using it — until then it's a human opening the request by hand.

How a request becomes a working AI

A Slack message, a Linear ticket, an issue label, or a failed test on the server triggers a cloud "routine" — a built-in Claude Code feature that runs on Anthropic's servers (so it works with your laptop closed), gets the request, and starts the work in a scratch copy. Slack and Linear connect through a connector or a simple web call.

The un-fakeable stamp

The server re-runs your tests and type-check on the exact code being merged, and won't let it in unless they pass. The AI writes no "I passed" note the server trusts — so that part can't be faked. (The deep review's opinion is measured, not faked-proof — section 8.)

one honest exception Claude Code has a built-in trigger for GitHub events. For GitLab (and other hosts), there's no built-in button — you wire the trigger through a simple web call to the cloud routine, or a small custom runner. Same end result; a little more setup on non-GitHub hosts. We say this plainly rather than pretend it's identical.

13 · What we're honestly not sure about

You asked for honesty over flattery. Here's the real list.

  • Nothing has been tested live yet. A handful of "the platform can do X" claims are read from the docs, not tried even once (does a "block until done" check truly make the AI keep working? does the screenshot check run on the server? does the strongest lock actually take effect on a Mac?). Each is a quick one-time test we should run before relying on it.
  • Our research only looked at fans. All the sources we studied are pro-automation. We correctly refused to copy their hype numbers — but we never went looking for a team that tried this and pulled back. That search is worth doing. (That's part of why you asked us to read the "you're overthinking background agents" article — that 3-pass read is queued; see the note at the end.)
  • We never did the money math. Running lots of AI jobs across many repos costs money, and so do the harness's own nightly self-improvement runs. Nobody added it up. A harness can pay for itself in output and bleed on upkeep.
  • The safety is designed, not attacked. We planned the defenses; we didn't try to break them.
  • No "stop everything" button. There's a per-job stop, but nothing halts all your repos at once if something goes wrong fleet-wide. That's a decision below.
  • Don't over-trust the stamp. The biggest risk is someone reading "un-fakeable gate" as "bad code can't get in." It can — the gate makes the tests un-fakeable, not the judgment. We keep saying so on purpose.

14 · Surviving crashes (a habit, not just a footnote)

Building this plan, the AI work ran into the daily usage limit three times and lost almost nothing. Here's the simple trick, because V2 makes it a rule:

Write everything to disk as you go, and read results from disk — not from memory. Every worker saves its result to a file before finishing. If the run gets cut off, the finished files are already saved; only the unstarted work is lost, and it picks up by checking which files are missing. Order the work so the cheap, important stuff saves first.

Why V2 keeps this: a long automatic job that only reports at the very end loses everything if it's interrupted. So V2's jobs save progress as they go and narrate what they're doing — which is also exactly the "let me watch it work" feature you asked for.

honest catch This trick has its own trap, and it bit us: "the file exists" was treated as "the work is done" — but a file can be saved and still be wrong. We literally caught a step where the review files were saved but their fixes were never applied. The lesson, now built in: check the contents, not just that the file is there.
