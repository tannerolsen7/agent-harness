# Ambition Re-mine — Playwright MCP for Debugging (Browser Automation in AI-Native Dev Workflows, 2026)

## What this source is (plain English, 2-3 sentences)
A 2026 ecosystem survey of browser-automation-over-MCP tooling (Playwright MCP, Chrome DevTools MCP, Stagehand, Browserbase, Vercel `agent-browser`, ProofShot, WebMCP) framed around one debugging recommendation: let an agent drive a real browser and read the cheap accessibility tree instead of expensive screenshots. Underneath the tool inventory, its real argument is *epistemic* (pass2 §1): make an agent emit **evidence a human or a deterministic gate can independently check** — accessibility snapshots, `@e1` element IDs, ProofShot HTML bundles, checked-in visual-regression baselines — instead of a natural-language "it works" claim. The most actionable distinction it never names: **debugging (find a cause) and verification (prove a change didn't break the surface) are different loops with opposite economics.**

## The full-ambition moves this source teaches

### Move: The trust contract — agent UI claims must ship as independently-checkable artifacts, not prose
- **Plain-English what & why:** Today when an agent says "I fixed the layout, it renders correctly now," a human takes that on faith — there is no proof attached. World-class teams flip the burden of proof: the agent must produce an *artifact* (a video, a console-log capture, an accessibility snapshot, a pixel-diff against a baseline) that a reviewer or a CI gate can check without re-running the agent's reasoning. This prevents the single most expensive failure mode of autonomous agents — a confident, wrong "done" that ships because nobody could cheaply disprove it. The failure it prevents: an overnight agent merges a PR whose UI is broken because "agent says it works" was the only verification.
- **The mechanism:** Add a browser-evidence leg that runs in CI (and/or as the final leg of `/cr`) against a preview deploy: navigate the changed route(s), capture an accessibility snapshot + console errors + a screenshot, diff the snapshot/pixels against a checked-in baseline, and **attach the bundle to the PR as a reviewable artifact**. The agent's claim is no longer the deliverable; the artifact is. Pair this with the already-flagged hole that even our *existing* review evidence (`.cr-ok`) never reaches CI — close both with one deterministic artifact gate.
- **Citation:** Map confirms the verification-evidence-to-CI hole: "Node 8.5(c) gap — CI never verifies `.cr-ok`" and "`.cr-ok` chain … gitignored, never reaches CI" `[map §3f / §8.5c, line 229–230]`. Browser-evidence leg is a confirmed absence: "package.json has no playwright/E2E dep; .github/workflows has no browser job" `[pass3 (b)1, verified]`. CI is tsc/lint/vitest only `[map §3f]`.
- **Conservative disposition:** §C-deferred and scaled down. Pass3 conceded this is "a real, citable gap" but immediately hedged "see (c)/(d) on whether browser tooling is the right fix vs. closing the `.cr-ok`-to-CI hole first," then in (d) reclassified it as a *decision, not an unknown* that "overlaps the existing bug-to-pr-automation … passes — synthesize, don't re-fetch." The conservative synthesis collapsed it into a tool-agnostic "wiring tweak." MASTER-FINDINGS §C treats the verification-evidence-to-CI gap as deferred, not a charter-level move.
- **RE-JUDGMENT under the new charter: ELEVATE.** This is the single most important move in the source and it is in-scope-now. The conservative "is browser tooling the right fix, or just close the `.cr-ok` hole?" framing is a false dichotomy that *shrinks* the move: the real move is **a deterministic, artifact-producing verification gate that reaches CI** — `.cr-ok` reaching CI is the floor, browser-evidence is the world-class ceiling, and an autonomous harness needs both. Under "autonomy is first-class," an unattended bug→PR loop is unsafe *without* this — there is no human watching to catch the confident-wrong merge. Make it bigger: a `/verify` project skill that produces a PR-attached evidence bundle (a11y snapshot + console + pixel-diff vs. baseline), wired as a required CI leg, gated by `disable-model-invocation` so the agent can't fabricate or skip it. This is the literal precondition for the autonomous front-door the synthesis says it wants.

### Move: Debugging ≠ verification — split the loops, give each its own budget and home
- **Plain-English what & why:** Debugging is exploratory: a bug exists, you hunt the cause, the loop is unbounded and expensive, and you cap it (e.g. "max 5 iterations then surface to a human"). Verification is the opposite: a change was made, you prove the surface still works, the answer is binary pass/fail, and it belongs in an automated gate, not an iterative session. Fusing them — as most tutorials do — means people either put an iterative debug loop into CI (wrong: CI should be pass/fail) or treat verification as a judgment call (wrong: it should be deterministic). The failure it prevents: a CI "verification" step that loops, burns tokens, and produces a *narrative* instead of a green/red verdict — non-reproducible, un-gateable, slow.
- **The mechanism:** Two distinct, separately-owned mechanisms. (1) `/debug` stays the interactive, capped, exploratory loop (we already have the skill `[map §3b]`). (2) A new `/verify` project skill is the deterministic pass/fail gate: fixed steps, no iteration, emits an artifact + exit code, runs in CI. Critically, our runtime skill list *shows* a `verify` skill but it is **not on disk** (`ls .claude/skills/` returns none) — it's a borrowed upstream/global skill we don't own and that won't travel with the plugin. Build a project-owned `/verify`.
- **Citation:** Debug≠verify is pass2 §7 ("the single most useful distinction the article contains and it never names it"). `/debug` exists `[map §3b]`. `/verify` not on disk: "the live skill registry shows `verify`, `run`, `code-review`, `simplify`; `ls .claude/skills/` returns none" `[pass3 (b)4, verified]`; map names the hazard: "the runtime skill list mixes all layers … cannot tell which layer owns each, nor which will travel" `[map §1]`.
- **Conservative disposition:** §D-minor / cross-referenced away. Pass3 (b)4 flagged the `/verify`-not-on-disk gap honestly but (d) punted it: "Gap 4 (`/verify` not a project skill) is a commands-vs-skills question already covered by that pass dir — cross-reference it." The distinction itself (debug vs verify) was acknowledged as "the most actionable" yet generated no build item — it was filed as analysis, not action.
- **RE-JUDGMENT under the new charter: ELEVATE.** "Clarity beats minimalism / more skills is fine when each earns its place" directly licenses building a project-owned `/verify` distinct from `/debug` — and each obviously earns its place because their economics are opposite. Cross-referencing it to "commands-vs-skills" buried a first-class build item. World-class version: `/verify` is a committed, plugin-travelling, `disable-model-invocation`-gated deterministic gate that the autonomous loop calls after every fix and before every merge; `/debug` remains the capped interactive hunt. This is exactly the kind of file the retired "fewer files = good" instinct would have suppressed.

### Move: Agent-debuggability == human-accessibility — mandate agent-legible markup (`data-testid`, `aria-label`, structured `console.error`, error-boundary messages, `aria-busy`)
- **Plain-English what & why:** Whether an agent can navigate and diagnose your app is decided by your markup, not your tooling. An unlabeled icon button shows up to the agent as `button [@e3]` and it guesses; a labeled one (`aria-label="Approve proposal"`) is unambiguous. The deep insight (pass2 §6): the markup that makes an app *agent-legible* is the exact same markup that makes it *accessible to humans* (WCAG). So the cost of agent-debuggability is near-zero for a well-built app and only expensive for a badly-built one — it's a property good teams already want for an independent reason. The failure it prevents: every browser-verification run produces noisy, guess-laden snapshots that the agent misreads, generating confident-wrong diagnoses on UI it literally cannot name.
- **The mechanism:** A CLAUDE.md rule (and a `docs/design/` instrumentation entry) mandating: `data-testid` on key interactive elements, meaningful `aria-label`/text on every interactive element, structured `console.error` (objects not concatenated strings), descriptive error-boundary messages (not "Something went wrong"), and `aria-busy`/`aria-label="Loading"` on loading states. Optionally an ESLint rule (e.g. jsx-a11y) to enforce labels at commit time. This makes both the accessibility-snapshot verification leg (Move 1) and the manual-QA blocker durable.
- **Citation:** Confirmed absence — "`grep` finds **zero** `data-testid` across `src/` and `app/`" and "no CLAUDE.md rule, no design-token doc covers it … no design/a11y instrumentation row" `[pass3 (b)2, verified]`. The accessibility==agent-legibility thesis is pass2 §6.
- **Conservative disposition:** §C / scaled-down. Pass3 named it ("the cheap, durable win … currently unmet and un-mandated") and the bottom line listed it as reframe #2 ("mandate agent-legible/accessible markup … which we have zero of"). But it stayed a "synthesizable now" reframe with no concrete enforcement mechanism and no charter weight — a note, not a build.
- **RE-JUDGMENT under the new charter: ELEVATE (moderately).** The dismissal isn't *wrong* about value — it undersells the leverage. This is the cheapest precondition for the entire autonomy stack: without agent-legible markup, every overnight browser-verification run degrades to guessing. Make it a hard CLAUDE.md rule + lint gate, not a reframe. The reason it's a moderate not maximal elevate: it's genuinely lightweight and additive (a rule + a lint plugin), so "bigger" here means *enforced and mandated*, not *architecturally large*. It earns first-class status because it is the foundation the verification gate stands on.

### Move: Resolve the unattended-harness / headed-only-browser-MCP contradiction (adopt a headless browser path)
- **Plain-English what & why:** Our harness's whole design center is *unattended* operation — overnight, parallel, UNATTENDED worktree mode. But the only browser MCP we've wired is `chrome-devtools-mcp`, which the source documents as **headed-only**: it attaches to a real Chrome window and "breaks in CI, overnight runs, headless." So an autonomous agent that tries visual verification at 3am fails silently — the exact silent-failure class the harness already fears for background agents. The failure it prevents: the autonomous bug→PR loop's verification step is structurally impossible in the very mode the harness is built for.
- **The mechanism:** For unattended runs, route browser verification through a **headless** path — either confirm `chrome-devtools-mcp` can run headless in the worktree/UNATTENDED context (Chrome 144 `--autoConnect` / 146 native toggle), or adopt **headless Playwright MCP** for the verification leg, which means *reversing* the `.claude/mcp.md` "Playwright redundant with chrome-devtools-mcp" rejection. Rank browser tooling on the attended-vs-unattended axis (pass2 §4's "single axis that matters most for an autonomous harness"), not the deepest-signal axis the article defaults to.
- **Citation:** Headed-only weakness: pass1 §3/§6. Contradiction confirmed: "an unattended harness wired to an attended-only browser tool" `[pass3 (b)3]`; `.mcp.json` configures only `chrome-devtools-mcp` and `.claude/mcp.md` records "**Playwright MCP — overlaps with chrome-devtools-mcp; running both is redundant**" `[pass3 (a), verified]`. UNATTENDED/worktree rows: `[map §3e, §6, line 212]`.
- **Conservative disposition:** §C-deferred to a "narrow, time-boxed external check … if and only if Phase 4 decides to act." Pass3 (d) made acting on it *conditional* on a Phase-4 trigger and called the Playwright rejection consistent with the article's own "running both is redundant" logic — i.e. it argued the rejection mostly stands.
- **RE-JUDGMENT under the new charter: ELEVATE.** Under "autonomy is first-class + cloud /schedule exists," unattended browser verification is not a maybe-Phase-4 — it's a precondition for the scheduled/overnight loop the charter centers. The "running both is redundant" defense of the Playwright rejection is conservative bias: redundancy was judged on *signal overlap*, not on the attended/unattended axis. Headless capability is the deciding factor, and on that axis Playwright (headless-friendly) and chrome-devtools-mcp (headed-only) are *not* redundant — they serve different operating modes. Resolve it now: keep chrome-devtools-mcp for attended deep-signal debugging, add a headless verification path (likely Playwright MCP, gated/scoped to the verify leg) for unattended runs. Caveat that keeps this honest: cloud `/schedule` runs on restricted-network Anthropic infra with no local MCP servers (only claude.ai connectors) — so the headless verify leg for *scheduled* runs likely must execute as a CI job against a preview deploy rather than via a local MCP, which actually *reinforces* Move 1 (CI-resident, artifact-producing verification) over an interactive MCP.

### Move: Tenancy false-confidence guard — the agent must assert it is acting as the intended tenant before trusting any snapshot
- **Plain-English what & why:** This is the source's named "false confidence from visual similarity" failure mode, sharpened by pass2 §3 into its most dangerous variant for an RLS product. A browser snapshot taken while authenticated as the *wrong tenant* renders perfectly and produces a confident, wrong diagnosis — and nothing on the screen reveals the mismatch, because tenant isolation lives in RLS and `src/data/`, invisible to the DOM. For a multi-tenant SaaS this is a correctness *and* a security trap: an agent could "verify" a fix against tenant A's data while believing it's tenant B's. The failure it prevents: an autonomous agent trusting a snapshot that was rendered under the wrong identity.
- **The mechanism:** Before any browser-verification run trusts a snapshot, the harness must assert the active session's tenant binding matches the intended one — e.g. read an in-page assertion of `team_id`/tenant (a `data-tenant` attribute or a known fixture marker), or pin the verify run to a deterministic seeded test tenant, and *fail closed* if the binding doesn't match. The saved auth session (a JWT with a tenant binding + expiry) must be re-validated, not assumed (pass2 §3: "save cookies once doesn't survive token rotation").
- **Citation:** Tenancy false-confidence is pass2 §3, omitted by the article. Confirmed absence: "There is no map row for 'agent verifies it is acting as the intended tenant before trusting a snapshot'" `[pass3 (b)5, absent]`. RBAC/tenant isolation in `src/data/` + RLS `private.team_ids()` `[CLAUDE.md Architecture]`.
- **Conservative disposition:** §C / noted-but-no-mechanism. Pass3 (b)5 stated "we have nothing for it" and called it "the highest-severity version of the article's named visual-false-confidence risk" — but proposed no guard and it never reached the bottom-line three reframes.
- **RE-JUDGMENT under the new charter: NEW (recovered as first-class).** The conservative synthesis effectively summarized this away — it's named in a sub-bullet, given no mechanism, and dropped from the action set. Under autonomy-first this is non-negotiable: an unattended agent that can mis-identify its tenant is a security incident generator, exactly the class the harness's Tier-0 firewall and destructive-op rules exist to prevent. Recover it as a hard requirement of the verification leg: **fail-closed tenant assertion before any snapshot is trusted.** This is small to build and high in severity — a textbook "name the failure mode the constraint prevents" win.

## Autonomy angle
Yes — strongly, and the conservative synthesis muted most of it. The source explicitly teaches the **bug→PR** front-door in two insertion points (pass1 §8): (1) *at PR open* — GitHub Actions triggers Claude Code (`anthropics/claude-code-action@v1`), agent reads the diff, runs browser MCP against a preview deploy, captures regressions/console errors, posts inline comments; (2) *at CI failure* — Gitar-style agents read the CI log, reproduce, fix, verify green, open a patch PR. It cites **Playwright AI Healer (>75% autonomous repair of selector/DOM failures)** and **Vercel `agent-browser`** (agent self-verification CLI) as production-grade autonomous loops already shipping. The load-bearing autonomy principle is the **trust contract**: autonomy is only safe when the agent's "done" is a checkable artifact, not a claim — which is precisely why the verification-evidence gate (Move 1), the headless unattended path (Move 4), and the tenant guard (Move 5) are autonomy *enablers*, not nice-to-haves. It does not directly address Slack/Linear summon or self-improving loops, but its CI-failure→patch-PR loop (AI Healer) *is* a self-healing primitive. Net: this source is one of the corpus's clearest arguments that the autonomous front-door needs an artifact-producing verification spine underneath it.

## The single biggest move (one paragraph)
Build the **artifact-producing verification gate that reaches CI** (Move 1) — a deterministic, non-iterative `/verify` leg that, against a preview deploy, captures an accessibility snapshot + console errors + a pixel-diff against a checked-in baseline and **attaches the bundle to the PR**, gated by `disable-model-invocation` so the agent can neither fabricate nor skip it. The vision synthesis should pick this up first because it simultaneously closes the map's already-flagged hole (`.cr-ok` / verification evidence never reaches CI, §3f/§8.5c) and supplies the missing precondition for *every* autonomy move the charter wants: a bug→PR or overnight-scheduled loop is unsafe without a deterministic, human-checkable proof that the change actually renders and behaves — "agent says it works" is exactly the confident-wrong failure that autonomy amplifies. It is world-class because it operationalizes the source's true thesis (shift the burden of proof from prose to artifact), it is the spine the other four moves bolt onto (agent-legible markup makes the snapshot trustworthy; the headless path makes it runnable unattended; the tenant guard makes it safe under RLS; the debug/verify split keeps it deterministic), and the conservative synthesis suppressed it into a "wiring tweak / decision-not-unknown" when it is in fact the keystone of the autonomous harness.
