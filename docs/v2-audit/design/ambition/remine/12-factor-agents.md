# Ambition Re-mine — 12-Factor Agents (Dex Horthy / HumanLayer)

## What this source is (plain English, 2-3 sentences)

A widely-cited (~19k-star) engineering manifesto arguing that production agents are not magic autonomous loops — they are **deterministic programs with an LLM as a single pure decision-function over a context window you fully own and engineer**. Its 12 (+1) factors are 12 places where teams accidentally let the model — or a framework wrapping it — reclaim authority (control flow, prompts, state, error handling, triggering) that the deterministic code should keep. Read deepest (pass2), it is a *boundary-policing manual*: own the seam you debug across, demote the model to `determine_next_step`, and refuse to cede prompts, context, or control flow to anyone else.

## The full-ambition moves this source teaches

### Move: Errors-into-context + deterministic circuit-breaker (F9, F8-aware)

- **Plain-English what & why:** When a tool call fails, a world-class agent does not throw the error up and die — it writes the failure *back into the context window* as information ("the migration failed because column X already exists") so the model can reason about it and try a different approach on the next loop. The failure preventer is twofold: (1) agents that crash on the first tool error are useless for any multi-step autonomous task; (2) but the *naive* version — append every error, retry forever — pollutes context and produces infinite retry loops that burn budget teaching the model its own failure. The world-class version pairs error-into-context (a context-engineering move) with a **deterministic max-retry / give-up decision in code** (a control-flow move), because the give-up decision is exactly the kind of branch F8 says must live in code the model can't override.
- **The mechanism:** A `PostToolUse` hook (or equivalent harness convention) that, on a failed tool call, (a) compacts the error into a structured, deduplicated context event rather than a raw stack trace, and (b) tracks a per-tool retry counter and hard-stops at N (escalating to a human-checkpoint or aborting the loop). Today our control flow lives in hooks [§3e], and there is **no error-handling hook, skill rule, or PITFALLS entry anywhere** — §3e lists every hook and none handle tool-error compaction; §4's memory model captures *human-corrected mistakes*, not *runtime tool failures fed back to the agent*. This is a new, codifiable convention: an `errors-into-context` doctrine in CLAUDE.md + a circuit-breaker hook.
- **Citation:** Confirmed absence — no error-into-context convention exists; §3e (every hook enumerated, none handle tool-error compaction) + §4 (memory captures human-corrected mistakes, not runtime tool failures).
- **Conservative disposition:** §C-style DEFERRED-with-narrowing. Pass3 (b) accepted it as a "Real gap" but immediately narrowed it: "needs the F8-aware framing, not the article's raw F9," and §(d) routed it to "a *focused check* of the harness's PreToolUse/PostToolUse hook surface … not a literature review," explicitly *not* in-scope-now build. It treated it as a research question ("what can a Claude Code hook actually intercept on a failed tool call?") rather than a build item.
- **RE-JUDGMENT under the new charter: ELEVATE.** Under "autonomy is first-class," this is not a nice-to-have — it is **the load-bearing reliability primitive of any unattended loop**. A bug→PR agent, a cloud `/schedule` run, a Slack-summoned fix: every one of these runs *without a human watching the first tool failure*. Without errors-into-context the agent dies silently on the first transient failure; without the circuit-breaker it loops until it exhausts budget. The conservative bias was treating this as a "convention to maybe document" — at fleet scale running parallel cloud agents across 5+ repos, a missing circuit-breaker is a recurring silent-failure and runaway-cost class. This moves to **in-scope-now, build the hook**. The pass3 narrowing (F8-aware: compaction + deterministic max-retry) is *correct and should be kept* — it makes the move stronger, not smaller. Bigger by: from "document a convention later" to "ship a PostToolUse circuit-breaker hook + retry-budget contract as a first-class autonomy-safety mechanism."

### Move: Unify execution state and business state (F5)

- **Plain-English what & why:** Don't run two (or more) systems that both claim to hold the truth and then spend your life keeping them in sync. The same fact — "this corrected mistake / this pattern / this decision" — should have **one home**. The failure it prevents: when state is duplicated across stores, they drift; the agent reads a stale copy, and "most async agent bugs live at this boundary" (the article's claim). For us this is not hypothetical: the same corrected-mistake fact lives in `.claude/memory.md` + `PITFALLS.md` + auto-memory `feedback_*` simultaneously, a triple-duplication the canon **both sanctions and forbids**, reconciled "only in prose, encoded in no tooling" [§4]. The auto-memory store (`MEMORY.md` + 51 siblings) is "a sixth store the canon's model doesn't account for" [§4, §6] — a literal second state system outside the canonical one.
- **The mechanism:** Phase-3's stated target already *is* the F5 fix [§4]: ONE coherent memory model where every store has one writer / one reader / one freshness rule, that accounts for the auto-memory store, encodes lifecycle-stage reconciliation in tooling (not prose), and collapses the triple-duplication. F5 is the *naming* of why this matters and the *test* for whether it worked (can the same fact still live in three places? then state isn't unified).
- **Citation:** §4 (the memory model — declared vs built; triple-duplication "both sanctions and forbids"; auto-memory as uncounted sixth store) + §6 (auto-memory as disk-only registry item).
- **Conservative disposition:** §(b) "Real gap, and the strongest factor-to-row mapping in the article." Fully credited — pass3 did *not* scale this down. (It correctly rejected the *article's own* `updateProposal` example as an unverifiable product-layer claim not in the harness map — that rejection is sound.)
- **RE-JUDGMENT under the new charter: UPHELD (already correctly scoped, not a cut).** This is the rare case where the conservative synthesis got it right and the new charter doesn't change the verdict — it *raises the stakes*. At fleet scale, parallel agents reading drifted memory stores is a correctness multiplier, not a solo annoyance. The move stays in-scope-now (Phase 3 owns it). The only charter-driven amplification: the unified model must survive **concurrent writers** (multiple worktree agents + the auto-memory subsystem writing at once), which the single-loop article never contemplates — so design the one-writer rule with fleet concurrency in mind, not just sequential sessions. Not an ELEVATE (already first-class), not an UPHELD-CUT (it's a keep, not a cut).

### Move: Machine-enforced authority-within-context / canon vs not-canon (F3 inverted)

- **Plain-English what & why:** The article's strongest opinion is "context engineering > model choice" — what you put in the context window, in what order, with what authority, determines output more than which model you use. Pass2 found the article's *blind spot* and inverted it into our gap: the article treats the context window as a **flat bag** whose only properties are order and compression — it has **no theory of authority** (which doc is canon, which is a stale spec, which overrides which). A knowledge-doc harness like ours lives or dies on exactly that distinction. The failure it prevents: the agent reads a rotted doc as if it were canon and acts on stale truth. Ground truth confirms the pollution is live — `HARNESS-AS-IS.md` carries stale absence-claims and "any 'ABSENT' claim … must be re-verified" [§0 Correction log]; `AGENTS.md` has a "None open" contradiction [§3a]; PITFALLS/memory are assigned to *both* Layer 1 and Layer 3 depending on the page; read-time is specified for only ~5 of ~14 knowledge files [§4].
- **The mechanism:** A machine-enforced doc-authority level — canon vs not-canon, live vs frozen — that the harness can *act on*, not just describe in prose. Concretely: an authority/freshness field on each knowledge doc, a hook or skill step that flags a stale-authority read, and (under the new GitHub-as-canon workstream) GitHub becoming the single source of truth so "which copy is authoritative" stops being ambiguous. F3 is the vocabulary for why context authority *is* the product.
- **Citation:** §0 Correction log ("the project audit artifact itself rots"); §3a ("AGENTS.md 'None open' contradiction"); §4 ("stale authority," "admitted ambiguities," read-time specified for only ~5 of ~14 files).
- **Conservative disposition:** §(b) "Real gap." Credited but left abstract — pass3 named it ("the harness has no machine-enforced doc-authority level") without specifying a mechanism or putting it in-scope-now; it stayed a diagnosis.
- **RE-JUDGMENT under the new charter: ELEVATE.** The new charter makes **GitHub the single source of truth** and runs a Notion→GitHub migration — which is *precisely* the F3 authority problem getting a real answer. The conservative version left it as "we have no machine-enforced authority level" (a complaint). The charter turns it into a workstream: as the canon migrates to GitHub, encode authority/freshness as a machine-readable field, and add a stale-authority guard so a cloud `/schedule` agent (which clones the repo and runs committed skills with *no human to sanity-check which doc is current*) cannot act on a rotted doc. This is bigger because autonomy removes the human who today silently corrects for stale context. Pass2's depreciation caveat sharpens it: as the model improves (Opus 4.8), some context-engineering becomes overhead [§9] — so the authority model must also carry a "is this scaffold still earning its place?" signal, tying F3 directly to the §9 Model Capacity Audit.

### Move: One-agent-one-job discipline, codified (F10)

- **Plain-English what & why:** Reliability degrades as an agent's scope grows; the world-class pattern is "one agent, one job, hand off cleanly." The discipline the article prizes: "an agent's job description should fit in one sentence." The failure it prevents: scope-creep agents that do five things adequately and none reliably — and at fleet scale, an agent whose job is unclear can't be safely composed or scheduled. We have the *roster* (23 agents [§3d]) but the *discipline* is uncodified — and the canon's own agent taxonomy is internally inconsistent ("8 specialist agents" header over a 9-row table; "Ten" templates over 8 roles [§3d, §7.6]), with **no scope-limiting design rule anywhere** in SOUL/AGENTS/CLAUDE per the §3a inventory.
- **The mechanism:** A codified scope rule for agents ("job description fits in one sentence; if it needs two, split it") in agent-contract.md / AGENTS.md, plus reconciling the inconsistent agent-count taxonomy so the roster is internally coherent. Critically, pass3 noted F10 "intersects the §9 Model Capacity Audit … F10 discipline is one of the few that is reasoning-discipline (keep), not capability-proxy (cut)" — so it survives the model-upgrade scaffold purge.
- **Citation:** §3d (23 agents; taxonomy inconsistencies) + §3a (no scope-limiting design rule in any governance doc) + §9 (reasoning-discipline-keep vs capability-proxy-remove distinction).
- **Conservative disposition:** §(b) "Real gap" but minor-flavored — framed as a "discipline gap," a rule with "no home in our docs today." Not given a build slot; treated as a doc-rule to add eventually.
- **RE-JUDGMENT under the new charter: ELEVATE (moderately).** Under "autonomy is first-class" and *fleet scale*, F10 is no longer a tidiness rule — it is a **composition precondition**. Self-improving loops, bug→PR pipelines, and Slack-summoned agents all *route between specialist agents*; routing is only safe when each agent's job is one crisp sentence (an orchestrator can't dispatch reliably to agents with fuzzy overlapping scopes). The conservative "discipline gap" framing under-weighted that autonomy *depends* on clean handoff boundaries. Bigger by: from "add a doc rule" to "codify the one-sentence-job rule *and* reconcile the agent taxonomy as a prerequisite for the autonomy orchestration layer." Not a full ELEVATE to top-of-list (it's enabling, not headline), but firmly in-scope-now rather than "eventually."

### Move: Trigger-from-anywhere (F11) — the autonomy front door

- **Plain-English what & why:** A world-class agent is triggerable from *any* surface — email, Slack, webhook, cron, mobile, an issue event — without rewriting its core logic, because the trigger is "just how you construct the initial context." This is the single factor that *is* the autonomy thesis: bug→PR, summoned-from-Slack, cloud-scheduled all *are* F11. The failure it prevents: an agent locked to one invocation surface (a human typing in a terminal) can never run unattended.
- **The mechanism:** Webhook / Slack / Linear / cron entry points that construct an initial context and launch the loop. Pass3 found the structural absence is total: "the only trigger surfaces are Claude Code sessions + git hooks [§3e/§3f] + CI [§3f]. No webhook/cron/email/Slack path exists in the entire inventory" [§(b)], and the harness "has **never been installed anywhere but event-vendor**" [§8].
- **Citation:** Confirmed structural absence — §3e/§3f (only trigger surfaces are CC sessions + git hooks + CI) + §8 ("never been installed anywhere but event-vendor"; backlog "GitHub Publishing … next gate: 3 real installs" unmet) + §2 (global layer has no global agents/hooks/commands).
- **Conservative disposition:** §C DEFERRED, hardest. Pass3 §(b): "F11 for us is downstream of the global-install gap, not a standalone plumbing task," and §(d) explicitly: "research here should be *deferred* until V2 has a shared installable harness, then look at webhook/cron entry points. **Premature now.**" This is the clearest instance of the old charter's "defer the trigger front-door."
- **RE-JUDGMENT under the new charter: ELEVATE — this is the headline reversal.** The new charter states autonomy (bug→PR, summoned from Slack/Linear, cloud scheduling) is "designed in, never deferred," and the resolved facts establish that **cloud `/schedule` already EXISTS** and runs on Anthropic infra (clones the repo, runs committed skills, calls connectors). So the pass3 deferral rests on a premise that is now MOOT: F11 was deferred as "downstream of the global-install gap" + "machine-asleep/durability" worries — but a cron trigger surface *already exists* and the install gap is now an active workstream (plugin + marketplace + thin `/init` template). The conservative bias was treating the trigger front-door as plumbing to do *after* everything else; the charter makes it the **north-star deliverable**. In-scope-now: (1) commit a side-effect-safe scheduled skill (`disable-model-invocation:true` makes deploy/open-PR/send-Slack skills safe — the resolved fact that *enables* this) and wire it to cloud `/schedule`; (2) design the bug→PR path as an F11 trigger (issue/webhook → initial context → loop → reviewed PR). Caveat to honor, not defer: cloud `/schedule` is network-restricted with no local MCP servers (only claude.ai connectors), so the triggered skill must be self-contained against committed code + connectors. Bigger by: from "premature, defer until 3 installs exist" to "the primary autonomy front door, built now on the cloud `/schedule` that already exists."

## Autonomy angle

This source is **directly and centrally about autonomy** — more than almost any source in the corpus. F11 (Trigger from Anywhere) *is* the bug→PR / Slack-summon / cron thesis stated as an architectural factor: "the trigger is just how you construct the initial context," triggerable from email/Slack/webhook/cron/mobile without rewriting core logic. F6 (Launch/Pause/Resume with simple APIs) is the durability primitive that makes an interrupted unattended run resumable — directly relevant to cloud `/schedule` runs that may be staggered or interrupted. F9 (errors-into-context + circuit-breaker) is the reliability primitive *without which no unattended loop is safe* — it is what keeps a bug→PR agent from dying on the first transient failure or looping forever. F10 (one-agent-one-job) is the composition precondition for any orchestrated/self-improving multi-agent autonomy. The article's *weakness* is also autonomy-relevant: pass2 showed F12's single-loop/single-process model **hand-waves orchestration as "plumbing"** — but for a fleet (worktrees, `/queue`, parallel cloud schedules) the orchestrator *is* the hard part; so adopt F11/F9/F6 as primitives while explicitly rejecting the article's claim that the multi-surface router is trivial.

## The single biggest move (one paragraph)

**Build the F11 trigger-from-anywhere front door now, on the cloud `/schedule` that already exists — with F9's errors-into-context + circuit-breaker as its non-negotiable reliability floor.** The conservative synthesis deferred F11 as "premature, downstream of the install gap" and routed F9 to "a focused research check, not a build" — both deferrals rest on premises the new charter retires: cloud `/schedule` *exists* and runs committed skills on Anthropic infra (killing the durability objection), `disable-model-invocation:true` makes side-effect skills (open-PR, send-Slack) *safe* (killing the "autonomy is too risky" objection), and the install gap is now an active plugin+marketplace workstream rather than a blocker. This is world-class because it is the exact move that converts the harness from "a human types in a terminal" to "a bug becomes a reviewed PR, summoned from Slack or fired by cron, while the laptop is closed" — the north star itself, stated by a ~19k-star manifesto as a first-class architectural factor rather than a someday-feature. The one dependency that makes it safe and not reckless is F9's circuit-breaker: an unattended trigger without a deterministic max-retry/give-up backstop is a runaway-cost and silent-failure generator at fleet scale, so ship them together.
