# Ambition Re-mine — When Is an LLM Call Worth It? (Decision Framework)

## What this source is (plain English, 2-3 sentences)
A product-engineering decision framework for deciding whether a shipped feature should make an LLM call at all: a 7-gate "stop at first NO" filter (deterministic? ambiguous input? language/judgment output? cost? latency? testable? unique value?), plus a doctrine for how to wrap any LLM call you do keep — structured-output validation, mandatory fallback, evals-in-CI, compounding-reliability math, and a reversibility gate for autonomous actions. Its worked example is *this exact repo's product* (proposal descriptions, brief parsing, change-request summaries), which is why pass2 had to separate "LLM-as-product-feature" from "LLM-as-the-thing-that-builds-the-software" — only the second matters for the harness audit. The durable content is not the gate tree (a teaching scaffold) but the "shell doctrine": how you pay honestly for putting a probabilistic core inside a deterministic shell.

## The full-ambition moves this source teaches

### Move: Evals-in-CI for the harness's own probabilistic outputs (golden-PR regression for /cr)
- **Plain-English what & why:** AI-native teams spend 20–30% of initial budget on evaluation infrastructure and build the evals *before* the features, because a probabilistic system degrades silently — a regression is invisible until a real user (here: a real shipped bug) hits it. The failure prevented: you swap models (Sonnet 4.6 → Opus 4.8, or any future bump), `/cr` quietly stops catching a class of bug it used to catch, and you discover this only when a defect that `/cr` "reviewed" reaches main. Deterministic CI (tsc/lint/vitest) cannot see this because it tests the *code under review*, never *whether the reviewer still reviews well*.
- **The mechanism:** Build an eval-in-CI store for the reasoning skills. Concretely: a frozen "golden PR" corpus — a set of diffs each with known, labeled defects (a missing fallback, an `as` cast without narrowing, a cross-tenant RLS hole, an open-redirect) plus a set of clean diffs. A CI job (or a scheduled cloud `/schedule` run) runs `/cr` against the corpus and asserts a catch-rate floor (e.g. baseline 95%, fail the build / open an issue at <85%) and a false-positive ceiling on the clean diffs. Same pattern for `/cr-security` (golden vulnerable diffs) and the 4 adversarial lenses. This is the article's "statistical eval on a golden set + behavioral probes" applied to a code-review agent rather than a classifier.
- **Citation:** Confirmed absence. [canon §3f] CI is `ci.yml` + `integration.yml` running tsc/lint/vitest only — "it never evaluates whether `/cr` still catches what it used to catch after a model change." No eval-in-CI store anywhere in the map ([canon §3b] lists no eval skill; `evaluate-solution` is a solution-quality skill, not an LLM-regression eval). Article basis: pass1 §Testing, §"20–30% of budget to evals."
- **Conservative disposition:** §C DEFERRED. MASTER-FINDINGS treated property-based / eval-in-CI as a hypothesis-gated deferral ("property-based testing for money-math" and the eval layer parked behind a "do we have the volume / golden set?" doubt). Pass3 itself flagged this as "the article's sharpest contribution to the V2 audit" but routed it to a "build-or-reject decision" rather than an in-scope build, and gated it behind a fresh-research caveat (pass3 §d: "one bounded exception").
- **RE-JUDGMENT under the new charter: ELEVATE.** This is the single biggest move and it should be in-scope-now, not deferred. The deferral rested on two conservative assumptions both broken by the new charter: (1) "no golden set / no volume" — false for a harness, because the golden set is *cheap and finite*: a few dozen labeled diffs the team already has in git history (every past bug that shipped is a golden negative; every `/cr` MUST-FIX is a golden positive). The article's "do you have volume?" doubt was calibrated to a *product classifier* needing thousands of labeled examples; a code-review regression probe needs ~30. (2) "machine asleep / can't run it durably" — moot: cloud `/schedule` exists, clones the repo, runs committed skills, so the golden-PR eval can run nightly on Anthropic infra with zero laptop dependency. Bigger by: making this a standing CI gate + a nightly `/schedule` routine that opens a regression issue, not a one-time "decision." Under "autonomy IS the goal," a self-improving harness *requires* a feedback signal on its own quality — this is that signal. Without it, every model bump is an unmeasured blind swap.

### Move: Model Capacity Audit needs an automated behavioral-probe backstop, not a manual re-audit
- **Plain-English what & why:** The harness already decided which scaffolds to cut "because the current model no longer needs them" — but those judgments were made against one model version and are explicitly "due for re-audit on a model update." The article's silent-regression argument supplies the missing enforcement: a human re-audit is itself a probabilistic, fallible, unscheduled step that will rot exactly like the cited constants rot. The failure prevented: Opus 4.8 (or 4.9) silently regains *or loses* a capability the cuts assumed, the cuts become wrong, and nobody re-runs the manual audit because it's a human chore with no trigger.
- **The mechanism:** Turn each "Replace (capability proxy)" judgment in §9 into a *behavioral probe* — a tiny test that asserts the model still has the capability the scaffold was removed for. E.g. the cut "structural option-count forcing → state thoroughness directly" becomes a probe: give the model a design prompt with the forcing removed, assert it still produces ≥N distinct options. Run the probe suite on every model bump (a `/schedule` routine keyed to model version). If a probe fails, the corresponding scaffold's removal is auto-reverted or flagged NEEDS-HUMAN. This converts §9 from a dated snapshot into a living contract.
- **Citation:** [canon §9] — judgments "made against Sonnet 4.6; re-audit due on model update → now Opus 4.8"; §9 "schedules a *manual* re-audit and names no automated probe." Article basis: pass1 §"cost of untested LLM behavior," §Compounding reliability; pass2 §4 ("cited constants will rot").
- **Conservative disposition:** §C DEFERRED / §D minor. Pass3 logged it as gap b2 but framed the fix abstractly ("the re-audit is a one-time human pass, not a standing behavioral-probe suite") without elevating it to a build item; MASTER-FINDINGS folded it into the general evals deferral.
- **RE-JUDGMENT under the new charter: ELEVATE.** The §9 cuts are the *engine* of the whole V2 "empower the model, remove the scaffold" thesis — and they are currently load-bearing on an undated, untriggered human promise. That is the most fragile foundation in the audit. Under the new charter the cloud scheduler removes the only real objection (durability), so a model-version-keyed probe suite is straightforwardly buildable now. Bigger by: this is not a side-test, it is the *safety interlock for the entire de-scaffolding program*. Every scaffold V2 removes should ship with the probe that justifies its removal — "remove the cage, but keep the sensor that tells you when the cage was load-bearing." Genuinely in-scope-now.

### Move: Compounding-reliability accounting + deterministic validation gates between probabilistic passes
- **Plain-English what & why:** Chained probabilistic steps multiply their failure: three 90%-reliable steps end-to-end is 0.9³ = 73%. A 9-pass review, a 23-agent roster with 4 lenses, and `/queue` running parallel worktree agents are *long probabilistic chains*. The failure prevented: each added pass/agent silently lowers end-to-end reliability, and with no deterministic checkpoint between steps a single bad pass poisons everything downstream while the chain reports success. The article's prescription is minimal LLM steps + a deterministic validation/fallback between each.
- **The mechanism:** Two parts. (1) Insert deterministic gates between reasoning passes where one is cheaply definable — e.g. after `/cr`'s auto-fix pass, a deterministic re-run of tsc/lint/vitest *before* the next pass trusts the fix; after a `/queue` agent claims done, a deterministic "did it actually push a green sentinel?" check before the orchestrator marks it complete. (2) Measure the chain: record per-pass agreement / catch rate so the team can see the real end-to-end reliability instead of assuming 9 passes = 9× confidence. This pairs with the golden-PR eval (it's the instrument that produces the numbers).
- **Citation:** [canon §3c] (9 passes + adversarial), [canon §3d] (23 agents, 4 lenses), [canon §3e] "the system is overwhelmingly advisory… no deterministic backstop for the bulk of skill bodies." Article basis: pass1 §"Compounding reliability."
- **Conservative disposition:** §C DEFERRED. Pass3 logged it as gap b3 ("long probabilistic chains with advisory-only validation between steps") but proposed no concrete mechanism and did not elevate.
- **RE-JUDGMENT under the new charter: ELEVATE (partial) — but with a sharp scope limit.** ELEVATE the *deterministic-gate-between-passes* and *measure-the-chain* parts: under "clarity beats minimalism," adding a tsc/vitest re-run gate between `/cr` auto-fix and the next pass is exactly the kind of mechanism that earns its place (it converts an advisory chain into a partially-verified one), and it's free to build. The conservative bias was treating "more validation gates" as friction; at fleet scale the friction is *silent compounding failure across parallel agents*, which is far costlier. Scope limit (honesty): do NOT over-rotate into "minimize LLM steps" — the article's "fewer steps" advice is product-latency-driven (pass2 §2: latency is an end-user UX tax there, but here it's just the developer's wait). Cutting `/cr` passes to chase 0.9ⁿ would trade *review depth* (the harness's actual world-class differentiator) for a reliability number that the deterministic gates already recover. So: add gates and measurement; do not cut passes.

### Move: Fallback obligation — every reasoning pass must have a defined low-confidence / failure behavior, designed before it ships
- **Plain-English what & why:** In a product, every LLM call must have a defined behavior on failure or low confidence (deterministic default, cached result, simpler model, non-AI path) — "return an error is not a product experience," and the fallback must be designed *before* the call is added. The harness violates this for its own reasoning steps: there is no defined behavior for what `/cr` does when a pass returns garbage, or what `/queue` does when an agent silently dies. The failure prevented: a pass or agent fails open and the pipeline proceeds as if it succeeded (the exact shape of the known "background agents fail silently" hazard, generalized).
- **The mechanism:** A standing rule + a uniform "pass result contract": every reasoning pass returns a structured result with an explicit confidence/abstention field; the orchestrator has a defined response to "pass abstained / returned malformed output" (re-run once, then escalate to NEEDS-HUMAN, never silently continue). For `/queue`: a deterministic liveness/heartbeat check so a dead agent is detected, not assumed-done. This is the article's fallback obligation lifted from product path to harness path.
- **Citation:** [canon §3c] (no defined low-confidence behavior for a reasoning pass), [canon §2 / memory "background agent Bash permissions"] (known silent-failure hazard; mitigation only addresses one cause). Confirmed absence of a general fallback spec in §3b/§3c. Article basis: pass1 §"The fallback obligation."
- **Conservative disposition:** §C DEFERRED. Pass3 gap b5 — logged as a confirmed absence but not elevated to a build item.
- **RE-JUDGMENT under the new charter: ELEVATE — and this becomes structurally critical *because* of autonomy.** The conservative reading could tolerate "agent fails silently, human notices" when a human watches every run. Under the new charter — bug→PR, Slack-summoned agents, nightly `/schedule` routines running with the laptop closed — *there is no human watching*. A silently-failed pass in an autonomous loop ships a broken PR or, worse, marks a regression as resolved. Fallback/abstention behavior is the precondition for safe unattended operation, not a nicety. Bigger by: this graduates from "nice doctrine" to "a gate on whether autonomous loops are allowed to merge anything at all." Combine with `disable-model-invocation:true` side-effect skills: a deploy/open-PR skill must check the abstention signal before firing.

### Move: The reversibility gate as the *primary* gate for any autonomous action
- **Plain-English what & why:** The article lists, almost as an aside, the production safety pattern for agentic/autonomous actions: write actions to a staging buffer before commit, require human confirmation for irreversible operations, and apply an explicit "is this reversible?" test. Pass2 §5's key insight: the article *under-ranks* this because its frame is products (which emit text for a human to read), but a harness is an agent (which *takes actions*) — so for the harness, reversibility isn't one gate among seven, it's *the* gate.
- **The mechanism:** A first-class, uniform reversibility classifier on every autonomous action the harness can take: each side-effecting skill/tool declares reversible vs irreversible; irreversible actions (force-push, DROP, prod mutation, external API writes, merge-to-main) require the existing same-turn explicit-instruction rule OR, in autonomous mode, a staging-buffer + human-confirmation step that the loop blocks on. Pairs directly with `disable-model-invocation:true` (removes irreversible skills from context unless explicitly summoned).
- **Citation:** pass1 §"is this reversible? test"; elevated in pass2 §5. Existing harness coverage: [canon §9] destructive-operation rules "keep verbatim — never remove"; [map §6, §3e] worktree + Tier-0 prod-key firewall + `block-dangerous-git/bash.sh` as the staging-buffer/backstop.
- **Conservative disposition:** §E ALREADY-BUILT. Pass3 §a: "We implement this *more* concretely than the article… We are ahead of the article here." Treated as a solved, no-gap item.
- **RE-JUDGMENT under the new charter: UPHELD-CUT (as a *new build*) — but RE-FRAME as the explicit design spine of the autonomy front-door.** Honest assessment: the *doctrine* genuinely is built and the destructive-op rules are world-class for the *interactive* case, so re-proposing a reversibility mechanism would be a phantom. The specific failure mode that keeps this from being a brand-new build: the same-turn-explicit-instruction rule already prevents the irreversible-action-without-consent failure. BUT — and this is the non-phantom part — that rule assumes a human *is in the turn*. The autonomy charter (bug→PR with no human in the turn) means the current mechanism has an untested edge: what is "explicit same-turn instruction" when the summoner is a Linear webhook? So the move is not "build a reversibility gate" (have it) but "extend the existing gate's contract to the unattended/summoned path." That extension belongs to the autonomy front-door design, sourced here, and is the one place this source's strongest idea still has unbuilt surface.

## Autonomy angle
Directly relevant, in two ways. (1) The reversibility gate (pass1 §"is this reversible?", pass2 §5) is *the* governing principle for any bug→PR or Slack/Linear-summoned agent that takes irreversible actions — the article supplies the staging-buffer + human-confirmation pattern that the autonomous front-door must implement, and the open question it forces is "what counts as consent when no human is in the turn." (2) The fallback-obligation and silent-regression doctrine become *load-bearing* under autonomy: a self-improving loop or nightly `/schedule` routine running with the laptop closed has no human to notice a silently-failed pass, so abstention/low-confidence behavior and an eval signal on the harness's own quality are preconditions for letting autonomous loops merge anything. The golden-PR eval is itself best run as a cloud `/schedule` routine. The article does not name Slack/Linear or self-improving loops, but its core doctrine is exactly the safety substrate those loops require.

## The single biggest move (one paragraph)
Build the **golden-PR evals-in-CI / behavioral-probe suite for the harness's own reasoning skills** (Move 1, with Move 2 as its model-bump trigger). This is world-class because it is the one thing that converts the harness from "a pile of prompts we hope still work" into a *measured* system: it makes every model upgrade a checked migration instead of a blind swap, it supplies the reliability numbers that the compounding-chain and fallback moves need to act on, and it is the literal feedback signal a self-improving autonomous harness cannot exist without. The conservative synthesis deferred it on a "we lack the golden set / volume" doubt that is simply wrong at harness scale — the golden corpus is a few dozen labeled diffs the team already has in git history — and on a durability doubt that the cloud `/schedule` infrastructure has made moot. AI-native companies spend 20–30% of their first budget here before they build features; our harness has spent zero, and it is now the most sophisticated *unmeasured* probabilistic system in the stack.
