## (b) REAL gaps it exposes — each with a citation

1. **No "skill rung" between memory and the skill registry — the promotion ladder dead-ends at PITFALLS.** Pass-2's export #3 and the page's own Application #2 name a missing layer: when a pattern repeats across `/compound` outputs it should become a *named skill*, not just another memory/PITFALLS line. Our promotion ladder (§4) promotes *facts* (corrections → memory → PITFALLS) but has **no mechanism to promote a repeated multi-step workflow into a new skill**. This compounds an existing, separately-cited pathology: the triple-duplication where the same fact lives in memory.md + PITFALLS + auto-memory simultaneously (§4). The skill rung is the missing *escape valve* — some repeated patterns are workflows, not facts, and forcing them into the fact-stores is part of why the fact-stores bloat. Gap is real and cites a confirmed structural shape. [as-is §4 promotion pipeline has no skill-creation step; §4 triple-duplication]

2. **The accountability principle is enforced but unnamed — and the place to name it is absent or thin.** Pass-2 export #2: the gate is permanent because it tracks accountability, not model weakness. The page's Application #3 wants it stated as the *rationale* for STOP-AND-SURFACE. Our as-is map shows the enforcement (destructive rules, merge gate) but the canon's STOP-AND-SURFACE itself is flagged for narrowing in §9 ("STOP-AND-SURFACE breadth → narrow to consequential decisions"). Naming *why* the gate is permanent is exactly what lets you narrow the *breadth* (capability-proxy STOP conditions, deletable) without touching the *accountability core* (never deletable). This is a real doc gap: the as-is map records no file that states the accountability rationale, and §9 is actively about to prune STOP-AND-SURFACE without that distinction written down. [as-is §9 "STOP-AND-SURFACE breadth … narrow"; absent: no named accountability-rationale doc in §3a governance inventory]

3. **No audit exists of whether structured task fields are actually READ at execution.** Pass-2's "what the page takes for granted" #2: structure that no agent reads is the exact "capability proxy" trap §9 warns about. The page asserts structure→quality as causation (pass-2 challenges this). Our `TASK-TEMPLATE` has fields, and `enforce-scope.sh` reads `## ALLOWED FILES` — but the map records **no evidence that the other template fields (success criteria, constraints, references) are consumed by any deterministic mechanism or reliably by the agent.** The page's own Design Challenge (audit five sessions: S/P/A spec quality vs outcome) is the right probe, and the map confirms we have never run it — the §9 audit is a *capability* audit, not a *task-spec-quality* audit. This is a confirmed absence of a measurement, not a missing feature. [as-is §9 is model-capacity audit only; absent: no spec-quality→outcome correlation recorded anywhere in the map]

4. **The "single canonical task object" assumption exposes our fragmentation.** Pass-2 "takes for granted" #1: Linear has exactly one issue object. Our map shows the task/intent surface is *spread across* TASKS.md, TASK-TEMPLATE, AGENTS.md open decisions, and the per-session ad-hoc description — with the map already flagging AGENTS.md's "None open" contradiction. There is no single typed task object; there are several partial ones. The page can't see this gap (Linear's product erased it for them), but applying its assumption to us surfaces a real coherence gap the map independently documents. [as-is §3a AGENTS.md "None open" contradiction; §5 TASK-TEMPLATE is one of several task surfaces, not the canonical one]

## (c) Weaknesses in the article's OWN reasoning

(Carried from pass 2, stated as disqualifiers for over-importing.)

- **Slogan contradicts mechanism.** "Issue tracking is dead" says the issue is obsolete; the structured-data thesis says the issue is more load-bearing than ever. The page never reconciles these (pass-2 §1). Importing the slogan would push us to *delete* task structure — the opposite of the page's real lesson.
- **Causation asserted from correlation.** "Structure → agent quality" is presented as mechanism; it is at least as consistent with "team discipline → both structure and quality" (pass-2 §2). Do not adopt "add more structure" as established cause-and-effect.
- **The load-bearing metric is a numerator without a denominator.** "60% of merged PRs" ignores abandonment/rework on delegated issues and PR-size mix; the curator raises this in Open Question #2 then builds the Synthesis as if settled (pass-2 §3). Treat 60% as "sometimes works," not proof.
- **"Skills transfer Fully" while admitting the mechanism is unknown.** Open Question #4 concedes Linear Skills might be prompt templates, sub-routines, or deterministic scripts — three different things with different transferability — yet the table rates transfer "Fully" (pass-2 §6). Over-claimed.
- **Market metrics smuggled in as mechanism evidence.** 75% of enterprise workspaces / 5x growth establish the *category* is real, not that the mechanism helps one developer (pass-2 "takes for granted" #3).
- **Codification presented as costless.** Every saved skill is also a ghost-rule / maintenance liability — the cost our §9 names (90-day ghost-rule collapse) and the page ignores. A skill rung that lacks a *retirement* rule would import the page's blind spot.
