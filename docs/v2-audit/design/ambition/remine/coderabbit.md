# Ambition Re-mine — CodeRabbit (AI-First Code Review, Reading vs. Writing & the Review Bottleneck)

## What this source is (plain English, 2-3 sentences)

CodeRabbit is the most-installed AI code-review app on GitHub (2M repos, 13M PRs, 8,000+ paying customers): it runs an automated semantic review on every PR in ~3 minutes, posting findings *on the PR itself* before a human looks. The article's operative thesis (recovered in pass2 §A) is not "AI reads code" — it is that **once agents make code generation nearly free, review becomes the conserved scarcity**, and review does not parallelize the way generation does because it terminates in one human's judgment at the gate. CodeRabbit is "a buffer that absorbs review volume so the human gate doesn't become the throughput ceiling," with its linchpin evidence being that AI-co-authored PRs draw ~1.7x more review comments per line — review cost rises *super-linearly* with agent output.

## The full-ambition moves this source teaches

### Move: Review verdict must land on the PR/CI surface, not in a local sentinel

- **Plain-English what & why:** CodeRabbit's structural advantage over our setup is *where the review output lives*. Its findings land on the pull request, in CI's view, auditable by anyone who looks at the PR — the review is a durable, inspectable artifact attached to the unit being merged. Our `/cr` does a *deeper* review (9 passes + 4 adversarial lenses) but its only durable output is a `.cr-ok` file that is gitignored and never reaches CI or the PR. The failure this prevents: a reviewer whose verdict is invisible at the merge boundary cannot be trusted, audited, or enforced — at fleet scale, a human (or another agent) glancing at a PR has no way to know whether review happened, what it found, or whether the "pass" was real. A self-reported boolean that never leaves the laptop is not a gate; it's an honor system.
- **The mechanism:** Make `/cr`'s findings a first-class PR artifact. Concretely: `/cr` writes its pass results (MUST-FIX resolved, NEEDS-HUMAN, SUGGESTION, recurring-findings delta) to a structured file that `scripts/pr.sh` posts as the PR body or a sticky PR comment, *and* a CI job that re-validates the `.cr-ok` sentinel as `branch:sha` so the PR cannot merge on a stale or absent review. This closes the Node 8.5(c) gap directly. For autonomous/cloud runs the same artifact is what a summoned-from-Slack agent reads to decide whether to merge.
- **Citation:** Ground-truth [§3f] / [canon §4]: "the Node 8.5(c) gap (CI never verifies `.cr-ok`) is a disk fact … canon's `.cr-ok` chain has the same hole (gitignored, never reaches CI)." Confirmed absence: no §3c/§3f row puts review output on the PR or in CI's view.
- **Conservative disposition:** §C-deferred / scaled-down. Pass3 (b)(1) named it precisely — "the reviewer's verdict is invisible at the PR/CI boundary" — but MASTER-FINDINGS folded it into a cautious "wiring-tweak" framing rather than a first-class move, and the article's *own* fix (run CodeRabbit on one PR) was treated as "an experiment, not research" (pass3 (d)).
- **RE-JUDGMENT under the new charter: ELEVATE.** This is the single most important move on the page and it must be in-scope-now, much bigger than a "wiring tweak." Under the AUTONOMY charter, autonomous agents — summoned from Slack/Linear, scheduled in the cloud — *cannot read a gitignored local sentinel*. A cloud `/schedule` run that clones the repo has no `.cr-ok` and no laptop to honor it; the review verdict MUST be reconstructable from GitHub (the new single source of truth). The conservative bias here was treating `/cr` as already-world-class because it is *deep*, while ignoring that depth on an invisible surface is worthless to a fleet. World-class = the review's full verdict is a queryable GitHub artifact + a hard CI gate, so any agent or human at the PR boundary can act on it. This is the bridge from "solo laptop reviewer" to "fleet-grade gate."

### Move: Calibrate the reviewer — measure `/cr`'s precision/recall against a labeled defect set

- **Plain-English what & why:** Pass2 §D and §E expose that CodeRabbit's *capability* claims ("semantic," "finds real defects") are vendor-sourced and unmeasured — only its *scale* numbers are triangulated. The exact same blade cuts us: nothing anywhere measures whether `/cr`'s findings are *good*. We don't know its false-positive rate (noise that costs the human attention) or its false-negative rate (real bugs it waves through). The failure this prevents: an always-on reviewer that is high-availability but low-precision is *noise*, and at fleet scale noise is catastrophic — every false positive on every PR across 5+ repos multiplies into a tax on the one scarce resource (human judgment) the whole system exists to conserve. You cannot improve, trust, or tune a reviewer you have never scored.
- **The mechanism:** Build the calibration harness our `@benchmark-runner` phantom promises. Assemble a labeled corpus of past PRs with known defects (seeded bugs + real historical findings from `RECURRING-FINDINGS.md` and `PITFALLS.md`), run `/cr` against it, and report precision/recall per pass and per lens. Run it on every model bump (we just moved Sonnet 4.6 → Opus 4.8 and have *never* re-scored the reviewer). The article's own Design Challenge — "(1) what it caught that you would have; (2) what it caught that you'd have missed; (3) what it missed that human review caught" — *is* the calibration protocol, applied to our own reviewer instead of CodeRabbit's.
- **Citation:** Ground-truth [§6]: "`@benchmark-runner` is a §6 phantom — 'Referenced on disk, never built.'" Confirmed absence (pass3 (b)(2)): "no calibration/benchmark of `/cr` findings anywhere in §3–§9." Pass3 (d) flags this as the *one* narrow YES for fresh external research (review-tool evaluation methodology).
- **Conservative disposition:** §C-deferred, with pass3 (d) granting it the single "narrow YES" for external research but stopping short of scoping a build. MASTER-FINDINGS did not surface it as one of the 6 moves.
- **RE-JUDGMENT under the new charter: ELEVATE.** This is in-scope-now and structural to a self-improving loop. The new charter's self-improving-loops pillar is *impossible* without measurement: you cannot run a "finding → rule → fewer findings" loop if you can't count findings or tell true from false. The conservative instinct to defer was right that it's hard, but wrong that it's optional — at fleet scale, an uncalibrated reviewer is the difference between a compounding system and an accumulating-noise system. World-class teams (the CodeRabbit/Augment/Ramp tier the charter names) score their reviewers; we score nothing. Build the benchmark harness, score `/cr` on every model bump, and gate model-upgrade adoption on the score not regressing.

### Move: Wire the governance corpus (ADRs, Rejected Patterns, PITFALLS) into the review as criteria

- **Plain-English what & why:** Pass2 §C is the source's deepest insight: CodeRabbit's blind spot is not "big PRs" — it is **memory locality**. It can reason over {the diff} ∪ {code-graph neighbors} ∪ {real-time web} but *cannot* reason over {historical design decisions, locked architectural choices, team conventions}. That second set is exactly what a governance layer encodes: our `CLAUDE.md`, `AGENTS.md` Rejected Patterns / Open Decisions, `docs/adr/`, `PITFALLS.md`. A migration that violates a locked ADR, a role-check placed in RLS (an *explicitly rejected* pattern), a schema-file/folder collision (a known PITFALL) — these are diff-local in *text* but governance-global in *meaning*. The failure this prevents: a reviewer that re-litigates settled decisions or silently lets a PR violate one. Crucially, pass2 §C shows this is *also our latent limitation* unless explicitly closed — `/cr`'s governance-awareness is *asserted, not wired*.
- **The mechanism:** Feed the locked-decision corpus into the `/cr` passes as explicit review criteria. Concretely: a pass (or a lens) whose input is `docs/adr/` decisions + `AGENTS.md` Rejected Patterns + `PITFALLS.md` entries, instructed to flag any diff hunk that contradicts a locked decision and cite the specific ADR/pattern. This is *the* move that makes our in-process reviewer categorically better than any SaaS reviewer — CodeRabbit *structurally cannot* do it (it has no access to our durable memory), and we have the corpus sitting right there, currently unused as review input.
- **Citation:** Ground-truth [§5] lists `docs/adr/` as a knowledge store; [§4] documents `PITFALLS.md` and the promotion lifecycle. Confirmed absence (pass3 (b)(3)): "no §3c/§4 row wiring ADR/Rejected-Patterns into review … the locked-decision corpus is not demonstrably an input."
- **Conservative disposition:** §C-deferred. Pass3 (b)(3) named it as "the one place CodeRabbit's limitation is *also our latent limitation* unless explicitly closed," but it was not promoted to a move in MASTER-FINDINGS.
- **RE-JUDGMENT under the new charter: ELEVATE.** This is the highest-leverage, most-defensible move the source teaches and it is in-scope-now. It is the precise thing that converts our reviewer from "a local copy of CodeRabbit" into "a reviewer no SaaS tool can replicate," because the moat is our durable project memory. With GitHub becoming the single source of truth, the ADR/Rejected-Patterns/PITFALLS corpus *is* the canon — wiring it into review is also what enforces canon at the merge boundary. The old framing ("asserted, not wired") correctly diagnosed the gap but deferred the fix; at fleet scale across 5+ repos with their own ADRs, a governance-aware reviewer is what keeps each repo's locked decisions enforced without a human re-checking them. Build it as a dedicated `/cr` lens with the locked-decision corpus as its input.

### Move: Close the compounding loop — review stream as a sensor that auto-promotes to enforcement

- **Plain-English what & why:** Pass2 §G names the closed loop the article leaves open. A reviewer that runs on *every* PR is a **sensor producing a labeled stream of recurring defect types** — exactly the input a compounding-knowledge layer wants. The article (Candidate-2) stops at "manually promote the top 3 findings to PITFALLS." The real insight: without a *closed* loop (finding → rule → enforcement → fewer findings of that type), the analytics are just a dashboard. The failure this prevents: a knowledge layer that accumulates observations but never converts them into mechanisms that stop the observed failure from recurring — you keep re-finding the same bug forever instead of making it impossible.
- **The mechanism:** We already have the *open half*: `RECURRING-FINDINGS.md` is auto-counted by `/cr` Step 3b, and the promotion path `memory.md → RECURRING-FINDINGS → (human-confirmed) → PITFALLS.md` exists [§4]. The missing closing move is the *last arc*: when a finding type crosses a threshold and is promoted to `PITFALLS.md`, generate an *enforcement* artifact where possible — a deterministic hook, a lint rule, or a new governance-lens criterion (feeds the move above) — so the next occurrence is *blocked*, not merely re-counted. This is the self-improving loop the charter wants, grounded in a sensor that already exists.
- **Citation:** Ground-truth [§4]: "`RECURRING-FINDINGS.md`, auto-counted by `/cr` Step 3b … promotion: pipeline→RECURRING-FINDINGS→(human-confirmed)→PITFALLS." Confirmed absence: no row closes finding→enforcement; the loop terminates at a human-read doc. Pass2 §G: "without a closed loop … the analytics are just a dashboard."
- **Conservative disposition:** §E-already-built (partial). Pass3 (a) claims "ours closes *more* of the loop than the article's manual 'promote top 3'" and treats the promotion lifecycle as essentially done. Pass2 §G disagrees: the loop's last arc (finding → *enforcement*) is open.
- **RE-JUDGMENT under the new charter: ELEVATE.** Pass3's "already-built, closes more of the loop" is exactly the §E conservative trap the charter warns against — it set the bar at *existence of a promotion path*, not at a *closed* compounding loop. We have a counter and a human-read doc; we do *not* have the arc that turns a recurring finding into a mechanism that prevents recurrence. That arc is the literal definition of "compounding" and of "self-improving loops" (a named charter pillar). At fleet scale this is the difference between a harness that gets smarter every PR and one that just keeps a tally. Build the finding→enforcement arc; it composes directly with the governance-lens move (the generated criterion *is* an enforcement artifact).

## Autonomy angle

Yes — this source is more autonomy-relevant than its conservative read admits, on three fronts:

1. **CodeRabbit Agent for Slack** (pass1, marked Verified): "stale-PR nudges, weekly ship briefs, incident triage." This is a *direct* instance of the charter's Slack-summon and self-improving-loop pillars — an agent that proactively pings on stale PRs and triages incidents from a chat surface. The conservative read filed it under "review routing → does NOT transfer (solo dev routes to Tanner anyway)." Under the fleet charter that dismissal fails: a fleet across 5+ repos *needs* stale-PR nudges and ship briefs surfaced to Slack precisely because no human is watching 5 repos' PR queues. This is a NEW first-class candidate the synthesis summarized away.

2. **Review-as-PR-artifact is the enabling substrate for bug→PR autonomy.** An autonomous bug→reviewed-PR pipeline (the charter's headline) *requires* the review verdict to be a GitHub artifact, not a laptop sentinel — see Move 1. Without it, an autonomous agent has no way to assert "this PR was reviewed and passed." So this source's biggest move is load-bearing for the entire autonomy front-door.

3. **The 1.7x-comments fact is the economic case for autonomous review.** If agent PRs cost ~1.7x more review per line and a fleet multiplies PR volume, then *human* review cannot scale with the fleet — the review buffer itself must be autonomous and land its verdict on the PR. This is the quantified justification for designing review autonomy in, not deferring it.

## The single biggest move (one paragraph)

**Make the review verdict a first-class GitHub artifact + hard CI gate (Move 1), and use that surface to wire in the governance corpus (Move 3).** The vision synthesis should pick this up first because it simultaneously (a) closes the confirmed Node 8.5(c) gap where `/cr`'s deep review dies in a gitignored sentinel CI never sees, (b) is the *enabling substrate* for every autonomy pillar — a Slack/Linear-summoned or cloud-scheduled agent can only act on a review it can read from GitHub, never from a laptop sentinel, and (c) is the one thing that makes our in-process reviewer categorically superior to CodeRabbit rather than a weaker local clone: CodeRabbit *structurally cannot* see our locked ADRs, Rejected Patterns, and PITFALLS (pass2 §C, its memory-locality blind spot), while we have that corpus sitting unused and need only feed it in as review criteria. CodeRabbit teaches that depth without a visible, auditable, enforceable surface is worthless at scale; we have the depth and lack the surface — building it is the world-class move, and it is the precondition for autonomous review across a fleet.
