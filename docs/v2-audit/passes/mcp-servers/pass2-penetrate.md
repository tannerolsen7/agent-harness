# Pass 2 — Penetrate: deeper thesis, hidden assumptions, contradictions

Building on pass1: the comprehension pass captured three layers — (i) MCP demystified as a runtime-discovery adapter [pass1 "Core thesis", "MCP vs REST"], (ii) the build-effort/security mechanics [pass1 "Mechanics", "What it takes", "Security surface"], and (iii) the article's own event-vendor verdict [pass1 "Application", "Standing rule"]. This pass works underneath those to find the load-bearing thesis, the assumptions the author never states, and where the piece argues against itself.

## 1. The real thesis is narrower than "what is MCP" — it's an asymmetry argument
The surface promise is demystification, but the actual claim doing the work is an **asymmetry between consuming and producing** [pass1 "Core thesis", "Application"]. Consuming MCP is framed as near-zero-risk and high-leverage; producing it is framed as a security liability gated behind validated demand. The whole article is an argument for **staying on the safe side of that asymmetry**. Demystifying the protocol is the *on-ramp*, not the point. This matters because it means the piece is not really teaching "how to build an MCP server" — it is building the case for *not* building one yet, and the technical content is marshalled toward that conclusion. A reader should notice the persuasive shape, not just the explanatory shape.

## 2. The hidden premise behind "consuming is near-zero exposure"
Pass1 recorded the claim that consuming Supabase/Playwright/Notion MCP is "near-zero security exposure because these run locally under your own credentials" [pass1 "Application"]. **This is the article's softest spot and it is unexamined.** The lethal-trifecta logic the article itself wields against *building* applies, unmodified, to *consuming*:
- A consumed MCP server the agent uses (Supabase MCP) gives **(1) access to private data** (the prod DB — and the canonical map confirms `.env.local` points at *production* Supabase).
- A consumed Notion/Playwright server can pull in **(2) untrusted content** (a scraped page, a Notion doc authored by someone else, a tool's own poisoned description).
- A consumed server with a write tool (Supabase `execute_sql`, Notion `create-page`) provides **(3) egress / mutation**.
So "consuming is safe" is true *only* because of a discipline the article never names: the human-in-the-loop approval and the read-mostly posture. The author treats "runs under your own credentials, locally" as the safety property, but **credentials-under-your-own-name is exactly the confused-deputy condition, not a mitigation** [pass1 "Security surface — confused deputy"]. The trifecta does not care who owns the credential; it cares whether one agent has all three legs. The article applies its sharpest tool asymmetrically — rigorously to the build decision, leniently to the consume decision — and the asymmetry is unjustified. Net-new: **the consume side needs the same trifecta audit the build side gets**, and the article's own logic demands it.

## 3. "Break the trifecta — remove one leg" is presented as simpler than it is
Pass1 captured the design rule "break the trifecta — remove one leg" as the article's headline mitigation [pass1 "Security surface", "Application"]. Underneath, this is harder than the one-liner implies, and the article never says which leg is actually removable for event-vendor:
- Removing leg (1), private data: a proposal tool that can't see client data is useless — non-removable for the product's purpose.
- Removing leg (3), egress: a `create_proposal`/send tool that can't send is useless — non-removable for the *demand* that would justify building.
- That leaves only leg (2), untrusted content, as removable — but the article itself lists the untrusted inputs (client free-text brief, scraped venue page) as *core product inputs* [pass1 "Application"]. You cannot build the proposal product Monica needs *without* ingesting client free text.
So "remove one leg" collapses, for this exact product, to "the one removable leg is the one the product is made of." The honest conclusion the article gestures at but doesn't state plainly: **for a client-facing proposal agent, the trifecta cannot be cleanly broken by removing a leg — it can only be managed by hard isolation between the reading agent and the sending agent.** The article's own "no external egress from the same agent that reads private data" [pass1 "Application"] is actually a *fourth* strategy (split the agent), not "remove a leg" — and that distinction is buried.

## 4. A genuine contradiction with the keep-it-small doctrine
The article's quality guidance says **"build few, high-impact tools"** like `search_clients`/`create_proposal` over raw `list_rows` [pass1 "What makes a good server"]. But its security verdict says those *exact* high-impact tools are the trifecta problem [pass1 "Application"]. So the article simultaneously holds: "the *right* design is coarse, intent-level tools" and "the *right* coarse tools are the dangerous ones." These aren't contradictory in logic, but the article never reconciles them into guidance. The reconciliation it's missing: **coarseness that's good for the model (one intent-level tool) is bad for the blast radius (one tool = read + decide + send fused).** The "code execution with MCP" insight (tools as an imported code API) [pass1 "What makes a good server"] is actually relevant *here* and the article doesn't connect it — a code-API surface can interpose a deterministic gate between read and send that a single coarse MCP tool cannot.

## 5. What the author takes for granted
- **That "agent consumer" is a binary.** The decision criteria [pass1 "Hype vs real"] treat "a non-deterministic agent will consume this" as yes/no. But event-vendor's own harness *is* a fleet of non-deterministic agents (the `/queue`, sub-agent, background-agent machinery in the canonical map). The article never asks whether event-vendor's *internal dev agents* are themselves the agent consumer that would justify a *dev-facing* (not customer-facing) MCP server — a category it skips entirely.
- **That building means customer-facing.** Every build scenario in the article is external (customers driving from their own Claude; an in-app assistant) [pass1 "Application"]. It never considers an MCP server whose only consumer is the team's own coding agents — which would have a totally different trifecta profile (no customer egress) and is the one variant the author's own framework would rate most favorably.
- **That the SDK-does-the-protocol claim removes protocol risk.** Pass1 noted "you never hand-write JSON-RPC; the SDK does it" [pass1 "Mechanics"]. The unstated assumption is that the SDK is trusted. The rug-pull and supply-chain dimension the article raises for *tool descriptions* [pass1 "Security surface"] applies equally to the *SDK and the MCP server packages themselves* — a dependency-trust surface the article omits.

## 6. The hedge on the scary numbers is a tell about epistemic discipline (and is the right move)
Pass1 flagged that the article self-tags the MCPTox 60–72% and "8,000+ exposed servers" figures as reported-not-confirmed [pass1 "Security surface — verification flags"]. Net-new read: this is the article being honest in a way most MCP-security writing is not — the genre is saturated with these exact unverified stats cited as fact. The author *uses* the security argument while *refusing to lean on the unverified scare numbers*, which means the verdict ("defer building") survives even if those numbers are wrong, because it rests on the structural trifecta argument, not on the prevalence stats. **The argument is robust to its own weakest evidence** — a deliberate construction worth preserving when this feeds a harness decision.

## 7. What this is really about for a harness redesign
Stripped down, the article delivers two reusable instruments and one verdict:
- **Instrument A — the two-question gate** [pass1 "Standing rule"]: (Q1) will a non-deterministic agent actually consume this, or is REST/SDK simpler? (Q2) does this give one agent private data + untrusted input + egress? This is a *decision procedure*, not just an opinion — it can be encoded.
- **Instrument B — the trifecta as a design invariant**, applicable to *any* tool surface the harness exposes or consumes, not only to a hypothetical built server.
- **The verdict** (consume/defer) is event-vendor-specific and time-bound; it will expire when a validated demand appears.
For a harness audit, the instruments are the durable yield; the verdict is a snapshot. Pass 3 should test whether the harness already encodes Instrument A/B anywhere, and whether the *consuming* side (which Pass 2 shows the article under-polices) is governed at all — because that, not the unbuilt server, is where event-vendor's live exposure actually is today.
