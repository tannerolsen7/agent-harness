### DROPPED nuance

1. **The runtime-vs-render *category-gap distinction* is lost at the design level.** Ashby's single
   load-bearing contribution is that `/p/[token]`'s `error.tsx` *renders a fallback but records
   nothing* — so the missing piece is a runtime failure-*signal*, a different category from the
   pre-merge render check, not a thicker version of it [pass3 §b1; cluster-findings-1.md:77–83].
   That precision survives only in the **intermediate** cluster file. By the time it reaches the
   design layer it is folded into MOVE 1's "render/visual-output gate" (the pre-merge half) plus a
   one-line §C deferral "visual render gate full build [C1-G4b]" [MASTER-FINDINGS:38,127]. No
   phase3/phase45/phase6 reconciliation preserves the runtime-≠-merge-time framing or names the
   "boundary renders, nothing logs" insight. **Where it should go:** the §C deferral row for
   C1-G4b in MASTER-FINDINGS (and/or the phase45 compounding-loop, since a runtime failure-signal
   is a *write-back* source) should carry one line: "runtime failure-logging behind the error
   boundary is a distinct *category* from the pre-merge render gate; defer the Supabase error-log
   table + feature-flag column as a build-plan decision." **Why it matters:** without it, a future
   builder reading §C will treat C1-G4b as "the screenshot gate, fuller" and may never build the
   runtime error-log table — which is the one genuine category gap the whole Ashby audit exists to
   surface, and the one signal a silently-broken render for a $30k client would otherwise leave
   nowhere for an agent or human to act on.
