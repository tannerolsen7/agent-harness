# Ambition Re-mine -- Commands vs. Skills: Authoring, Triggering & Where They Sit

## What this source is (plain English, 2-3 sentences)

A piece written specifically for this harness arguing that the old "should this be a slash command or a skill?" question is now obsolete: in current Claude Code, custom commands and skills run on one unified machinery, so a "command" is just the simplest form of a skill (a bare prompt with no auto-trigger). It then isolates the *two* decisions that actually still change behavior -- **who decides when a capability runs** (you, via an explicit `/name`, vs. the model, via a `description` it matches against) and **how much of it sits in always-loaded context** (progressive disclosure: ~100 tokens for name+description until a task matches, then the body, then bundled references/scripts). Its core contribution is recovering, from those two axes, a control vocabulary expressed almost entirely in YAML frontmatter (`disable-model-invocation`, `user-invocable`, `context: fork`, `paths`, `allowed-tools`) plus a `description` string.

## The full-ambition moves this source teaches

### Move: Invocation control as a first-class, structural property of every capability (`disable-model-invocation` and the full frontmatter control surface)

- **Plain-English what & why:** Every skill now carries a YAML flag that decides *who is allowed to start it*. With `disable-model-invocation: true`, the model literally cannot auto-trigger the skill -- the skill leaves the model's context entirely; only a human (or an explicit `/name` call) can fire it. The inverse, `user-invocable: false`, makes a skill model-only background knowledge. `context: fork` + `agent:` runs a skill as an isolated subagent. The failure this prevents is the agent "deciding to deploy because the code looks ready" -- model judgment leaking into side-effectful or irreversible actions that a human should gate. Crucially for V2: this is the exact mechanism that makes **autonomy safe**. You can hand a fully autonomous loop a big toolbox and still guarantee it can never *itself* invoke deploy/force-push/migration-apply, because those skills are physically removed from its decision surface.
- **The mechanism:** Audit all 26 skills and assign each an activation tier. Reversible side-effect skills (`/queue` opening a PR, `/cr`, `/feature`) get `disable-model-invocation: true` so they stay human-summoned. Background-knowledge skills (`/supabase`, `/explain`) can stay model-invoked with sharp descriptions. The autonomy-relevant payoff: any skill that performs an irreversible side effect gets `disable-model-invocation` so an autonomous loop sees a safe toolbox -- this is the frontmatter half of the "autonomous car, not the cage" design, paired with a PreToolUse kill-gate for the execution half.
- **Citation:** Confirmed absence -- `[verified in pass3(b)(2)]` "0/26 skills use `disable-model-invocation`, `user-invocable`, `paths`, or `context: fork`; frontmatter is `name`+`description` only." Ground-truth §3e/§5 records the missing execution-side guard (`block-dangerous-bash.sh`, ABSENT on disk) that this pairs with.
- **Conservative disposition:** Partially-applied, scaled-down. MASTER-FINDINGS folded it into **MOVE 2** ("0/26 invocation-control frontmatter" at line 82) and §G bounded-check #2 (verify the schema before writing). But it bounded the flag hard via pass2 §2.4: "the flag is a *trigger-gate* (governs who starts the skill), not a *kill-gate*... For **reversible** side effects the flag is the correct tier and a cheap, real win. For **irreversible** ones the structural backstop belongs in a PreToolUse guard." The synthesis treated `disable-model-invocation` as a minor frontmatter hygiene item, never as the **enabler of autonomy**.
- **RE-JUDGMENT under the new charter: ELEVATE.** The trigger-gate-vs-kill-gate distinction is correct and should be kept -- but the conservative framing missed the *headline*. Under the old "defer the trigger front-door" charter, `disable-model-invocation` was just tidy frontmatter for skills a human already types. Under the new charter where **autonomy is first-class** and **cloud /schedule exists**, this flag is the single mechanism that makes the entire autonomy program safe to ship. An autonomous bug-to-PR loop or a scheduled cloud run is only responsible if the irreversible skills are removed from the model's invocation surface. So this is not "add a flag to /queue"; it is "design the activation tier of all 26 skills as the safety substrate for autonomy" -- a foundational MOVE, co-equal with the bash kill-gate, not a hygiene footnote. The KEY RESOLVED FACT confirms it: "disable-model-invocation:true removes a skill from the model's context entirely -> makes side-effect skills (deploy, open-PR, send-Slack) safe. This is what makes autonomy safe." The conservative synthesis had this fact in front of it and still filed it under MOVE 2 plumbing.

### Move: Rewrite every skill description as a *situation*, not a phrase-key (situational triggering)

- **Plain-English what & why:** The `description` field is the *only* place the model looks when deciding whether to load a skill -- the body is invisible at activation time. Today our descriptions are keyword lists ("Use when the user says '/cr', 'run a code review', 'review this branch'"), which games the matcher rather than describing reality. The world-class form names the *situation*: "after a branch's review completes," "when more than three exploratory searches are needed to understand a change." The failure this prevents: skills that should auto-fire don't, because the triggering situation never literally matched a hard-coded phrase -- and the agent that "doesn't spawn sub-agents unprompted" is exactly this failure (the spawn condition lives in inert body prose, not the description).
- **The mechanism:** Rewrite all 25 populated descriptions from phrase-keys to situational statements. Move every sub-agent spawn condition (Explore on >3-query exploration, security-reviewer after `/cr`, parallel spawns for independent tasks) *into* the description as a situation, since body text is inert at trigger time.
- **Citation:** Ground-truth §9 (Model Capacity Audit) -- "Phrase-keyed skill descriptions -> 'trigger should be the situation, not the words'" listed as a capability proxy to **replace**. Plus `[verified in pass3(b)(1)]`: the live `/cr` description is literally trigger-words.
- **Conservative disposition:** Fully-applied, and correctly so. This landed in MOVE 4 (the §9 re-audit, line 89: "every phrase-keyed trigger... is a candidate cut") and was explicitly carved out in §F reject-as-literal: the article's *own* "front-load trigger-words" Standing Rule was rejected because it IS the §9 anti-pattern, replaced by "situational triggers." pass2 §2.3 flagged this as "the article's most consequential unforced error."
- **RE-JUDGMENT under the new charter: ELEVATE (in priority, not in correction).** The synthesis got the *direction* right -- situational over phrase-keyed -- and that judgment holds at world-class scale. What the conservative framing under-weighted: at parallel-fleet scale across 5+ repos, situational triggers are not a polish item, they are **the reliability substrate of autonomous activation**. An autonomous loop that summons sub-agents, picks the right review skill, and self-routes work depends entirely on descriptions that describe the real situation -- a fleet of agents matching against keyword soup will mis-route at volume. So keep the correction exactly, but elevate it from "a §9 cleanup row" to "a precondition for trustworthy autonomous and parallel activation." Not a re-judgment of the conclusion; a re-judgment of its rank.

### Move: Tier knowledge by trigger-existence -- load-tiering / progressive disclosure as an architecture, not a line-count diet

- **Plain-English what & why:** Always-loaded files cost their full length in every session for every agent; a skill costs ~100 tokens until its description matches. The sharp principle (which the article fumbles and pass2 §2.5 recovers): tier-1 (always-loaded) is for content that must shape behavior *before any task-matching can occur* and therefore **has no natural trigger** -- the destructive-operation rules, "honest assessment over validation," the discipline checkpoint. Triggerable content (PITFALLS: "read before writing code in an affected area") belongs in tier-2/3. The failure this prevents is two-sided: paying tier-1 cost for triggerable content (context bloat that degrades every agent), *and* the inverse danger the article ignores -- demoting no-trigger safety content into a tier that only loads on match, so it never loads when an unprompted destructive command arrives.
- **The mechanism:** Audit the 799-line always-loaded root (CLAUDE.md 325 + AGENTS.md 474) by trigger-existence, not length. Demote the triggerable duplicated stores (PITFALLS.md, RECURRING-FINDINGS.md) toward tier-2/3 on-demand references; **keep** the no-trigger safety floor (destructive-op rules, §9 keep-verbatim content) in tier-1 regardless of length.
- **Citation:** Ground-truth §4 (PITFALLS/RECURRING-FINDINGS/memory.md triple-duplicated, "both sanctioned and forbidden") + §9 (keep-verbatim safety content that must NOT move). `[verified]` 799-line root is exact.
- **Conservative disposition:** Applied, with the article's literal form rejected. MASTER-FINDINGS MOVE 3 (line 82-83: "tier by *trigger-existence*, not line-count") absorbed it; §F rejected "shrink root to 200 lines" as "a line-count fetish." This was handled well and honestly.
- **RE-JUDGMENT under the new charter: UPHELD-CUT on the "200-line target," ELEVATE nothing further.** The "shrink to 200 lines" instruction genuinely deserves cutting, and the named failure mode is precise and survives at fleet scale: **blindly shrinking the root risks demoting no-trigger safety content (destructive-op rules) into a tier that only loads on description-match -- i.e., it never loads at the exact moment an unprompted destructive command arrives.** That failure mode is *worse* at world-class scale: a parallel fleet of autonomous agents running scheduled cloud jobs is precisely where an unprompted-destructive-command guard must be unconditionally present. So I uphold the cut of the line-count target and keep the trigger-existence principle as-is. The conservative treatment here was rigor, not timidity. (One honest note: the trigger-existence audit *itself* should be elevated in scope -- it is the lens for the whole context-engineering pass, not just the PITFALLS row -- but the synthesis already treats it that way in MOVE 3.)

### Move: Plugin-as-package as the distribution unit (skill = authoring format, plugin = distribution format)

- **Plain-English what & why:** A plugin is the installable unit -- a directory with a `.claude-plugin/plugin.json` manifest bundling skills, commands, agents, hooks, and `.mcp.json` into one versioned, namespaced, marketplace-installable package. The failure it prevents: template-copy drift -- when every repo holds a hand-copied folder of harness files, they silently diverge and nothing updates them. A plugin is version-pinned and `/plugin update`-able, so the behavioral harness travels as one released artifact and pulls fixes down.
- **The mechanism:** Package the behavioral harness (skills + agents + hooks + MCP config) as a Claude Code plugin published to a marketplace.json on a git repo; install via `/plugin install`; update via `/plugin update`. Pair with a thin `/init` template for per-repo project-owned files, since a plugin physically cannot carry permissions/settings.json.
- **Citation:** Ground-truth §8 ("the harness has never been installed anywhere but event-vendor; 'Multi-project' is a goal, not a state") + §2 (other repos carry no harness). Confirmed absence: no installable/shared unit exists.
- **Conservative disposition:** DEFERRED / sequenced-behind-convergence, and the *vehicle* was tilted away from plugin. MASTER-FINDINGS MOVE 5 chose a **GitHub template repo** ("Claude Code only, one install path... *then* add Cursor/npx/UI"), gated on "**converge canon<->disk FIRST**," citing pass2 §2.7: "you cannot version-distribute a harness whose own canon and disk are in bidirectional drift." Plugin was demoted to "the §8 endpoint, not a near-term build." It survives only as Open Question #1 (line 212: "GitHub *template repo* (canon-locked) vs. Claude Code *plugin + marketplace*").
- **RE-JUDGMENT under the new charter: ELEVATE.** The KEY RESOLVED FACTS settle the open question against the conservative lean: "Distribution = plugin + marketplace (portable mechanism) + thin /init template (per-repo files). A plugin physically can't carry permissions." The conservative synthesis hedged between template-repo and plugin and *leaned template* because it was written before the plugin-marketplace maturity it itself notes (line 218: "the canon's template-repo plan (2026-05-18) predates plugin-marketplace maturity"). Under the new charter the plugin is the answer, full stop, and it is *bigger* than the synthesis allowed because plugins also supply the Phase-4/5 "pull updates down" self-improving path the template plan explicitly defers (line 215-216). The "converge-first" precondition is real and should be honored as sequencing -- but it does not change the *destination*, and the conservative framing let a true precondition shade into picking the weaker vehicle. ELEVATE: commit to plugin+marketplace as the distribution architecture now (build after convergence), not as a deferred endpoint to be decided later.

## Autonomy angle

This source is, on re-read, **one of the most autonomy-load-bearing in the corpus** -- even though the conservative synthesis surfaced none of that. `disable-model-invocation: true` is the precise mechanism named in the KEY RESOLVED FACTS as "what makes autonomy safe": it removes side-effect skills (deploy, open-PR, send-Slack) from the model's context entirely, so a fully autonomous loop -- bug-to-PR, Slack/Linear summon, self-improving cycle, scheduled cloud run -- can be handed a large toolbox while being structurally unable to *itself* invoke an irreversible action. The situational-trigger rewrite is the reliability substrate for autonomous *activation* (an autonomous agent self-routing to the right skill/sub-agent depends on descriptions that match real situations, not keyword soup). And the plugin-as-package move is what lets the self-improving harness *distribute and update itself* across a fleet (`/plugin update` is the pull-down path). The source does not itself describe a bug-to-PR classifier or a Slack front-door, but it supplies the **safety and activation primitives that any of those front-doors must be built on**.

## The single biggest move (one paragraph)

**Treat `disable-model-invocation` (and the full activation-control frontmatter surface) as the safety substrate for autonomy across all 26 skills -- not as frontmatter hygiene for skills a human already types.** This is the move the synthesis most under-read: it correctly noted the flag is a trigger-gate, then filed it under MOVE 2 plumbing and a 10-minute schema check, missing that this single YAML field is exactly what the resolved charter calls "what makes autonomy safe." Pairing per-skill activation tiers (irreversible side-effect skills removed from the model's invocation surface) with the already-owed `block-dangerous-bash.sh` execution kill-gate (§5) gives the two-tier safety design -- trigger-gate + kill-gate -- that lets V2 hand an autonomous, scheduled, fleet-scale agent a big toolbox without it being able to deploy, force-push, or apply a migration on its own judgment. That is the "build the autonomous car, not the cage" design made concrete in mechanism, and it should be elevated to a foundational autonomy MOVE, co-equal with the kill-gate, rather than a sub-bullet of context hygiene.
