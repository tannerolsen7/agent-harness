# Pass 3 — Apply to OUR harness

Building on pass2: the durable, vendor-neutral residue of the Vercel piece is (i) the
**verification-loop thesis** — an agent is only trustworthy if it can observe the real
consequence of its own change and be *gated* on that observation; (ii) the **two-question
kill-filter** for whether to automate a task (state correct-output Q3; state the human-only
step Q4); and (iii) the architectural diagnosis that **agent work is long-lived/blocked and
session-bound execution is the wrong shape**. I map only these against
`CANONICAL-HARNESS-AS-IS.md`. Every gap cites a ground-truth row or a confirmed absence.

## (a) What we ALREADY do

- **Bounded-task, verifiable-output discipline is already the harness's spine.** Pass2's kill-filter (Q3 "what does correct look like") is encoded in CLAUDE.md's "define inputs, outputs, what it must NOT do, and what done looks like" and the TDD-first rule for pure functions. The ground-truth map confirms the skill layer is built: `/tdd`, `/cr`, `/feature`, `/dev` are all present on disk [canon §3b "On disk AND in canon, aligned"]. The article's Q3 is not a new idea here; it is our `done looks like`.
- **Human-judgment-stays-human (pass2 Q4) is already enforced structurally.** The destructive-operation rules (no irreversible op without explicit same-turn instruction) and the `human-checkpoints-complete` gate the article itself praises are live. The canon's keep-list explicitly protects exactly this: "Destructive-operation rules (PocketOS)… never remove" [canon §9, Keep verbatim]. The article's Q4 filter is our PocketOS rule generalized.
- **The deployment/verification *infrastructure* exists.** CI runs tsc+lint+vitest on every PR and push [canon §3f, `ci.yml` + `integration.yml`]; pre-push runs build + integration tests. event-vendor runs on Vercel, so per-commit preview URLs already exist — the article's "fully, as a user" claim is correct at the platform layer.
- **Skill-discovery-before-authoring is partially native.** CLAUDE.md mandates skimming `docs/solutions/README.md` and `docs/adr/README.md` before designing — a check-what-exists-first discipline analogous to the article's skills.sh inventory step, sourced internally rather than from a package manager.
- **Upstream skill packs are already installed.** The article's skills.sh recommendation ("install best-practice packs from Vercel, Anthropic, Trail of Bits") is *already done in spirit*: 15 Matt-Pocock/Supabase/Vercel skills are symlinked at `~/.agents/skills/` via `mattpocock/skills` (`.skill-lock.json`, v3) [canon §1 Global-skills row; §2]. We already consume an external skill ecosystem.

## (b) REAL gaps it exposes (each cites a ground-truth row or confirmed absence)

1. **The verification loop is NOT closed for UI/rendered output — confirmed absence of a render-gate.** Pass2's central indictment: a preview URL no agent opens, asserts against, and gates on is a dead artifact. The ground-truth map's enforcement inventory (§3e Hooks) lists *no* hook, and §3f no CI step, that verifies rendered output — every gate is tsc/lint/vitest/build, i.e. code-shape, never live-render. The map also states the system is "overwhelmingly advisory… no deterministic backstop for the bulk of skill bodies" [canon §3e Net enforcement picture]. So "agent confirms the changed view renders before marking done" has **no enforcement surface today** — it would be advisory prose, the exact failure mode §3e names. This is a genuine gap: a manual-QA / visual-verification *gate* is absent from §3e/§3f. (Note: the canon already keeps "the manual-QA coverage blocker" on its never-remove list [canon §9], so the *principle* is sanctioned but the *enforcement* is unbuilt.)

2. **No agent browser access wired into the contract — confirmed absence.** The article's candidate explicitly "requires Chrome MCP" and asks "does the compound agent have browser access?" The ground-truth map's global config inventory lists only the `notion` MCP [canon §2: "mcpServers={notion(http)}"]; no Chrome/browser MCP appears anywhere in the canon or disk inventory. Confirmed absence → the render-gate in gap 1 is currently impossible to execute, not merely unwired. Any V2 proposal here is a §5-style "build it" with a real dependency.

3. **Execution is session-bound; the non-blocking-checkpoint primitive is absent.** Pass2 isolated the vendor-neutral diagnosis (agent work is long-lived/blocked; session-bound is wrong-shape). The ground-truth map has no scheduler, queue, or fire-and-resume mechanism in any layer: §3e hooks are synchronous event guards, §3f scripts are one-shot, and the memory model §4 is read/write-at-session-boundaries. The `human-checkpoints-complete` gate exists but, per the article's own concession, blocks the session while waiting. Confirmed absence of any pause/resume execution primitive → this is a real architectural gap, but per pass2 it is a *harness-execution-model* gap, NOT "adopt Vercel Workflows." Disposition leans horizon, matching the map's bias to "build the simplest thing."

4. **skills.sh exposes an UNGOVERNED trust boundary we already straddle.** Pass2: installing a skill = installing privileged instructions that steer agent judgment; blast radius is the agent's behavior, not its dependency tree. The ground-truth map shows we *already* pull skills from an external ecosystem (15 symlinked Matt-Pocock skills, a `/tdd` project-fork that "has diverged… two copies, no sync") [canon §1; §3b]. There is **no provenance, pinning-with-review, or trust policy** for externally-sourced skills anywhere in the map. The map flags the coupling as a risk ("project structure is being pulled toward an upstream ecosystem's expected layout") but records no governing control. So the article's open question (supply-chain risk for agent skills) maps to a confirmed absence in *our* harness, independent of whether we ever touch skills.sh. This is the article's most useful contribution to the inner loop.

5. **The "what do you hate most?" candidates the article names are partly phantom — citation matters.** The article proposes turning TASKS.md maintenance, PITFALLS.md updates, and changelog entries into skills/sub-tasks. Against the map: PITFALLS promotion is already specified (pipeline→RECURRING-FINDINGS→PITFALLS, ≥3 or by judgment) [canon §4], and memory capture is the relevant automation — but the canon's `session-end.sh` Stop-hook that would auto-propose memory candidates is **absent on disk** ("disk's memory is fully manual") [canon §3e session-end row; §5]. So the genuinely actionable "boring task worth automating" the article gropes toward is *already a named canon-only build item*: the memory-capture hook. The article reaches the right instinct (automate the tedious memory/findings bookkeeping) but doesn't know our map already has the row. This is a real gap — but it is §5's `session-end.sh`, not a net-new skill.

## (c) Weaknesses in the article's OWN reasoning

- **Infrastructure-existence conflated with loop-closure.** Pass2 established this: "for event-vendor this is already solved" is false in the sense that matters — the platform owning a preview URL says nothing about whether the *harness* gates on it. The article repeatedly reasons in capabilities-provided, never enforcement-wired, because it is written from the vendor's side.
- **Recommends installing from an ecosystem it has just flagged as a supply-chain risk** (skills.sh "low-effort to try" in Application vs the unanswered quality-control open question). Internal contradiction; the safe move is provenance-first, which the article never states.
- **Headline metrics vs its own open questions contradict.** "Hundreds of days saved" / "59% faster" are printed as value, while the open questions concede they may measure work *shifted* from research to correction. The article never resolves whether the agent reduces or relocates work — and even labels the "hundreds of days" figure a non-audited speaker claim in its own source-reliability section.
- **Conflates a vendor product (Workflows) with the architectural insight** (session-bound is wrong-shape), then defers the whole thing as "horizon," dodging both the vendor-neutral build and the admission that the diagnosis bites now.
- **"Millions of agent deploys → bets are correct" is vendor self-interpretation.** Volume of telemetry ≠ neutral inference; the most-cited source is the party selling the product.

## (d) Does it warrant FRESH external research? (be disciplined)

Mostly **no — synthesize, don't re-research.** Three of the four gaps are already-named rows in the ground-truth map (memory-capture hook §5; skill provenance is a governance decision; session-bound execution is a horizon architecture call) and need *decisions*, not more sources. The verification-loop thesis is corroborated internally — the map's own cross-references to Ramp (screenshots/live preview) and Basis (verifier sub-agent, diff-scoped tests) mean we already hold the comparative evidence; re-reading Vercel adds nothing.

Two narrow, bounded items would warrant a *short* fresh look only if V2 decides to build the corresponding gap:
- **If gap 1/2 is greenlit (render-gate):** verify current Chrome-MCP-in-CI / headless-preview-assertion patterns — but this is a "how does this tool work" lookup (CLAUDE.md "research before guessing"), not 3-pass deep research. Cost-bounded, build-gated.
- **If gap 4 is greenlit (skill provenance):** a one-pass scan of how agent-skill package managers (skills.sh, and Anthropic's own plugin marketplace, which the map shows we already use via the notion-plugin) handle signing/pinning — to set our internal pin-with-review policy. Again a targeted lookup, not deep research.

Net recommendation: **synthesize into V2 decisions against the existing rows; trigger a fresh lookup only downstream of a build decision, and only at "how does the tool work" depth.** No standalone deep-research spin-up is justified by this article.
