## The pillar in one paragraph (plain English, no jargon)

Right now the harness — all 26 skills, 23 agents, the hooks, the review pipeline, the memory stores — exists in exactly one place: the `event-vendor` repo, plus a pile of Notion pages that describe it and drift out of sync with the code (canon §0: "the harness the canon describes as 'global / multi-project' is, on disk, a single-project artifact"; §8: "never been installed anywhere but event-vendor — 'multi-project' is a goal, not a state"). The charter says the real unit of scale is one world-class engineer running parallel agent fleets across **5+ repos**. That is impossible today: there is no installable package, every other repo starts from zero, and an improvement made in `event-vendor` never reaches the others. This pillar builds the part that makes the harness *travel*: package the portable behavior (skills + agents + hooks) as a **versioned Claude Code plugin** published to a **marketplace** so `/plugin update` becomes the native pull-down path; ship a thin **`/init` template** for the per-repo files a plugin physically cannot carry (permissions, `CLAUDE.md`, `AGENTS.md`, auto-mode policy); move canon **from Notion into the GitHub repo** so the harness's source of truth is the same Git artifact it ships; govern the **15 third-party skills** the harness already depends on (pin them, review them on update, decide per-skill which travel); make the harness **summonable from outside its own process** (the technical substrate every autonomy front-door sits on); and run the **context-maintenance loop as a cross-repo cloud routine** so the fleet stays coherent without a human babysitting five repos' worth of drift. In short: take a harness that is a single-repo prototype with a Notion shadow, and turn it into a distributed, version-pinned, self-updating product that any repo can install and that pulls fixes down on its own.

### 1. Plugin + marketplace as the distribution spine (P0 — the foundational decision, build after convergence)

- **Plain-English what + why (the failure it prevents):** A plugin is the installable, versioned unit — a directory with a `.claude-plugin/plugin.json` manifest bundling skills, commands, agents, hooks, and `.mcp.json` into one namespaced, marketplace-installable package. The failure it prevents is **template-copy drift**: when every repo holds a hand-copied folder of harness files (or a symlink that resolves to HEAD), they silently diverge and nothing updates them. A plugin is version-pinned and `/plugin update`-able, so the behavioral harness travels as one released artifact *and pulls fixes down*. This is the difference between "we wrote a harness" and "the harness is a product five repos run."
- **The concrete mechanism:** Extract the project-agnostic behavior (the 26 skills, 23 agents, the hooks, the manifest schema, the sensor-ledger schema) into a Claude Code **plugin** published to a `marketplace.json` on a Git repo (the `agent-harness` repo). Install via `/plugin install`, update via `/plugin update`, pin a version, hold a lock. Pair with a thin `/init` template (Move 2) for the per-repo files a plugin physically cannot carry. The symlink-live install is explicitly **dead** — it resolves to HEAD not a SHA and becomes a second source of truth that drifts (F-rejected §7 KILL-UPHELD: "symlink-deployer stays dead; versioned plugin + marketplace + lock is the world-class form").
- **Citation:** Confirmed absence — canon §8 ("There is no installable, shared, version-controlled harness… GitHub Publishing — in progress; next gate: 3 real installs," both unmet); canon §0 (the "multi-project" descriptor is false on disk). Elevated by `commands-vs-skills.md` Move "Plugin-as-package" (RE-JUDGMENT ELEVATE: "commit to plugin+marketplace as the distribution architecture **now**… the conservative framing let a true precondition shade into picking the weaker vehicle") and `harness-engineering-survey.md` Move "The portable harness" (ELEVATE to "#1 structural workstream"). The KEY RESOLVED FACT settles the prior open question (template-repo vs plugin) against the conservative lean: "Distribution = plugin + marketplace + thin /init template."
- **Tag:** **P0**, the foundational decision; built *after* canon↔disk convergence (the publish gate), but the decision and the manifest schema (Move 6) are committed now.

### 2. The thin `/init` template for project-owned files (P0 — the forced seam, co-built with the plugin)

- **Plain-English what + why:** A plugin **physically cannot carry `permissions`/`settings.json`** (the 27-byte proof in the RESOLVED FACTS). So distribution has a hard seam: the *portable mechanism* (skills/agents/hooks) ships as a plugin; the *project-owned files* (per-repo `CLAUDE.md`, `AGENTS.md`, `permissions.allow`/`deny`, the `autoMode` policy, area-rule shards) ship as a thin `/init` template the human runs once per repo. The failure it prevents: a fresh install where the plugin lands but the repo runs **bare-default permissions and bare-default auto-mode** — the exact failure E-already-built §8 names ("repo #4/#5 silently run bare defaults… the safety classifier the whole autonomy program rides on is effectively off").
- **The concrete mechanism:** Build a `/init` skill (or expand the existing `setup-strategy` family) that materializes the per-repo files from a committed canonical template: `CLAUDE.md` skeleton, `AGENTS.md` skeleton, the `permissions.allow`/`deny` baseline (including the guard-file lockout from E-already-built §9, the one TRULY-WORLD-CLASS item), and the **auto-mode policy placed where the classifier reads it** with a single-tenant-prod carve-out. The agent *prepares* paste-ready content; the human *applies* guard-file/settings changes — the no-self-edit boundary holds (F-rejected §8 KILL-UPHELD: "agent self-edit of a guard file stays forbidden; the autoMode content + /init materializer + pre-flight gate are massively elevated"; memory `feedback_no_agent_edits_guard_files`).
- **Citation:** Resolved fact (plugin can't carry permissions). Confirmed absence — canon §3a/§8 (no `/init` materializer; other repos carry "no project-specific harness, no global CLAUDE.md"). Elevated by `auto-mode-config.md` (committed canonical source + `/init` materializer + pre-flight gate) via E-already-built §8 and F-rejected §8.

### 4. MCP-as-substrate — make the harness summonable from outside its own process (P0 — the autonomy front-door's technical substrate)

- **Plain-English what + why:** Today the harness is purely an MCP **client** — it can only be driven by a human at a prompt (canon §2: global config lists `notion` MCP as a server it *calls*). The world-class move is to make the harness's skills/pipeline **callable from outside the current process** — so a Slack bot, a Linear webhook, a CI failure, or a cloud-scheduled routine can invoke "run `/cr` on this branch," "open a reviewed PR for this bug," "run the spec pipeline." The failure it prevents: a harness that is *the autonomy ceiling stated as a feature* — it can never be summoned, can never run an externally-triggered bug→PR loop, can never be a node in a self-improving multi-agent system. This is the technical substrate every autonomy front-door (bug→PR, Slack/Linear summon) sits on; this pillar owns the *distribution/integration* half of it.
- **The concrete mechanism:** Expose the harness as externally-summonable endpoints — `RemoteTrigger`-style entry points (and/or harness skills exposed as MCP tools to an external orchestrator) — that route an inbound event into the existing worktree → `/cr` → `pr.sh` shell. The side-effect actuator (open-PR / deploy / send-Slack) is a **`disable-model-invocation:true`** skill, removed from the model's context so it is a *safe* actuator the loop cannot fire on its own judgment (RESOLVED FACT: "`disable-model-invocation:true`… makes side-effect skills safe"). Cloud `/schedule` already runs committed skills on Anthropic infra, so the durability objection that would have killed external triggers is **moot**.
- **Citation:** Confirmed absence — `ai-automation-ecosystem.md` Move "MCP-as-substrate": "pass3 **explicitly refused to map this**… 'our harness *is* the MCP client'… I refuse to invent a gap there." RE-JUDGMENT: "ELEVATE — the single biggest suppressed move… the 'it's just the client' framing is the autonomy ceiling stated as a design choice." The market prior art (Pipedream/Composio/n8n converging on "expose your tools to agents over MCP") is the world-class evidence. Pairs with `stripe-minions-kaliski.md` (Slack-summon → agent → PR, built by Zapier's CTO — `zapier-skillmd.md` Autonomy angle, "direct evidence the pattern is world-class, not speculative").

### 5. Skill-provenance trust governance (P1 — the supply-chain control on the distribution boundary)

- **Plain-English what + why:** The harness already straddles a supply-chain boundary: **15 third-party skills** are symlinked from `mattpocock/skills` (+ Supabase, Vercel, Anthropic) via a v3 lock file (canon §1, §78, §117), and `/tdd` is a **divergent project-local fork** ("two copies, no sync" — canon §93). Installing an agent skill is *not* like installing a library — it is installing **instructions that steer the agent's judgment** across every repo that pulls it. The failure it prevents: a malicious or low-quality upstream skill (or a silent upstream *update*) corrupting agent behavior — a supply-chain vector into *every repo the fleet touches, executing autonomously, with no human reading each run*.

De-duplicate the skills that already appear twice (`supabase-postgres-best-practices`, `tdd` show up as both project and plugin copies — grounding skills-C §136/§155/§184) by picking the plugin/marketplace copy as canon and dropping the in-repo duplicate.
- **Citation:** Confirmed absence — canon §1 (15 symlinked Matt-Pocock skills, no governing control recorded), §93 (`/tdd` fork). Elevated by `vercel-agentic-infra.md` Move "Skill provenance / trust governance" (RE-JUDGMENT ELEVATE: "from 'one-pass lookup if greenlit' to a **first-class trust-governance control** on the distribution boundary"); scale-bias §17 (PROMOTED — first-class control).

### 6. The harness-manifest.json — catch prose-inventory drift (P1 — the schema the whole distribution serializes through)

- **Plain-English what + why:** The runtime skill list today mixes every layer with **no signal** for which layer owns each skill, which travels to another repo, or what tools each needs (canon §1: "When the agent sees `/cr`, `/queue`, `/dev` (project)… it cannot tell which layer owns each, nor which will travel"). The harness's own prose inventory drifts from disk (canon §0 correction log: the audit artifact itself rotted and shipped four false absence-claims). The failure it prevents: an installer/agent that cannot reason about its own skills programmatically — it can't tell a project skill from a portable plugin skill, can't pre-load required tools, can't build a marketplace because there is no manifest to read, and can't detect when the prose inventory lies.
- **The concrete mechanism:** A per-skill **frontmatter contract** + a `harness-manifest.json` consumer that reads it: `name`, **situational** `description` (not phrase-key), `required-tools`, `owning-layer`, `portable: true|false`, `scope: project|universal`, the per-skill upstream-dependency disposition (Move 7), and `disable-model-invocation` for side-effect skills. The manifest drives (a) the plugin+marketplace distribution, (b) the thin `/init` template, and (c) the agent filtering its own skill list by owning-layer. The manifest is also the input to the context-loop scanner (Move 9): a manifest that disagrees with disk is a drift ticket. **Build both halves** — frontmatter without a consumer is documentation (`zapier-skillmd.md` Move "SKILL.md frontmatter contract + a real skill router": "frontmatter without a consumer is documentation — so build both halves").
- **Citation:** Confirmed absence — canon §1 (no owning-layer/portability signal), §3b (~26 disk skills, no registry). Elevated by `zapier-skillmd.md` (RE-JUDGMENT ELEVATE: "the schema the whole portable-harness vision serializes through"); `osmani-agent-skills.md` Move "adopt/borrow/reject screen" (the import-vetting gate the manifest enables); F-rejected §6 (the manifest needs the owning-layer signal — collapsing agents would erase it). The situational-trigger requirement is `commands-vs-skills.md` Move 2 + canon §9.
- **Tag:** **P1**. The frontmatter contract is the input the plugin/marketplace physically requires; build it with the plugin, wire the consumer right after.

### 7. Per-skill upstream-dependency disposition policy (P1 — what travels when the harness ships)

- **Plain-English what + why:** A tool you build on can have its roadmap captured by an owner whose incentives diverge from yours (the Pipedream/Workday lesson). The harness has exactly this shape — 15 vendored skills pulling its structure toward an upstream layout, plus a live un-synced `/tdd` fork — and has **never priced it**. The failure it prevents: silent drift where the project structure is slowly pulled toward an upstream ecosystem's expected layout and nobody notices until a breaking change strands the fleet on an un-maintained fork — *independently in every one of the 5+ repos*.
- **The concrete mechanism:** A one-page `UPSTREAM-DEPENDENCY-POLICY.md` (in GitHub canon) plus a **per-skill disposition column** in the manifest (Move 6): for each upstream skill, record `vendor-and-freeze` / `track-upstream-with-named-sync-cadence` / `cut`, and the failure mode that disposition prevents. This is the distinct-but-paired sibling of provenance (Move 5): provenance is *trust* (pin + review-on-update), disposition is *travel* (which skills ship, which freeze, which are cut). Add a **recurring-maintenance-cost** note per surviving mechanism — the §9 golden rule applied to upkeep, reframed by the charter from "a column to justify cuts" to "the standing acceptance criterion that lets a deliberately maximal harness carry 40 hooks without rotting" (`ai-automation-ecosystem.md` Move "recurring-maintenance-cost lens").
- **Citation:** Confirmed under-pricing — canon §1 (CONTEXT.md coupling + `/tdd` fork), §8 (cross-project reality). Elevated by `ai-automation-ecosystem.md` Move "Price the upstream-dependency owner-drift risk" (RE-JUDGMENT ELEVATE: "roughly 5-10x bigger… at fleet scale an un-priced upstream dependency drifts every repo independently"); scale-bias §22 (PROMOTED — first-class V2 item).

### 8. Push-back-up — the promotion gate that flows improvements upstream (P1, automated GATED)

- **Plain-English what + why:** When a fleet runs across 5+ repos, an improvement (a new guard, a sharpened skill, a learned-pattern row) is made *in one repo*. Without a path back up to the shared plugin, that improvement never reaches the other four — the fleet's learning does not compound. The failure it prevents: 5 repos drifting *apart* as each accretes local improvements the others never see, which is the inverse of the whole "harness as moat" thesis.
- **The concrete mechanism:** A `scope: project|universal` field on the promotion gate (the manifest, Move 6). When a change is tagged `universal`, the promotion path opens a **human-gated PR** against the `agent-harness` plugin repo; `/plugin update` then carries it down to every repo on the next pull. This is human-gated for now (the no-self-edit-of-shared-canon boundary), and becomes a candidate for automation **once a 2nd repo exists** to receive the push — until then there is no destination, so the automated form is gated on install-state, not deferred on doubt.
- **Citation:** Confirmed absence — canon §8 (the fleet does not exist yet; "apply engineering system to Recyclops" is unmet). Elevated by `harness-engineering-survey.md` Move "portable harness" ("carries those earned blocks to every other repo so the whole fleet inherits each fix once") + the Hashimoto-ratchet move (a corrected mistake becomes an *enforced* rule that travels). The `scope` field is the manifest's promotion primitive.
- **Tag:** **P1** for the human-gated PR path (build with the plugin); **GATED** for automation (flip-trigger: a 2nd repo installs the plugin).

### 9. The cross-repo self-improving context-maintenance loop as a cloud routine (P0 substrate / P1 repair-worker)

- **Plain-English what + why:** Context (the canon docs, skills, AGENTS.md) is now a production artifact with code's failure economics: a human reads a slightly-stale doc occasionally and shrugs; an *agent* re-onboards from that same doc thousands of times and reasons wrongly with full confidence every time. The failure it prevents: undetected context rot — and the harness has a **live, dated proof** of it (canon §0 correction log: the audit artifact itself rotted and shipped four false absence-claims). At fleet scale across 5+ repos, the rot is faster, not slower (scale-bias §8: "fleets across 5+ repos rot *faster*, not slower").
- **The concrete mechanism:** Ship the `/scan-context` skill (documented in canon, **absent on disk** — canon §5) as a committed skill run on a clock by a cloud `/schedule` routine **across the fleet**. Three parts in dependency order (`basis-canon-not-canon.md`): (1) a **CI check** validating every knowledge artifact on every merge (frontmatter present, `owner` set, prose instructional not descriptive, no broken cross-refs — the deterministic enforcement of "default-no" that is genuinely absent); (2) a **scheduled scanner** opening tickets for doc-stale, doc-fiction (phantom refs like `learned-patterns.md`), canon-vs-canon contradictions (the §7 cases), duplication, and 90-day decay; (3) a **repair worker** that opens scoped `/cr`-gated, human-merged fix PRs. The scanner is the missing **upstream root** of the chain the harness already paid for — its world-class `/cr` enforces code against canon that §7 proves contradicts itself, so the scanner is what makes `/cr`'s canon-conformance trustworthy. Safety design built in, not bolted on: a declared `owner` + a machine-checkable `supersedes:`/`version:` precedence schema (the out-of-loop human anchor that stops the loop "eating its own tail"), and the worker **denied write access to guard files / settings / the destructive-op floor** (memory "no agent edits to guard files"; E-already-built §9 the one TRULY-WORLD-CLASS rule, applied as the worker's path-scope denylist).
- **Citation:** Confirmed absence — canon §5 (`/scan-context` documented, absent), §3f (no CI validates any knowledge artifact), §0 correction log (live rot proof), §7 (nine contradictions). Elevated by `basis-canon-not-canon.md` (full loop, P0), `packmind.md` (bidirectional drift: doc-stale AND doc-fiction + 90-day decay + proposes own fixes on a cloud schedule), `basis-monorepo-deep.md` (scale-bias §9: "ELEVATE, hard… the single most suppressed move"), `harness-io.md` (dedicated `/scan-context` guarded by §9, weekly cloud routine). scale-bias TOP-5 #3.
- **Tag:** **P0** for detection (CI check + scheduled scanner — ship now); **P1** for the repair-worker (the auto-PR-opening half, gated on the guard-file denylist and the `owner`/`supersedes` schema being in place). This is the flagship distribution-layer autonomy loop and it is *cross-repo* — the cloud routine sweeps the fleet, not one repo.

## What is DECISIVELY better than V1 here (the weak-version → world-class deltas)

Each delta names the V1 weak version, the failure it permits, and the world-class form — no phantom upgrades.

1. **Distribution: single-repo prototype + Notion shadow → version-pinned plugin + marketplace with a pull-down path.** V1 weak version: the harness exists in `event-vendor` only; "multi-project" is a goal, not a state; the install method is "reconstruct from a Notion page," and the canon itself is in bidirectional drift (canon §0, §8). Failure permitted: every new repo starts from zero and improvements never compound across the fleet. World-class: `/plugin update` is the native pull path; the harness is one released, version-locked artifact (Move 1). This is the single biggest structural delta in the pillar.

2. **Source of truth: Notion (drifting, agent-unreadable) → GitHub Git canon (diffable, convergence-checkable).** V1 weak version: canon lives in Notion, drifts from disk, and a cloud agent can't reliably read/write it (WAF blocks on security content). Failure permitted: canon and the artifact it describes drift forever, and the convergence-as-publish-gate is un-enforceable because there's nothing to diff. World-class: canon is Git Markdown in the same repo it ships; convergence is a `git diff`; `/notion-sync` retired, `/compound` Step 8 re-pointed (Move 3).

3. **Skill provenance: ungoverned symlinks to floating upstream refs → pinned, reviewed-on-update, dispositioned.** V1 weak version: 15 third-party skills symlinked to HEAD with no provenance record, plus an un-synced `/tdd` fork the map flags as a risk but governs with *zero* controls (canon §1, §93). Failure permitted: a floating upstream skill that steers judgment is a supply-chain vector into every repo the fleet touches, autonomously, unread. World-class: pinned SHAs, human review-diff on update, per-skill disposition, side-effecting upstream skills behind `disable-model-invocation` (Moves 5 + 7).

4. **Integration shape: MCP client only → externally-summonable substrate.** V1 weak version: the harness is purely an MCP *consumer* — driveable only by a human at a prompt (canon §2). Failure permitted: no bug→PR, no Slack/Linear summon, no node in a self-improving multi-agent system — the autonomy ceiling stated as a feature. World-class: harness skills/pipeline summonable from outside the process, with the side-effect actuator gated by `disable-model-invocation` (Move 4). pass3 *explicitly refused to map this gap*; un-suppressing it is a decisive reversal.

5. **Context maintenance: write-only, manual, single-repo, detection-only → cross-repo scheduled scanner + auto-PR repair worker.** V1 weak version: `/scan-context` is documented in canon but **absent on disk**; no CI validates any knowledge artifact; the audit doc itself rotted and shipped four false claims (canon §5, §3f, §0). Failure permitted: undetected context rot that an agent reasons wrongly from thousands of times, faster at fleet scale. World-class: a CI knowledge-artifact check + a cloud-scheduled cross-fleet scanner + a `/cr`-gated repair worker with an `owner`/`supersedes` safety schema (Move 9). The conservative synthesis cut the *repair half* on "dangerous at solo scale" and "the machine sleeps" — both premises dead.

6. **Self-knowledge: prose inventory that lies → machine-readable manifest that catches its own drift.** V1 weak version: the runtime skill list mixes all layers with no owning-layer/portability/tool signal; the agent can't reason about its own skills programmatically; the prose inventory drifts from disk (canon §1, §0 correction log). Failure permitted: no marketplace can read it, no installer can build from it, and drift goes undetected. World-class: a per-skill frontmatter contract + a `harness-manifest.json` consumer that the scanner cross-checks against disk (Move 6).

## Honest cuts (UPHELD-CUT items in this pillar, with named failure modes)

These survive the world-class charter — the cut rests on irreversibility, threshold, install-state, or a duplicate-of-something-stronger, **not** on solo-scale skepticism. Do not elevate everything.

1. **Symlink-live install — KILL-UPHELD (F-rejected §7).** A symlink resolves to HEAD, not a pinned SHA, and becomes a **second source of truth that drifts** (manifest-drift across N adapter folders, pass2-D). The versioned plugin + marketplace + lock is the world-class form; the symlink-deployer stays dead. Failure mode if resurrected: every repo silently tracks a moving upstream and nothing pins or reviews the change.

2. **The Saul Fernandez three-repo architecture (agent-library + agent-setup symlink-deployer + resource-catalog) + per-tool adapters + Backstage-style catalog — UPHELD-CUT (`harness-engineering-survey.md` Move "portable harness").** This is a genuine large-org packaging shape; each adapter folder is a second source of truth that drifts. The *principle* (deploy outward, rebuild from clone) is fully elevated via plugin+marketplace+thin-`/init`; the *three-repo/adapter machinery* is the one packaging variant cut, with the named failure mode being manifest-drift across N adapter folders. This is not the conservative "shrink to principle" dodge — it keeps the full ambition and cuts one variant with a concrete failure.

3. **Cross-harness skill router / portability to Cursor / Gemini / Copilot — NOT-SETTLED, do not build now (scale-bias §21 PROMOTED-but-scope-dependent; `osmani-agent-skills.md`).** The rejection was scope-dependent, not pure bias: it "becomes live" once the harness ships as a plugin across 5+ repos. Building a cross-harness adapter *before* the plugin exists and a second repo runs it is solving for a portability target that has no consumer. Mark not-settled; the flip-trigger is the plugin shipping and a non-Claude-Code harness needing the same skills. Failure mode if built now: a speculative adapter layer maintained against zero non-Claude-Code installs.

4. **Toolshed-style centralized MCP tool registry with task-time curation — CUT (C-deferred §7, `stripe-minions-kaliski.md`).** Even at world-class fleet scale, building a Stripe-style 500-tool registry today solves a problem the harness does not have — the tool surface is genuinely small and skills already load on invocation. Failure mode if built now: a speculative abstraction with no token-paralysis traffic to justify it — the exact over-engineering "build what's needed now" still forbids. (A per-task tool-curation *manifest* is a near-horizon watch-item if the connector surface grows; the centralized-registry *build* is cut.)

5. **The agent self-applying the autoMode block / any settings.json or guard-file edit — KILL-UPHELD as an action (F-rejected §8; memory `feedback_no_agent_edits_guard_files`).** A self-improving agent that can edit the policy file governing its own autonomy has no policy floor. The *content* + the `/init` materializer + the pre-flight verify are all elevated (Move 2); the *self-edit* stays a human handoff (agent surfaces paste-ready content). This cut is what *keeps the elevated content safe* — it is a boundary, not a deferral.

6. **The "shrink CLAUDE.md/AGENTS.md root to 200 lines" line-count target — KILL-UPHELD (F-rejected §1, `commands-vs-skills.md`).** Touches this pillar because the `/init` template materializes that root. Blindly shrinking demotes **no-trigger safety content** (the destructive-op rules) into a tier that only loads on description-match — so it never loads when an unprompted destructive command arrives, and that failure is *worse* across a parallel fleet running scheduled cloud jobs. Tier by trigger-existence, not line count; the `/init` template keeps the no-trigger safety floor in tier-1 regardless of length.

## Open forks (genuine decisions only Tanner can settle)

1. **Marketplace hosting: private Git repo vs. a public/Anthropic-listed marketplace.** A private `agent-harness` repo marketplace keeps the harness internal and avoids skill-provenance exposure both ways; a public listing invites contribution and pull but turns *your* harness into an upstream others pin (the provenance problem in reverse). The 5+-repo fleet is yours, so private likely suffices — but this decides whether push-back-up (Move 8) ever has external consumers. Only Tanner can set the boundary.

2. **`/scan-context` repair-worker autonomy level on day one: open-PR-and-wait vs. open-PR-and-auto-merge-on-LOW-risk.** The repair worker is `/cr`-gated and human-merged by default (Move 9). Whether a context-only fix (a doc typo, a phantom-ref deletion) that is CI-green + `/cr`-clean + in a non-guard path may **auto-merge** via the deterministic risk classifier (the Ona-L4 mechanism, scale-bias TOP-5 #4) is a trust decision for a $30k-client-adjacent tool. The mechanism is safe under `disable-model-invocation`; the threshold is Tanner's call.

3. **`/tdd` fork disposition: deliberate-fork-we-own-forever vs. re-sync-to-upstream-with-cadence.** The fork has diverged (canon §93, edited 2026-06-07) and carries the project-specific TESTING.md-ledger wiring. Classifying it (Move 5/7) forces a one-way-door decision: own it forever (and accept it never inherits upstream improvements) or commit to a named sync cadence (and accept re-merge cost each time). Only Tanner knows whether the divergence is intentional project value or accumulated drift.

4. **Convergence scope as the publish gate: resolve all nine §7 canon contradictions before the first publish, or publish from a declared-precedence snapshot.** The publish gate requires canon↔disk convergence. The strict reading blocks the first plugin release until every §7 contradiction is resolved (later-dated-page-wins made into a real `supersedes:` schema). The pragmatic reading publishes from a snapshot where the precedence schema *declares* the winner for each contradiction, resolving them lazily via the scanner. This trades first-publish latency against shipping a known-imperfect canon — a sequencing judgment with real cost either way.

5. **Per-repo `/init` template depth: minimal floor vs. opinionated full scaffold.** `/init` must materialize the safety floor (permissions baseline, guard-file lockout, auto-mode policy). Whether it *also* lays down opinionated `CLAUDE.md`/`AGENTS.md` content (area-rule shards, the full discipline rules) or just a skeleton is a fork: a thick template makes new repos instantly world-class but risks shipping event-vendor-specific assumptions into unrelated repos; a thin one is portable but leaves each repo under-configured until hand-tuned. Only Tanner knows how uniform the 5+ repos will be.
