# Ambition Re-mine — Spec-Driven Development & Agent Workflows at Notion (Ryan Nystrom)

## What this source is (plain English, 2-3 sentences)

A *How I AI* podcast write-up of how Notion AI's "Afterburner" team ships features by handing coding agents a permanent, version-controlled **spec** (not a throwaway task) that includes an **executable Verification section** — backed by a custom CLI that lets the agent run the product from a shell and check its own work against the spec. Around that core they run three autonomy workflows: a 9 AM fan-out "Hot Potato" standup pre-read, a "Boxy/Software-Factory" Notion-task→GitHub-PR-in-20-min loop on a VM, and the spec-first build loop itself. The unifying thesis (recovered in pass2) is that **an agent's autonomy is bounded by the quality of the verification surface you can hand it — and that surface must be a built artifact, not a written intention.**

## The full-ambition moves this source teaches

### Move: The per-feature behavioral contract — a spec written for a future cold-start agent

- **Plain-English what & why:** Most repos hold two kinds of knowledge: the *code* (answers "how") and project-context docs like CLAUDE.md (answers "what this codebase is"). Neither answers the third question — "**what is THIS feature supposed to do, and how do I know it still does it?**" Notion writes that third thing as a Markdown spec per feature, commits it to `/agent-specs/`, and keeps it as the permanent source of truth. The failure it prevents is **behavioral drift**: the spec's real payoff is not the first build — it's the fifth modification six months later, made by an agent that has zero memory of the original session and would otherwise silently break behavior nobody re-stated. Pass2 sharpens the audience: the spec is written *for the stateless agent that doesn't exist yet*, whose entire job-relevant context must be re-established cold. The spec exists to make cold-start cheap and drift-proof.
- **The mechanism:** Add a per-feature behavioral-contract doc class to the harness — an `/agent-specs/`-equivalent (e.g. `docs/specs/<feature>.md`, and note `docs/specs/` is already named in CLAUDE.md's doc-update table as "behavioral spec / agent-readable contract for a module" but does not exist on disk per §3a). Each spec has three required sections: **Behavior** (what it does), **Implementation pointers** (where it lives), and a **Verification** section (the executable steps that prove it still works). Wire `/feature` to write/update the spec *first*, commit it, then build against it; wire future edits to update the spec, then reconcile code to the spec. The spec's git history becomes a human-and-agent-readable changelog of *intent*.
- **Citation:** Confirmed absence. §3a (Governance/context docs) inventories CLAUDE/CONTEXT/AGENTS/SOUL/ARCHITECTURE/TESTING/STRATEGY — **none is a per-feature spec**. §4 (memory model) lists `memory.md`/`RECURRING-FINDINGS.md`/`PITFALLS.md`/`docs/solutions/`/`docs/adr/` — ADRs capture *decisions*, solutions capture *patterns*, PITFALLS capture *traps*; **no per-feature behavioral contract exists**. (CLAUDE.md *references* a `docs/specs/` doc class in its update table, but §3a confirms it is not built.)
- **Conservative disposition:** §C-deferred / scaled to a "decision, not a build." Pass3 calls it "the article's single most transferable, tool-agnostic idea and it maps to a real hole" — then immediately defers it: "Scope a thin `/agent-specs/`-equivalent against §3a/§4 **before building**... a **Phase-3/5 design decision**... not external research," and floats absorbing it into `docs/adr/` + "a verification section in existing tests." MASTER-FINDINGS folded the source's value down to "**one durable, tool-agnostic idea** ... plus independent confirmation of a §9 cut. Both are mapping-and-decision work, not discovery."
- **RE-JUDGMENT under the new charter: ELEVATE.** This is the load-bearing autonomy primitive of the entire corpus, not a Phase-5 paperwork decision. Under "autonomy is first-class," bug→PR and Slack-summoned builds are *only* safe if a cold-start agent can re-establish what a feature is *for* and verify it without a human — which is exactly and only what the per-feature spec provides. The conservative bias is twofold: (1) it treated a confirmed structural absence (§3a/§4) as a "scope question" to defer, when the charter says never reject/defer an idea merely because it adds a doc class — "more skills/mechanisms is FINE when each earns its place." (2) The suggested mitigation — "absorb into `docs/adr/` + a verification section in existing tests" — is the wrong abstraction: ADRs are cross-feature *decisions* with no behavior/verification contract, and developer-authored tests are not a spec-derived oracle (pass3 itself admits this in gap 3). How much bigger: this should be **in-scope-now as a first-class doc class wired into `/feature`**, shipping with its Verification section from day one, not a deferred design memo. It is the single highest-leverage move in this source.

### Move: The executable Verification section + a product-driving CLI (verification as a built artifact, not prose)

- **Plain-English what & why:** Notion's spec ends with a Verification section that is *runnable*, not a paragraph of good intentions. They built a custom CLI that lets an agent run Notion AI from a shell — send queries, toggle features (e.g. Ask Mode on/off), read the output transcript — so the agent executes the spec's verification steps as test cases and certifies its own work against the contract *with no human in the loop*. The failure it prevents: an autonomy gate that certifies *process ran* ("review happened") rather than *the feature behaves as specified*. Pass2's parent law: **autonomy is rationed by verifiability, and the verification surface must be a built artifact.** A prose "Verification: it should work correctly" closes no loop; a shell command that asserts behavior does.
- **The mechanism:** Two coupled changes. (1) Make each spec's Verification section a list of **executable assertions** (CLI invocations, scripted checks, a render-and-diff, an agent-runnable harness) — not prose. (2) Re-type the `.cr-ok` gate: today the agent pre-push gate "validates `.claude/.cr-ok` sentinel (`branch:sha`); aborts if stale or missing" — a *process-completion* token that "is gitignored, never reaches CI." Upgrade the autonomy gate so that for any feature with a spec, the gate also requires the spec's Verification section to *pass*, not merely that `/cr` ran. The sentinel becomes a readiness *signal*; the verification surface becomes the capability *unlock*.
- **Citation:** §3e (the agent pre-push "validates `.claude/.cr-ok` sentinel... aborts if stale or missing"); §3f (CI is `ci.yml`/`integration.yml` running tsc/lint/vitest; the Node-8.5(c) gap — "CI never verifies `.cr-ok`", sentinel "gitignored, never reaches CI"); §9 Replace list pre-authorizes exactly this: "The `.cr-ok` sentinel as a capability gate → document as a readiness signal, not a capability unlock."
- **Conservative disposition:** Partially §E-already-built, partially a §9 pre-authorized cut treated as a "one-line decision." Pass3 says "we already ration autonomy on a built gate — but ours gates on a *sentinel*, not a *verification surface*," then frames the fix as merely confirming a known §9 re-typing: "a **one-line decision to fold into the §9 re-audit**, not new research." It explicitly *sequences this behind* the spec gap ("downstream of the spec gap above and should not be built before it").
- **RE-JUDGMENT under the new charter: ELEVATE.** The §E "we already have a built gate" framing is the conservative move that hides the actual gap: we have a gate that certifies *the wrong thing*. Pass3 itself nails it — "`.cr-ok` is a process-completion signal masquerading as a correctness signal." Under "autonomy is first-class," an unattended bug→PR loop that merges on a "review ran" token, not a "behavior verified" assertion, is a correctness hole the moment a human stops watching. This is not a one-line §9 footnote; it is **the keystone that makes the whole autonomy charter safe to turn on.** The "downstream, build it second" sequencing is right in *order* but wrong in *priority*: the executable-verification surface should be designed in lockstep with the spec layer, not deferred as an afterthought. The world-class version: an agent-runnable verification harness (CLI/scripted assertions per spec) whose pass/fail is what the autonomy gate actually checks — and which CI can verify too, closing the §3f gitignored-sentinel hole. How much bigger: from "fold a re-type into the §9 audit" to "build the executable verification surface as a co-equal first-class subsystem alongside the spec layer."

### Move: CI-as-throughput — pipeline latency is a ceiling on agent fleet output

- **Plain-English what & why:** Slow CI was historically tolerable because a *human* context-switches while the pipeline runs — you go do something else for 40 minutes. An *agent does not*: it blocks. So if N agents each wait on a 60-minute pipeline, your fleet's wall-clock throughput is capped by pipeline latency, and a 3-minute pipeline is literally a ~20x multiplier on the same wall clock. Notion's "Afterburner" exists to cut CI to a quarter of current; they cite Stripe's ~1,300 agent PRs/week as impossible without it. The failure it prevents: building a parallel agent fleet whose real bottleneck is silently CI latency, not agent capability. Pass2's crucial qualifier: this is **real but conditional on actually running a fleet** — below parallelism, CI speed is ordinary DX.
- **The mechanism:** Treat CI latency as a fleet-throughput metric once `/queue` saturates: measure pipeline wall-clock, identify whether tsc/lint/vitest/integration is the serialization bottleneck under parallel worktrees, and invest in CI speed (caching, sharding, selective test runs) as a *throughput* lever, not a comfort one.
- **Citation:** §3f (CI = `ci.yml` + `integration.yml`, tsc/lint/vitest); §3b/§1 (`/queue` runs parallel worktrees — so the throughput argument is live, not hypothetical); §8 (the harness "has never been installed anywhere but event-vendor"; "Multi-project is a goal, not a state"; the install gap dominates).
- **Conservative disposition:** §C-deferred as "real but low-priority." Pass3: "CI speed is a real lever the moment `/queue` saturates, but the map gives no evidence CI latency is the current bottleneck, and §8 says the install gap dominates. **Real but low-priority gap — flag, do not prioritize; cite §8 over the article's urgency.**"
- **RE-JUDGMENT under the new charter: UPHELD-CUT (with a sharpened trigger).** This is a genuine prioritize-later, and the failure mode that justifies *not* front-loading it is concrete: optimizing CI latency before the harness is even installed beyond one repo, or before `/queue` is regularly saturating, is **premature optimization that spends weeks shaving a pipeline that is not yet on the critical path** — §8's reality is that the harness runs in exactly one project, so there is no fleet whose throughput CI currently caps. The §9 golden rule applies in reverse: there is no failure mode that CI-speed work prevents *today*, so today it is overhead. BUT — sharpen the trigger so it is not lost: the moment `/queue` regularly runs ≥3 parallel worktrees that block on the same pipeline, CI latency becomes a first-class throughput metric and this flips to in-scope. This is not conservative bias; it is correct sequencing with a named, measurable flip condition. (Charter note: the "doesn't apply to solo / our economics differ" dismissal does NOT apply here — the cut is justified by install-state, not by scale skepticism.)

### Move: Parallel sub-agent fan-out as a map-reduce on context-gathering (the Hot Potato pre-read)

- **Plain-English what & why:** Notion's 9 AM standup agent fans out *in parallel* across five sources (Slack, GitHub merged PRs, Notion task DB, Honeycomb CI metrics via MCP, yesterday's transcript), each sub-agent gathering one slice, then reduces them into a fixed-section pre-read posted to Slack. Pass1/pass2 frame sub-agents as a "scaling primitive" — a *map-reduce on context gathering* — and Nystrom calls them a "sleeper feature" (expensive, finicky, under-promoted, but essential). The failure it prevents: a single agent serially crawling five systems, blowing its context window and losing the plot, when the work is embarrassingly parallel. Notable secondary detail: the agent *self-configured its own MCP integration from a screenshot* — and pass2 flags this as a safety surface ("a self-modifying agent with write access to even one DB is larger than the page admits").
- **The mechanism:** A scheduled fan-out agent (cloud `/schedule`, which the charter confirms exists and runs on Anthropic infra) that spawns parallel sub-agents over the project's information sources — GitHub PRs, Linear/Notion tasks, CI status, prior session handoffs — and reduces them into a committed daily pre-read / situational-awareness brief, with scoped (mostly read-only) permissions per source.
- **Citation:** §3d (disk has 23 agents including the 4 review lenses + 6 spike agents — a real sub-agent roster); §3b (`/queue` parallel worktrees). Confirmed absence of a *scheduled cross-source fan-out / pre-read* agent: §2/§3e have "no webhook/cron/parallel-trigger fleet surface" (per pass3 (a)).
- **Conservative disposition:** §E/§D — largely treated as already-covered and not surfaced as a distinct candidate. Pass3 (a) credits us with parallel worktrees via `/queue` and the 23-agent roster as our adversary/fan-out coverage, and the source's standup-pre-read workflow is **not carried into pass3's gap list at all** — it was summarized away in favor of the spec layer.
- **RE-JUDGMENT under the new charter: NEW.** Pass3 collapsed Hot Potato entirely, treating "we have parallel worktrees" as if it covered "we have a scheduled cross-source fan-out pre-read." It does not: `/queue` parallelizes *build* work; nothing in §2/§3e is a scheduled situational-awareness agent that reduces five sources into a committed brief. Under "cloud `/schedule` EXISTS" + "self-improving loops / cloud scheduling designed in, never deferred," this is a clean first-class autonomy candidate: a scheduled fan-out agent is exactly the "keep working when laptop closed" pattern the charter now treats as in-scope. Recover it as a candidate — with the pass2 safety caveat baked in: scoped, mostly-read-only per source, and *no* self-rewriting-instructions-with-write-access (pass2's self-configuring-MCP warning is a real abuse surface; the destructive-op floor in §9/CLAUDE.md must bound it).

## Autonomy angle

This source is **dense with autonomy** — arguably the corpus's clearest picture of *earned, verified* autonomy:

- **Bug/task → reviewed PR:** Boxy is a literal Notion-task-→-GitHub-PR-in-~20-min loop on a VM. An engineer `@mentions` the agent in a task comment; it spins up a VM with the full codebase + Codex + dev tooling, reads the task/comments/screenshot, and comments back **two links: a finished PR and a live preview-environment URL**, with **self-captured screenshots proving it verified its own UI**. On a CI type-error it explained its reasoning and fixed it; it also resolved a merge conflict. This is the bug→reviewed-PR front-door the conservative synthesis deferred — demonstrated working.
- **Summon-from-a-tool:** the `@mention`-in-a-task-comment trigger is precisely the "summoned from Slack/Linear" pattern; Notion's summon surface is the task DB, but the mechanism (mention → autonomous build → PR + preview links back) is identical.
- **Cloud scheduling / self-improving loops:** Hot Potato is a scheduled (9 AM) cloud-style fan-out agent — the charter confirms cloud `/schedule` exists on Anthropic infra, so this is directly buildable. The spec-first loop is itself a self-improving loop: spec → build → self-verify via CLI → ship → spec stays as source of truth → next agent updates spec → reconciles code.
- **The governing autonomy law** (pass2): autonomy is rationed by a *built verification surface* — the deepest autonomy lesson here, and the one that makes the rest safe.

## The single biggest move (one paragraph)

**Build the per-feature behavioral contract with an executable Verification section — the spec layer — and wire the autonomy gate to verify it, not the `.cr-ok` process token.** This is the move the vision synthesis should pick up first because it is the *enabling substrate* for the entire autonomy charter: bug→PR, Slack/Linear summon, and cloud-scheduled self-improvement are only safe when a stateless cold-start agent can (1) re-establish what a feature is *for* from a committed contract and (2) prove it still behaves correctly with no human watching — which is exactly and only what a spec-with-runnable-Verification provides. It is world-class because it is the one durable, **tool-agnostic** idea in a tool-churning landscape (the spec outlives Codex/Boxy/any agent), it maps to a confirmed structural absence (§3a/§4 have no per-feature behavioral contract; CLAUDE.md *names* `docs/specs/` but it is unbuilt), and it independently converges with the §9 pre-authorized re-typing of `.cr-ok` from "capability gate" to "readiness signal." The conservative synthesis shrank this to a deferred Phase-5 "decision, not a build" and proposed absorbing it into ADRs+tests — the wrong abstraction (pass3 itself admits ADRs are decisions and tests are not a spec-derived oracle). Under the new charter it is in-scope-now, first-class, and shipped *with* an independent review pass on the spec from day one (pass2's "spec-first has no built-in adversary" failure mode — do NOT copy Notion's self-verification by the implementer).
