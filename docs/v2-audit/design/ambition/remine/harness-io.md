# Ambition Re-mine — Harness.io: "The Agent-Native Repo / Context Files as Execution Surface"

## What this source is (plain English, 2-3 sentences)

A Notion research page mining one blog post (Dewan Ahmed, "The Agent-Native Repo: Why AGENTS.MD is the New Standard," Mar 2026, Part 1 of 5) from Harness.io, a CI/CD vendor. Its one durable, transferable idea: **a context file (AGENTS.md / CLAUDE.md) is not documentation about the program — it is an input to a running program, and should be audited by the same standard as code: does this line change the output?** The rest of the source is a vendor pitch for pipeline-native, RBAC-governed agents that the article itself concedes does not transfer at solo scale.

This is a deliberately **single-principle** source. The honest ambition re-mine does not manufacture four world-class moves where there is really one strong one plus a small number of secondary mechanisms. Below I recover the full-ambition form of the load-bearing move, then re-judge the others honestly — including one I uphold as a genuine cut even at fleet scale.

## The full-ambition moves this source teaches

### Move 1: The execution-surface audit — context files graded like code, not prose

- **Plain-English what & why:** Treat every line of CLAUDE.md / AGENTS.md as a line of a program the agent runs, not a sentence in a README. A world-class team asks of each line, "does this change what the agent does?" — and if it cannot, the line is dead weight that dilutes the lines that *do* matter. The failure it prevents: context files bloat into stale, contradictory prose that an agent reads, half-applies, and silently degrades on. A 600-line CLAUDE.md where 200 lines are inert documentation is *worse* than a 400-line one, because the inert lines bury the load-bearing rules in the model's attention budget. The article's own canon (`[canon §3a]`, `[canon §7]`) already records event-vendor's AGENTS.md carrying a "None open" contradiction and an un-applied "add these rows manually" mid-migration block — exactly the documentation-shaped cruft this audit targets.
- **The mechanism:** A first-class, repeatable audit pass — not a one-time cleanup — that classifies every entry in CLAUDE.md / AGENTS.md into one of three buckets: (1) **execution surface** (changes agent behavior — keep, sharpen), (2) **dormant safety constraint** (changes behavior in ~0% of sessions but names a failure mode it prevents — keep verbatim, never delete), (3) **documentation** (the *why*, context, history — relocate to CONTEXT.md under a one-writer/one-reader freshness rule). The audit is guarded by `[canon §9]`'s golden rule — "if you can't name a failure mode the constraint prevents, the constraint is overhead" — which is the *correct* phrasing because it protects bucket (2), whereas Harness's literal "does it change behavior?" would delete the safety floor (pass2 §D). Host it on an existing surface (`/cr` doc-drift pass or `/compound`) and run it on a cadence, with the output being a per-file line-classification report and a drift delta since last run.
- **Citation:** Real gap — `[canon §3a]` (AGENTS.md "None open" contradiction), `[canon §7 item 9]` (un-applied manual-rows block), and the confirmed absence of any pass/skill/hook that classifies context-file entries by behavioral effect (pass3 §b item 1). The golden-rule guard is `[canon §9]` line 345.
- **Conservative disposition:** **Fully-applied, but scaled to "import exactly one thing."** MASTER-FINDINGS / pass3 §"Net recommendation": "Import exactly one thing: an execution-surface audit pass for CLAUDE.md/AGENTS.md, guarded by `[canon §9]`... Host it on an existing surface (`/cr` doc-drift pass or `/compound`), **not** on the non-existent `/scan-context`." It was adopted — but framed minimally, as a single doc-drift pass bolted onto an existing skill, and explicitly *not* given its own surface.
- **RE-JUDGMENT under the new charter: ELEVATE (moderately).** The audit itself is correct and the §9 guard is genuinely world-class — that judgment holds. What was conservative bias is the **hosting decision and the cadence**. The synthesis chose to bolt the audit onto `/cr` "rather than build `/scan-context`" partly because building a skill = more files, and the old charter treated more files as a red flag. Under the new charter (clarity beats minimalism; more skills are fine when each earns its place), a **dedicated `/scan-context` skill is the right home**, not a sub-pass smuggled into `/cr`. Reasons: (a) a doc-drift audit and a code review have different inputs, cadences, and outputs — fusing them buries the audit and means it only runs when you happen to be reviewing code; (b) a standalone skill can be invoked by a **scheduled cloud agent** (the resolved fact: cloud /schedule exists, clones the repo, runs committed skills) so the context-file audit runs *autonomously on a cron*, catching drift between human sessions instead of waiting for a /cr; (c) `disable-model-invocation` is irrelevant here (read-only audit) so there's no safety cost to giving it its own surface. The world-class form is bigger than "one pass on /cr": it is **a committed `/scan-context` skill that a weekly cloud routine runs across all 5+ repos, emitting a per-repo line-classification + drift report**, so context-file rot is caught fleet-wide by machine, not by a human remembering to audit. That is the move the conservative synthesis suppressed when it said "host on existing surface, not /scan-context."

### Move 2: Colocated behavioral spec per feature area (feature-scoped AGENTS.md)

- **Plain-English what & why:** A world-class org keeps the behavioral spec for a module *next to the module*, owned and updated by whoever changes that code. The failure it prevents: a single root context file that every team edits becomes a merge-contention, ownership-diffusion bottleneck where nobody is accountable for any given rule, and rules for unrelated areas drown each other out. Harness's version: module engineers own their module's AGENTS.md, not a central platform team.
- **The mechanism:** Split event-vendor's monolithic root AGENTS.md/CLAUDE.md into feature-area sections (vendor management, event creation, payment flows), each maintained alongside its feature, with `/compound` updating the relevant section after each AFK session.
- **Citation:** Confirmed absence + answered open question — pass3 §b item 4: direct disk check found the *only* AGENTS.md/CLAUDE.md at repo root; everything is in one root file. `[canon §3a]` treats root CLAUDE.md/AGENTS.md as "aligned in purpose."
- **Conservative disposition:** **Rejected-with-reason at solo scale.** Pass3 §b item 4: "Recommendation: not a gap worth closing now. Splitting into feature-area files at solo scale buys discovery-locality the article can't show matters (its discovery hierarchy is unverified) at the cost of more files to keep non-stale — and `[canon §4]` already shows our staleness/duplication problem is our worst one." Pass2 §C reinforces: the ownership argument collapses to "colocate the spec," which is just "docs near code" restated.
- **RE-JUDGMENT under the new charter: UPHELD-CUT.** This is a real cut even at world-class fleet scale, and I name the failure mode that justifies it (per the §9 golden rule). **Failure mode the split causes: it multiplies the staleness surface against a non-deterministic reader with no eval to verify freshness.** event-vendor's single worst problem per `[canon §4]` is staleness/duplication across knowledge stores ("triple-duplication the canon both sanctions and forbids"). Feature-scoped context files take one file with one freshness obligation and turn it into N files, each of which can independently rot — and the agent loads several of them per task, so a stale feature-section silently corrupts behavior with no compiler to catch it. The *org-chart* benefit Harness cites (avoiding a central-team bottleneck, parallel module ownership) does not exist when one person + an agent fleet own everything: there is no contention to relieve, only new rot surfaces to maintain. The discovery-locality benefit the article claims rests on its 100/80/40/<10 discovery hierarchy, which pass2 §E shows is unverified vendor-sourced and partly tautological. **This is the discipline that keeps the re-mine honest:** under the new charter "more files is fine when each earns its place" — and these files do *not* earn their place, because each one adds a rot surface without relieving any contention. ELEVATE-everything reflexively would adopt this; the correct call is to hold the cut and state why. (Re-examine only if event-vendor itself grows to genuine multi-team module ownership — then it flips to ELEVATE.)

### Move 3: In-pipeline / governed agent actions (RBAC + audit + rollback inherited by the agent)

- **Plain-English what & why:** Harness's distinctive product move: agents run *inside* CI/CD pipeline stages, so every action an agent takes inherits the pipeline's secrets scoping, RBAC, audit log, and rollback semantics — the agent is governed structurally, not by hoping it behaves. The failure it prevents: an ungoverned agent that can take an action no human can trace, undo, or attribute, in a regulated/compliance environment.
- **The mechanism (our scale):** The article's own translation — "agent runs in GitHub Actions; Claude Code permission model + PreToolUse hooks as the RBAC equivalent; ci.yml as in-pipeline verification."
- **Citation:** Already built — `[disk §3e]` (`block-dangerous-git.sh`, `block-npm-install.sh`, `permission-logger.sh`, `worktree-create.sh` prod-key firewall), `[disk §3f]` (`ci.yml` + `integration.yml` run tsc/lint/vitest on every PR). Pass3 §a items 2-3.
- **Conservative disposition:** **§E already-built.** Pass3 §a: "Claude Code permission model + PreToolUse hooks as the RBAC equivalent — already built... In-pipeline verification at our scale — already built." Correctly notes "we already do agent-output-validated-in-pipeline; we just don't (and shouldn't) do Harness's agent-*inside*-the-pipeline-stage."
- **RE-JUDGMENT under the new charter: UPHELD-CUT (partial — one autonomy-relevant sliver to ELEVATE).** The "don't run agents *inside* pipeline stages" verdict holds even at fleet scale: putting an LLM inside a CI stage where its actions inherit production secrets and auto-rollback is the *exact* threat surface the PocketOS incident and our Tier-0 prod-key firewall exist to prevent — an agent with a subtle bug producing "plausible-looking output" (the article's own open question #3) that the pipeline then trusts. **Named failure mode: a probabilistic agent inheriting pipeline secrets + RBAC can take an irreversible, fully-attributed-but-wrong production action with no human gate.** That is a genuinely bad fit at any scale and the cut is correct. **However** — the new charter's autonomy mandate (bug → reviewed PR) does reframe the *audit-trail* half of Harness's idea: see Autonomy angle. The sliver worth ELEVATING is not "agent in pipeline" but "**every autonomous agent action emits a structured, queryable audit record**" — which we have only as a `permission-logger.sh` log, not as a first-class accountability artifact a human can review before a PR auto-merges.

## Autonomy angle

The source is **mostly not about autonomy triggers** — there is no bug→PR, Slack/Linear summon, or self-improving loop in it. But two threads connect, and the new charter makes both live:

1. **Cloud-scheduled context-file audit (the real autonomy unlock here).** Move 1's `/scan-context` audit is a perfect fit for the resolved fact that cloud /schedule exists, clones the repo, and runs committed skills with no laptop open. A **weekly cloud routine** that runs the execution-surface audit across all 5+ repos and reports drift turns a manual discipline into a self-maintaining one. This is the autonomy angle the conservative synthesis could not see, because it pre-dated treating the scheduler as in-scope — it parked the audit on `/cr` (human-triggered) instead of on a cron (machine-triggered).

2. **Audit-trail-as-accountability for autonomous actions.** Harness's load-bearing governance claim — "in-pipeline agent actions inherit the human audit trail; RBAC as accountability infrastructure" (pass1 §4) — is exactly what an autonomous bug→PR loop needs to be *safe*. When an agent goes from a Linear ticket to a merged PR with no human in the middle, the thing that keeps it accountable is a structured, queryable record of every action it took and why, reviewable before merge. We have `permission-logger.sh` (a flat log), not a structured per-run accountability artifact. Harness's principle ("governed if inside, unverified output if outside") argues that autonomous agents need their audit trail to be **first-class and inspectable**, not a side-effect log — a real input to the self-improving / auto-merge gate the new charter wants.

Beyond those two: **none** on direct triggers (no summon, no self-improving loop primitive in this source).

## The single biggest move (one paragraph)

Pick up **Move 1 in its elevated form: a dedicated, committed `/scan-context` skill that performs the execution-surface audit — guarded by the `[canon §9]` "name the failure mode" rule so it can never delete a dormant safety constraint — and that a weekly cloud routine runs autonomously across every repo in the fleet.** It is world-class because it fixes the highest-leverage, lowest-glamour failure in an agent harness: context files are the agent's program, and a bloated/stale/contradictory one degrades *every* task the agent runs, silently, with no compiler to catch it. The conservative synthesis got the audit right and the guard right, but shrank it to a sub-pass on `/cr` to avoid building a skill — leaving it human-triggered and review-coupled. The new charter removes that constraint: build the skill (clarity beats minimalism), give it its own surface, and put it on the scheduler so context-file rot is caught by machine across the whole fleet between human sessions. That is the difference between "we audit our CLAUDE.md when we remember to" and "our context files cannot rot, because a cloud agent verifies them every week in every repo" — and the second is the only one that holds at the scale of parallel agent fleets.
