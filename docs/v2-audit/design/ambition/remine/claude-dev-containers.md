# Ambition Re-mine -- Claude Code Dev Containers (Sandboxed Agent Execution Environments)

## What this source is (plain English, 2-3 sentences)

The official Claude Code "Development containers" feature: an OS-level sandbox you run the agent inside, so that `--dangerously-skip-permissions` (no approval prompts) becomes the *designed* way to run an unattended agent rather than a foot-gun. The article's real payload is that the container is **not** the safety boundary -- the **egress firewall** (an iptables allowlist that blocks all outbound traffic except a named set of domains) is the only control that works independently of the agent's own reasoning, and a root-owned `managed-settings.json` is a policy file the agent literally cannot edit. The conservative pass concluded "Candidate, not Adopted -- follow-on hardening, the threat hasn't materialized."

That conclusion was written under the OLD charter (autonomy deferred, solo scale, threat model "hasn't bitten us"). Under the NEW charter -- autonomy is first-class, cloud `/schedule` already runs agents unattended on Anthropic infra, and a world-class engineer runs parallel fleets across 5+ repos -- the entire risk calculus inverts. The thing this article is *about* (running an agent with no human in the loop) is now the thing we are explicitly building. So the "decline-to-build" verdict is exactly the kind of conservative bias the re-mine charter says to re-examine.

## The full-ambition moves this source teaches

### Move: The egress firewall as the safety architecture that MAKES autonomy safe (not "follow-on hardening")

- **Plain-English what & why:** When an agent runs with no human approving each step (overnight, scheduled, summoned from Slack), the one failure you cannot prevent by being careful is *prompt injection*: a malicious string in a GitHub issue, a dependency's README, a webpage the agent fetches, or a Linear ticket convinces the agent to `curl` your credentials (`~/.claude`, `.env.local`, Supabase service key) to an attacker's URL. Permissions don't stop this -- the agent *wants* to make the call, it's been manipulated. The only control that survives a compromised agent is one that operates *below* the agent: an OS-level egress firewall that blocks every outbound connection except a hardcoded allowlist (Anthropic inference, Supabase, GitHub, npm, Vercel). The agent can't talk itself out of a packet that iptables drops. The article's sharpest line: "`--dangerously-skip-permissions` without the egress firewall is a convenience feature. With the egress firewall it is a safety architecture."
- **The mechanism:** Build the egress allowlist as a real enforced artifact, not just documentation. Two enforcement tiers, both in-scope now: (1) **Tool-call layer** -- the absent `block-dangerous-bash.sh` PreToolUse guard intercepts `curl`/`wget`/`fetch` to any host not on the allowlist and exits 2 (deterministic, container-free, works on host macOS and in cloud `/schedule`). (2) **OS layer** -- for the autonomous fleet tier (overnight `/queue`, scheduled routines), an actual `init-firewall.sh` iptables allowlist inside a per-agent container or the cloud sandbox. The allowlist itself becomes a committed, versioned file in the harness that both tiers read.
- **Citation:** `[canon §08 / §5 build-or-reject row: block-dangerous-bash.sh -- "3rd structural guard (deploys, rm -rf, boundary writes)"]` + `[disk §3e: "Canon's 3rd guard -- ABSENT on disk. Disk has no safety-floor bash guard"]`. Egress allowlist as artifact: `[absent: no documented egress allowlist in the ground-truth map]`.
- **Conservative disposition:** §C deferred / scaled-down-as-"doesn't-apply-to-solo." Pass-3 (b)1 partially rescued the tool-call layer (the absent bash guard) as a real gap but framed it as getting "a large fraction of the egress firewall's blast-radius value with **zero** DinD, zero NET_ADMIN, zero container" -- i.e. it kept the cheap tool-call version and *rejected the OS-layer firewall outright* ("the container, the volumes, the DinD analysis, and the firewall-in-a-container are all correctly **rejected** against the map"). The verdict rested on pass-1 §8's "the threat model has not materialized in the 4-task and early 10-task batch runs."
- **RE-JUDGMENT under the new charter: ELEVATE.** The dismissal fails the charter on two independent counts. First, the "hasn't materialized" test is the wrong test for a *safety* constraint -- the ground-truth's own §9 Golden Rule ("name a failure mode the constraint prevents, or it's overhead") is *satisfied*: the failure mode (overnight prompt-injection -> credential exfil) is vividly nameable, and §9 explicitly flags treating a safety constraint like a quality constraint as "the PocketOS incident." The pass-2 analysis already caught this but the conservative synthesis collapsed it into a wiring tweak. Second, and bigger: the charter states cloud `/schedule` *exists and runs unattended on Anthropic infra*, which means we are NOW shipping the exact scenario the firewall protects -- an agent processing untrusted input (issues, tickets, web content) with no human in the loop, across 5+ repos. The blast radius of one prompt-injected scheduled agent is every credential in every repo it can reach. This is not "follow-on hardening"; it is a **precondition for turning autonomy on at all.** How much bigger: the conservative synthesis yielded ONE row (build the bash guard). The elevated move is a two-tier egress architecture: (1) the committed allowlist artifact, (2) the bash-guard curl-block for host/cloud runs, AND (3) a real OS-layer firewall for the highest-autonomy tier (cloud sandbox / per-agent container) -- explicitly designed-in, not rejected. The old "reject the container firewall" reasoning was pure solo-scale bias: at fleet scale the firewall is the difference between "one repo compromised" and "all five."

### Move: Image-baked / root-owned `managed-settings.json` -- a policy floor the agent physically cannot edit

- **Plain-English what & why:** Today the harness's entire policy surface (`settings.json`, deny rules, allow lists, `.claude/hooks/**`, CLAUDE.md) lives *in the repo as files the agent can read and, in principle, write*. The harness compensates with a behavioral rule ("never edit guard files -- surface as NEEDS HUMAN") and a PreToolUse deny on `/.claude/hooks/**`. But that is "a rule the agent is asked to follow," and the deny entry is itself in a file an agent could edit first. For an autonomous agent running unattended, "asked to follow" is not a boundary -- a sufficiently confused or injected agent edits `settings.json` to remove its own deny rules, then does the dangerous thing. `managed-settings.json` is a Claude Code settings-precedence feature that sits at the **highest** precedence, overriding all user and project settings, and is placed at a root-owned OS path (`/etc/claude-code/`) that the non-root agent user cannot write. It is the difference between "a constraint the agent cannot circumvent" and "a rule the agent is asked to follow."
- **The mechanism:** Place a root-owned `managed-settings.json` on the host (and bake it into any cloud-sandbox / container image) carrying the non-negotiable floor: the deny list (destructive ops, guard-file edits, credential reads), the main-branch commit block, the prod-key firewall invariants. The agent runs as a non-root user; the file is `chown root:wheel` / mode 644. This gives the deterministic, agent-unreachable policy backstop that BOTH canon and disk currently lack -- the ground-truth's net-enforcement note says the system is "overwhelmingly advisory -- neither has a deterministic backstop for the bulk of skill bodies, CLAUDE.md rules, or the autoMode lists."
- **Citation:** `[absent: deterministic agent-unreachable policy floor]` via `[disk §3e net-enforcement: "Both agree the system is overwhelmingly advisory -- neither has a deterministic backstop..."]`. Related canon gap: `[canon §09: ~/.claude/CLAUDE.md global behavior config -- "the global layer's missing keystone," absent globally]`.
- **Conservative disposition:** §C deferred, gated on a doc-check. Pass-3 (b)3 rated it "the article's single most valuable mechanism, extracted from the container" but tagged it "Confidence: directional -- the host-OS precedence behavior of `managed-settings.json` outside a container needs a one-line doc confirmation before building." So even the rescued version was held behind a research gate and never made it into the synthesis's 6 moves as a build item.
- **RE-JUDGMENT under the new charter: ELEVATE.** The mechanism is correct and the conservative framing under-rates it for one reason: it treated "agent-editable policy" as a low-probability problem ("in principle") because no agent had yet edited its own deny rules in the small batch runs. Under first-class autonomy that probability is no longer hypothetical -- it is the *defining* attack on a self-improving loop (an agent that can edit its own constraints is an agent with no constraints). The charter explicitly says `disable-model-invocation:true` is "what makes autonomy safe" -- managed-settings is the same doctrine one layer down: the deterministic, model-unreachable floor. This should be IN-SCOPE-NOW, not gated behind a doc-check. The doc-check is real (does host macOS honor `/etc/claude-code/managed-settings.json` natively?) but it is a 5-minute lookup, not a reason to defer the design. And there is a charter-aligned escalation the conservative pass never reached: for the *cloud `/schedule`* tier, the image is built fresh on Anthropic infra each run, so the managed-settings file is baked into the image by definition -- the "host precedence" uncertainty disappears entirely. So managed-settings is unconditionally available in exactly the tier (autonomous cloud runs) where it matters most. The old reasoning ("editable in principle, threat unproven") is solo-scale bias applied to what is now the central trust-boundary of the autonomous harness.

### Move: Per-agent OS-level isolation for the parallel fleet (close the worktree isolation gap)

- **Plain-English what & why:** `/queue` runs parallel agents in git worktrees -- separate branches and working directories, but **same host**: same filesystem, same network stack, same Claude binary, same `~/.claude`. That gives branch-level isolation (two agents can't merge conflicting changes) but NOT process isolation. A prompt-injected agent in worktree A can read worktree B's files, B's `.env.local`, B's session history, and exfiltrate them -- because they all live on one host the agent can `cat`. At solo scale with 4 trusted tasks this is theoretical. At fleet scale -- 23 agents, parallel `/queue` batches, scheduled routines, summoned-from-Slack runs processing untrusted input -- "one agent reads all the others' secrets" is a real lateral-movement surface. Dev containers (or the cloud sandbox) close this by giving each agent its own filesystem and network namespace.
- **The mechanism:** Tier the isolation by autonomy level rather than all-or-nothing. (1) Trusted interactive work -> worktree on host (today, unchanged). (2) Untrusted-input or unattended work (Slack summon, scheduled, overnight `/queue`) -> one container OR cloud sandbox per agent, each with its own `${devcontainerId}`-scoped (better: per-worktree-scoped) `~/.claude` volume and its own egress firewall. The cloud `/schedule` runtime already provides this isolation for free (clones the repo, runs in its own sandbox) -- so the move for *scheduled* autonomy is "route it to cloud `/schedule`," and the local container is only needed for unattended-but-local runs.
- **Citation:** `[disk §3e: worktree-create.sh -- "Disk-only (prod-key firewall); a genuine disk advance over canon"]` (the existing isolation primitive) + pass-1 §6 isolation-gap analysis (worktrees give branch isolation, not OS process isolation; `[absent: per-agent OS-level filesystem/network isolation]`).
- **Conservative disposition:** §F rejected -- "the dev container itself ... DinD resolution -- all are solutions to container-only problems we do not have." Scaled-down explicitly as "doesn't apply to solo": pass-1 §8 said "Today's blocker for overnight runs is task dependency management and agent throughput, not blast radius," and the §F kill-list flagged the "dev-container/VM/microVM/gVisor sandbox stack" as "wrong threat model at solo scale."
- **RE-JUDGMENT under the new charter: ELEVATE (partial) -- with one UPHELD sub-cut.** ELEVATE the *principle*: per-agent isolation IS warranted once the fleet processes untrusted input unattended, because cross-agent credential reads are a nameable failure mode (charter: "the real scale is a world-class engineer running parallel agent fleets across 5+ repos" -- exactly the scale where lateral movement matters). The §F rejection ("wrong threat model at solo scale") is struck verbatim by the charter's rule that "too much for a solo dev" is not a valid rejection. BUT the *local DinD dev-container for the Supabase test stack* is an UPHELD-CUT (see below) -- the right vehicle for isolated autonomous runs is the **cloud `/schedule` sandbox**, which the charter confirms already provides repo-clone + isolated execution, not a hand-rolled local DinD container. So: elevate "isolate autonomous agents from each other," but realize it through cloud sandbox routing + a host managed-settings/egress floor, NOT through the local DinD container the article centered on.

### Move: Per-worktree credential scoping -- stop the symlink from re-sharing the prod key into every worktree

- **Plain-English what & why:** The harness has a real Tier-0 prod-key firewall (`gen-local-env.sh`, `test-local.sh`) that isolates the *local* Supabase stack credentials per worktree. But each worktree's `.env.local` is a **symlink to the root `.env.local`, which points at production**. So every worktree -- and every parallel agent -- shares the identical production Supabase credential. A prompt-injected agent in any worktree reads the prod service key trivially, and the Tier-0 firewall it was supposed to be protected by is partially defeated, because the firewall isolates the local-stack creds, not the shared prod symlink.
- **The mechanism:** Scope production credentials per-worktree (or, better, don't put the prod service key on disk in every worktree at all -- inject it only for the specific task that needs it, via the managed-settings / containerEnv path the article recommends over host credential-file mounts). At minimum: the symlink should resolve to a per-worktree env that carries only the credentials that worktree's task requires.
- **Citation:** pass-1 §9 transfer row + pass-2 §6: `[absent: per-worktree credential isolation at the .env.local layer]`; the Tier-0 firewall it undercuts: `[disk §6 / §3e: worktree-create.sh + prod-key firewall -- "a genuine disk advance (Tier-0 credential isolation)"]`; `[memory: "vitest reads .env.local which is prod," "No .env credential reuse"]`.
- **Conservative disposition:** Fully-applied as a wiring tweak. Pass-3 (b)2 rated it "the cheapest defensible hardening in the article and it needs no container" -- one of the 3 rows the article was allowed to contribute.
- **RE-JUDGMENT under the new charter: ELEVATE (in priority, not scope).** The conservative pass got this *right* as a finding but under-rated its *urgency* by treating it as a cheap one-off. Under first-class autonomy across 5+ repos, the shared-prod-credential symlink is the single most-exploitable hole: it converts any single prompt-injection in any worktree into full production database access, and it does so identically in every parallel agent. This is not the cheapest "nice to have" -- it is the highest-priority precondition for letting unattended agents touch worktrees at all. Same scope as the conservative version; an order of magnitude more urgent. Pair it with Move 1 (the egress firewall) and Move 2 (managed-settings) and you have the three-piece minimum credential-safety floor for autonomy.

## Autonomy angle

This source is **directly about autonomy** -- more so than its conservative verdict admits. The entire feature exists to answer "how do you run `--dangerously-skip-permissions` (no human approving each step) safely?" which is the autonomy question. Specific teachings:

- **Self-improving loops:** managed-settings (Move 2) is the mechanism that makes a self-improving loop safe -- an agent that can edit its own deny rules has no constraints, so the policy floor must live where the agent cannot reach it. This is the same doctrine as `disable-model-invocation:true`, one OS layer down.
- **Cloud scheduling:** the charter's confirmed cloud `/schedule` (Anthropic infra, restricted network by default, repo-clone, isolated execution) is the *natural home* for the article's container -- it already provides per-run isolation and a fresh image, which dissolves the article's two biggest objections (DinD for the local stack, and host-precedence uncertainty for managed-settings). The source teaches what the egress allowlist for a scheduled run must contain (Anthropic inference, Supabase, GitHub, npm, Vercel) -- directly useful for configuring `/schedule`'s restricted network.
- **Bug -> PR / Slack-Linear summon:** the threat model the firewall addresses (untrusted input -> exfil) is exactly what a summoned-from-Slack or bug->PR agent faces, because the triggering payload (issue body, ticket, Slack message) is attacker-controllable. The source argues the egress firewall is the only control that survives a compromised agent processing such input.

It teaches nothing about the *trigger front-door itself* (how the bug becomes a PR), but it teaches the *safety envelope* that front-door must run inside.

## The single biggest move (one paragraph)

Build the **two-tier egress firewall as enforced artifact** (Move 1), starting with the committed allowlist file + the absent `block-dangerous-bash.sh` curl-to-non-allowlisted-host guard, and designing the OS-layer firewall in for the cloud-`/schedule` / per-agent-container tier. This is the move the vision synthesis should pick up first because it is the one control that operates *independently of the agent's own reasoning* -- the only thing that still protects you after a prompt injection has fully compromised the agent's judgment. Every other autonomy feature the charter wants (bug->PR, Slack summon, scheduled self-improving loops) processes attacker-controllable input with no human in the loop; without the egress firewall, every one of them is a credential-exfiltration vector across all 5+ repos in the fleet. The conservative synthesis rejected this as "wrong threat model at solo scale / hasn't materialized" -- but the charter makes autonomy first-class and the ground-truth's own §9 Golden Rule says a nameable failure mode is not overhead. The failure mode (overnight injection -> `curl` the prod key to an attacker) is nameable, vivid, and now in-scope by design. World-class autonomous harnesses don't add the firewall after an incident; they build the cage *for the autonomous car they are about to switch on*.
